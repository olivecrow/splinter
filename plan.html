1. 제품 목적과 변경할 수 없는 요구사항

1.1 해결하려는 문제

Codex 같은 AI 코딩 도구에 개발 작업을 맡길 때, 동일 프로젝트의 동시 실행 제약 때문에 막히는 병렬 작업을 유연하게 수행하도록 하는 도구를 만든다. Unity 프로젝트는 코드 외에도 많은 에셋과 큰 임포트 캐시를 포함하므로, 작업마다 프로젝트 전체를 일반 복사하고 삭제하는 방식은 반복 비용이 크다. 각 대화의 AI가 필요할 때 독립 작업공간을 확보하고, 여러 차례 대화하며 작업한 뒤 사용자의 완료 의도에 따라 반영·보존·폐기하는 것이 제품의 기본 사용 모델이다.

Unity의 제약은 “PC 전체에서 Editor 하나만 실행 가능”이라는 뜻이 아니라, 같은 프로젝트가 이미 열려 있을 때 그 프로젝트를 다른 Editor·batch 실행이 동시에 사용할 수 없다는 것이다. 이 제품은 잠금을 우회하지 않고 작업별로 다른 프로젝트 경로와 쓰기 상태를 제공한다. [5]

제품의 우선순위는 대형 프로젝트의 작업공간 용량 부담 해소가 1순위, Editor 동시 실행이 2순위다. 각 대화의 AI가 전체 에셋 복제 없이 독립 파일 작업공간에서 병렬로 편집하고, 프로그램이 지속 상태·검증·결과 통합·정리를 관리한다. Unity 실행은 독립 Editor와 단일 Editor 순차 검증을 분리해 평가한다.

저장공간 우선 후속: 공통 저장소 1차의 SF-01 소스 검증은 정의한 범위에서 통과했고 SF-02는 계측·명시적 저널 정리 하위 범위만 Partial이다. 기존 VSS 보존 실패로 공통 저장소 1차 단위는 미완료이며 격리 볼륨의 보존·회수 검증 뒤 지연 회수 1차에서 대기 상태·명시적 재시도·공유 VSS 공간 관측을 연결했다. 저널 정리 1차는 결과 수집 전 대체 범위의 할당 회수와 제한된 중단 복구를 검증한다. 쓰기별 flush 정책 변경·단일 Editor 연결과 SF-03~06은 미실행이다. 기본 실행 방식 선택은 미확정이다. 기존 독립 Editor·원본 지속 편집·전체 복제/읽기 hydration 금지와 PV 제한을 유지한다.

AI 개발 작업의 병렬화AI가 코드·테스트·에셋 작업을 독립적으로 수행한다. 사용자가 복제 폴더와 Editor 연결을 직접 관리하지 않는다.
범용 코어, 첫 구현은 Windows·UnityOS·파일시스템·애플리케이션·버전관리·에이전트 연결을 교체 가능한 계약으로 분리한다. 다른 환경의 실제 구현은 포크와 기여로 확장할 수 있게 한다.
CLI가 제품의 기본 인터페이스설치·연결 후 사용자는 자연어로 작업만 지시한다. 실제 명령 실행·상태 확인·실패 복구·명시적 완료/폐기는 각 대화의 AI와 Splinter Runtime이 CLI로 처리한다. 병렬 실행이 불필요하면 기존 프로젝트에서 직접 작업한다. GUI 대시보드나 MCP를 필수로 만들지 않는다.
실제 Git worktree와 수명주기 결합작업용 브랜치와 linked worktree를 생성하고, 같은 작업 루트에 CoW 소스·전용 Unity 상태를 제공한다. worktree 생성부터 회수까지 하나의 관리 절차로 취급한다. 독립 Git 저장소 복제를 기본 경로로 사용하지 않는다.

1.3 첫 공개 버전의 범위

항목첫 버전의 결정
제품 구성프로젝트용/전역용 설치·Codex 스킬/플러그인 연결, CLI/Runtime, Git 어댑터, 스냅샷·변경분 저장, Unity 어댑터/브리지를 제공한다. 별도 조정 AI·Runner·DAG·상주 DB는 기본 흐름의 필수 조건이 아니다. 현재 내부 알파 구현과 미구현 공개 목표를 구분한다.
Windows 저장소기존 Windows/NTFS 원본 + 작업 시작 시점의 불변 스냅샷 + 범위별 변경 저장. 최초 전체 복제·읽기 hydration·필수 ReFS 이관 없이 SO-01~06으로 검증한다. VSS/WinFsp의 SO fixture와 제품 NI-01~08의 1차 내부 알파 검증은 완료했다. NR 복구·파일 지원과 일반 프로젝트 지원은 미완료다.
기존 NTFS 프로젝트원본 위치·파일시스템을 유지하고 최초 전체 기준본도 만들지 않는다. 원본은 작업 중 계속 수정 가능하며 각 작업은 시작 시점의 스냅샷을 유지한다. 작업 기간 전체의 원본 쓰기 차단은 금지한다.
Git 지원일반 저장소와 기존 linked worktree에서 프로젝트를 자동 탐지한다. 새 작업은 고유 브랜치 + 실제 linked worktree로 생성한다. 일반 Git 연동은 선택 부가기능이 아니라 첫 제품의 필수 범위다.
Unity 지원실사용 프로젝트의 정확한 Editor 패치 버전부터 검증한다. 최신 버전 자동 선택이나 프로젝트 자동 업그레이드는 하지 않는다. API 설계 참고는 Unity 6.0·Test Framework 1.4다.
필수 Unity 기능코드·테스트 작성 후 컴파일·리로드 복구, 에셋 생성·수정·임포트, 실제 Play 진입·정지·관찰, EditMode/PlayMode 테스트 발견·실행·결과 회수.
병렬 범위작업공간 간 병렬, 같은 Editor의 변경 명령은 직렬. 에이전트·Editor·컴파일·GPU·외부 상태의 동시 사용 수를 각각 제한한다.
첫 버전에서 제외자체 커널 파일시스템 드라이버, 전역 싱글 인스턴스 강제 우회, 완전한 보안 샌드박스, 다른 OS/엔진의 실제 구현, 무중단 핫리로드, 의미적 무충돌 병합 보장.

최초 전체 복제 없이 시작하고 변경한 범위에 필요한 공간만 사용한다. 소스·리소스·Library를 모두 같은 계약으로 다룬다. 스냅샷 보존 블록·메타데이터·신규 데이터·결과 저장 비용은 남고 전체 합계에 포함한다. ReFS 알파는 최초 기준본을 요구하므로 이 목표를 충족하지 않는다. NTFS 독립 실험 SO-01~06과 제품 workspace NI-01~08은 각각의 fixture 범위를 완료했다. PV 작업·비용 검증의 선택 범위는 제한을 유지해 마감했다. 공통 저장소 1차는 구현했으나 기존 VSS 보존 실패의 해결이 남으며, 설치·대화 연결·완료/폐기는 별도 후속 범위다. 복구·파일 지원 조건은 지원 확대의 필수 관문으로 유지한다.

1.4 설계 불변 조건

하나의 관리 worktree에는 하나의 논리 작업공간과 하나의 작성자 예약이 대응한다. 현재 활성 Editor나 전역 작업 폴더에 의존하지 않는다. 브랜치·작업 경로·Unity 인스턴스·에이전트 세션·검증 결과의 연결을 명시적으로 기록한다. AI가 수정할 파일을 틀리게 예측해도 해당 작업공간의 정상 쓰기는 다른 사본에 반영되지 않아야 한다.

원본 보호의 검사 대상은 사용자의 소스·현재 체크아웃·staged 변경·미저장 편집 상태다. linked worktree 생성과 결과 커밋에 따른 공유 Git 관리 정보의 정상 추가까지 “원본 변경 금지”로 오해하지 않는다. 동시에 Git 공유 구조와 일반 사용자 권한 코드를 완전한 보안 격리라고 표현하지 않는다.

“자유롭게 저작 가능”은 새 코드를 쓰고, 컴파일된 새 타입으로 에셋을 만들고, 실제 게임과 테스트를 실행할 수 있다는 뜻이다. 기본 흐름은 Play 종료 → 수정 → 동기화/컴파일 → Play 재진입이며, 컴파일·저작·Play를 한 Editor에서 무조건 동시에 허용한다는 뜻이 아니다.

2. 설치·필요 시 사용·대화별 작업·명시적 종료

2.1 사용자가 보는 경험

사용자는 “이 프로젝트에서 병렬 작업용 Splinter를 쓰도록 가져와줘” 또는 “전역에서 쓸 수 있게 설치해줘”라고 요청한다. AI가 요청 범위의 실행 파일·의존성·Codex 스킬 또는 플러그인 연결을 준비한다. 그 뒤 평소 사용하는 각 대화에서 직접 작업을 지시한다. 별도 조정 AI나 새 하위 작업자 실행은 필요하지 않다.

사용자: 프로젝트용 또는 전역용 설치 요청
→ 해당 대화의 AI: Splinter 설치 · 지침 연결 · 실제 발견/진단 확인
→ 대화 A: “Splinter로 병렬 작업해줘” → 작업공간 A에서 수정·검증
→ 대화 B: 같은 프로젝트의 독립 실행 필요 → 작업공간 B에서 수정·검증
→ 각 대화: 추가 요청 · 수정 · 검증 · 같은 작업 재개를 반복
→ 사용자: “A는 원본에 반영하고 정리해줘” → A 통합·회수, B는 유지
→ 사용자: “B는 필요 없으니 버려줘” → 원본 반영 없이 B만 폐기
※ 독립 실행이 필요 없는 요청은 기존 프로젝트에서 바로 작업

대화나 AI 응답 종료, Editor 종료, 시간 경과를 작업 완료로 간주하지 않는다. 사용자의 명시적 반영·보존·폐기 의도에 따라 해당 작업만 끝낸다. “정리”가 코드 정리인지 병렬 작업 종료인지 문맥상 모호한 경우에만 의도를 확인한다. 이미 명확한 완료/폐기 요청에는 같은 승인을 반복하지 않는다.

운영 계약·구현 책임과 SW-01~10 관문은 대화별 작업과 설치 계획에 정의한다. 설치·자동 binding·discard는 아직 미구현이고 기존 workspace 명령의 성공과 구분한다.

2.2 프로젝트용·전역용 설치와 Codex 연결

설치 범위제품이 준비할 것완료 기준
프로젝트용해당 프로젝트 정책·버전 참조와 저장소 범위 스킬 연결. 검증한 공용 실행 파일은 재사용 가능해당 프로젝트에서만 발견·진단 성공. 다른 프로젝트의 정책·전역 PATH 불변
전역용현재 OS 사용자 범위의 실행 파일/경로와 공용 스킬 또는 플러그인. 프로젝트 정책은 별도 적용여러 프로젝트에서 발견, 각 프로젝트의 연결·상태는 독립. 머신 전체 설치는 명시 요청/필수 권한 경계로 제한
기존 설치와 공존버전·의존성·기존 설정을 읽고 호환 설치 재사용, 변경 소유 manifest 저장재요청의 중복 설치/연결 없음. 동일 대상 저장소는 공통 상태 저장소·잠금 사용
최소 연결CLI 운용 스킬을 우선 연결하고 배포 시 스킬 포함 플러그인 제공 가능. MCP는 선택기존 AGENTS.md·인증·설정 보존. 설치된 실제 Codex에서 명시/암묵 호출과 미사용 확인
업데이트·제거활성 작업의 버전 유지, 해당 설치 소유 연결과 사용하지 않는 배포물만 정리공유 설치·타 프로젝트·미완료 결과 보존. 도구 제거는 작업 폐기와 별개

설치는 self-contained 배포물과 필요한 Windows 의존성을 준비하고 개발 도구 빌드를 사용자에게 요구하지 않는다. 프로젝트용 설치가 외부 프로그램·드라이버까지 Unity 패키지 하나로 해결된다고 가정하지 않는다. 스킬은 저장소·사용자 범위에서 발견할 수 있고 배포용 플러그인은 스킬만 포함할 수 있다. 실제 설치 버전의 지원을 검사하며, 새 지침이 현재 대화에 보이지 않으면 필요한 재로딩/새 대화를 안내하고 작업 연결은 보존한다. [48][50]

기존 NTFS 원본의 이동·전체 복제·필수 ReFS/Dev Drive/VHDX 이관은 하지 않는다. 공급자·드라이버·권한의 실제 필요를 진단하고 정확한 설치/helper 경계만 처리한다. 설치는 모든 개발 요청에 Splinter를 강제로 적용하는 승인이 아니다.

이 조건의 병렬 작업에는 Codex의 별도 worktree 생성 기능 대신 Splinter의 workspace API를 사용한다. Splinter 내부의 실제 Git linked worktree는 유지한다. 두 관리자가 같은 작업공간을 소유하거나 일반 checkout을 중첩하지 않는다.

Core는 공급자 중립적인 작업 ID를 유지하고 Codex 대화 locator는 연결 어댑터가 관리한다. 대화 A/B의 task key·workspace·실제 루트·공통 상태 저장소·소유 세대·검증/완료 상태를 기록한다. 문맥 압축·새 CLI·대화 재개에도 이 기록과 실제 상태를 대조한다. 전역 “마지막 작업”이나 활성 창으로 대상을 추측하지 않는다. 현재 대화의 파일 편집 도구·명령·Editor가 실제로 같은 루트와 권한을 사용하는지 검증한다.

작업 생성은 선택된 저장소 모드의 전제조건을 따른다. 목표의 saved-working-copy 정책은 저장된 미커밋 변경을 일관된 내부 기준으로 보존하되 사용자의 index/HEAD를 변경하지 않는다. 현재 NTFS 알파의 clean 저장소 제한을 숨기지 않고, 미저장 Unity 메모리를 snapshot으로 취급하지 않는다.

2.4 작업 지속과 완료의 Unity 루프

각 대화는 코드·테스트·에셋 수정 → 올바른 Editor에서 sync/compile/import → 새 코드·에셋/Play/테스트 검증 → 추가 사용자 요청을 반복한다. 필요한 기능만 실행하고 간단한 편집에 불필요한 Editor를 시작하지 않는다. 현재 스크립트 알파와 후속 저작·Play·테스트 구현 범위를 구분한다.

사용자가 원본 반영·종료를 요청하면 최신 작업 소스를 검증·보존하고 최신 원본에 통합·검증한 뒤 해당 작업의 소유 자원을 회수한다. 결과만 보관하는 종료와 반영 없는 폐기도 별도 지원한다. A만 완료해도 B는 자기 기준으로 계속 작업한다. 원본 dirty·충돌·검증 실패에는 결과를 보존하고 성공을 주장하지 않는다. 상세 폐기 조건은 13절을 따른다.

3. 범용 모듈과 각 대화·프로그램의 책임

각 Codex 대화의 AI가 CLI를 직접 호출한다. 프로그램의 공통 상태·잠금·자원 제어가 동시 작업을 조정하며 별도 조정 AI를 요구하지 않는다. 설치와 대화 연결은 OS/AI 어댑터에, 작업의 의미와 편집은 대화의 AI에 둔다.

4. 원본 스냅샷·변경분 저장과 Git worktree

4.1 저장 배치

원본은 기존 위치에 유지하고 계속 수정 가능하다. 기준은 원본의 시작 시점 스냅샷이며 전체 파일 사본이 아니다. 작업별 가상 경로는 스냅샷 읽기와 전용 변경 저장소를 합성한다. 소스·Library 모두 같은 쓰기 격리를 적용한다. 제어 기록과 결과는 별도 소유 영역에 둔다.

기존 NTFS 원본 ── 시작 시점 스냅샷
                     ├─ 작업 A 경로 = 기준 읽기 + A 변경 범위/메타데이터
                     └─ 작업 B 경로 = 기준 읽기 + B 변경 범위/메타데이터
제어 영역: 기준 ID · 작업 ID · Git 연결 · 저널 · 사용량 · 회수 증거

4.2 저장 계약

최초 전체 복제, 읽기에 따른 영구 hydration, 큰 파일의 첫 쓰기에 따른 전체 copy-up을 금지한다. 일부 쓰기는 블록/범위별로 저장하고 삭제·rename·truncate·확장은 메타데이터와 변경 범위로 표현한다. mmap·자식 프로세스·원자적 파일 교체·잠금·변경 알림을 포함한다. 파일 감시 후 복사나 writable hardlink/junction을 쓰기 격리 수단으로 사용하지 않는다.

원본 변경 후에도 이전 작업의 기준은 유지돼야 한다. 새 작업의 기준 시점과 공유 여부를 명시한다. 공급자 수명·공간 압박·외부 스냅샷 소실은 명시적 실패/복구 상태로 드러내며 현재 원본으로 조용히 전환하지 않는다.

4.3 Windows 후보와 확장성

현재 우선 후보는 SO fixture를 통과한 VSS 시스템 CoW + WinFsp + 범위별 저널이다. 실제 Windows 11 Home/NTFS에서 원본의 계속된 수정, 기준 시점 유지, 작은 쓰기와 복구·회수를 확인했다. VSS 볼륨 전체 diff 비용·권한·보존 정책과 Unity 일반 호환성은 제품 통합에서 계속 검증한다. 최초 full-copy 공급자는 허용하지 않으며 WinFsp가 overlay 저장 정책을 대신 구현하지 않는다.

공통 스냅샷/변경 저장 계약과 OS 파일시스템·프로세스 어댑터를 분리한다. Linux/macOS의 FUSE 계열 확장은 후속 실제 구현이며 현재 지원으로 표시하지 않는다. ReFS는 기존 호환 볼륨에 대한 선택적 백엔드다. NTFS 데이터를 ReFS VHDX에 한 번 복사하는 경로는 정상 제품 경로가 아니다.

4.4 Git 연동

작업자가 사용하는 가상 경로 자체를 실제 linked worktree로 연결한다. Git 어댑터가 common directory·HEAD·독립 index를 관리한다. 원본 .git을 복제하지 않는다. 소스 기준과 저장된 상속 변경, 도구 overlay, 작업 결과를 구분하며 원본 HEAD/staged 상태를 변경하지 않는다.

4.5 생성 절차

  1. 프로젝트·Git·앱 호환성과 스냅샷/마운트 지원·예산을 검사한다.
  2. 일관된 시작 시점 스냅샷과 소스 provenance를 확보하고 원본의 계속된 수정을 허용한다.
  3. 작업 ID·경로·브랜치·저널을 예약한다.
  4. no-checkout Git 등록과 가상 파일시스템 마운트를 조정한다. .git 연결은 작업별로 제공하고 파일을 전체 전개하지 않는다.
  5. 파일을 다시 쓰지 않는 index 초기화, 기준/변경분 연결과 접근 검사를 완료한 뒤 WorkspaceReady를 발행한다.
  6. 전용 변경 저장소에서 Unity를 시작하고 필요한 임포트/컴파일과 준비 완료를 확인한다.

생성 단계마다 중단 후 동일 ID로 재조정해야 한다. Git 등록·마운트의 실제 순서와 호환성은 실험으로 고정한다. LFS/filter/CRLF 비용과 실패를 숨기지 않는다.

4.6 공동 수명주기

작업공간·Git 등록·마운트는 대응 관계를 유지한다. 해당 작업의 새 쓰기 중지·소유 앱과 자식 종료 → flush·현재 결과를 기준 스냅샷과 독립적으로 보존 → 열린 핸들/마운트 해제 → Git 등록/변경 저장소 회수 → 마지막 의존성이 없는 스냅샷 해제 순서로 정합성을 확인한다. 원본 Editor의 쓰기를 작업 기간 동안 막지 않는다. 결과가 여전히 기준 블록에 의존하면 기준을 먼저 삭제하지 않는다. 임대 만료·시간 초과·디스크 압박만으로 유일한 결과를 삭제하지 않는다.

4.7 외부 도구와 관찰

에이전트는 반환된 작업 경로를 사용한다. 외부에서 만든 worktree는 소유권·소스·실행 상태를 검사해 연결하며 이미 발생한 전체 checkout 비용을 절감 성과로 보고하지 않는다. 작업공간 밖 원본을 임의 수정하는 코드까지 차단하는 보안 샌드박스로 표현하지 않는다.

4.8 증거와 지원 경계

SO-01~06 fixture 증거는 전체·반복 읽기, 작은 쓰기, 원본/A/B 시점 격리, Git·Unity·mmap·잠금·알림과 장애/회수를 포함한다. 재부팅·전원 손실·실제 물리 볼륨 고갈·모든 명령 경계 중단은 NotRun이다. logical bytes와 file-data allocation을 구분하며 snapshot 보존·delta·메타데이터·캐시·Git/LFS 결과 비용을 모두 기록한다. 초기 measurement-v1-invalid의 물리 수치는 사용하지 않으며 실제 1TB 데이터셋 시험으로 확대하지 않는다.

5. Unity 스냅샷 확보와 파일 분류

5.1 시작 시점 확보

  1. 원본 HEAD·staged/unstaged/untracked·에셋과 .meta·Unity/패키지/설정·외부 의존성을 기록한다.
  2. 저장·임포트·캐시 쓰기의 일관된 체크포인트를 확인한다. 미저장 상태를 캡처했다고 간주하지 않는다.
  3. 원본 데이터와 Library의 시작 시점 스냅샷을 확보한다. 전체 준비 worktree나 필수 cold import를 만들지 않는다.
  4. 원본은 계속 편집할 수 있게 유지하고 작업은 고정 snapshot ID와 소스 provenance를 사용한다.
  5. 도구 브리지와 작업의 수정은 전용 변경 저장소에 기록한다. 작업 기여를 시작 시점/상속 변경/도구 변경과 구분한다.
  6. 실제 Unity 실행·임포트·컴파일로 캐시 호환성을 검증한다. 필요한 재작성 비용만 작업별로 기록한다.

디스크 스냅샷은 Unity 메모리 상태의 자동 캡처나 Library 정상성을 보장하지 않는다. 필요한 짧은 캡처 절차와 지원 한계를 검증한다. 캐시 오류를 원본 전체 Library 삭제나 별도 전체 데이터 사본으로 우회하지 않는다.

5.3 브리지 설치가 사용자 변경을 숨기지 않도록

현재 실험에서 고정한 실행 준비: 캡처된 Library/ilpp.pid, Library/Pipeline/.unity-pipeline-port, MCP 실행 PID 파일은 원본 프로세스의 주소를 담는다. 작업 전용 overlay에서 이 ephemeral 항목만 whiteout해 원본 compiler helper 간섭을 막는다. 재사용 가능한 Library와 원본 파일은 유지한다. 브리지의 도구 소유 경로·hash를 검증하고 최종 Git source 결과에서는 제외한다.

도구 설치 전 소스 상태와 도구 설치 후 실행 기준본을 별도 식별자로 기록한다. Packages/manifest.json과 잠금 파일에 도구 의존성을 추가했다면 해당 JSON 변경만 나중에 제거한다. 패키지 파일 전체를 결과에서 제외하면 AI가 의도한 다른 패키지 변경까지 잃는다.

권장 첫 배치는 작업공간에 포함되는 버전 고정 UPM 패키지다. 외부 절대 경로에 의존하는 링크보다 이동과 포크에 유리하다. 기본 브리지는 Editor 전용으로 두고, 런타임 관찰 코드는 필요할 때만 별도 모듈로 사용한다. 일반 Player 빌드에 개발 브리지가 포함되지 않는지도 자동 시험한다.

도구 overlay 때문에 발생한 Git 차이는 changes inspect에서 별도 항목으로 드러낸다. skip-worktree나 광범위한 ignore로 Packages 전체를 숨기지 않는다. 사용자 프로젝트에 정식 채택한 브리지는 정상 소스로 관리할 수 있지만, 실행용 주입은 결과 커밋 전 정확히 분리한다. 소스 스냅샷 작성·필터 적용·상속 변경 회수는 Git 어댑터 적합성 시험에 포함한다.

6. 외부 Host와 Unity 브리지

6.1 외부 프로세스를 제어의 중심으로 둔다

구현 경계: 이 절의 외부 제어는 일반 프로그램의 책임이며 조정 AI를 뜻하지 않는다. 현재 Splinter.Host는 읽기 전용 in-process 조합 계층이고 Runtime의 atomic JSON·잠금과 Windows supervisor가 상태·프로세스 수명을 유지한다. 상주 Host/DB와 아래 통신 변경은 필요가 입증되면 도입할 선택지이며 첫 공개의 선행 조건이 아니다.

Host는 사용자의 로그인 세션에서 일반 권한으로 실행한다. v0에서 GUI Editor를 Windows 서비스의 비대화형 실행 환경에 넣는 구성을 시도하지 않는다. Unity 실행 파일은 사용자가 등록한 설치 경로 또는 검증된 탐지 결과로 정하고, 프로젝트의 정확한 버전과 대조한다.

상주 GUI 실행에는 프로젝트 경로와 작업별 로그 경로를 지정한다. 같은 프로젝트를 별도 batch Editor로 동시에 열 수 없으므로, 열린 작업공간의 테스트는 내부 브리지로 실행하거나 해당 Editor를 닫고 batch 경로로 전환한다. 원본 프로젝트의 잠금 파일을 삭제해 중복 실행을 강제하지 않는다. [5]

Windows 실행기는 자신이 시작한 프로세스를 Job Object 등으로 추적한다. 자식 프로세스가 기본적으로 job에 포함되지만 breakaway 예외가 있으므로 종료 시험으로 확인한다. 프로세스 이름이 Unity.exe라는 이유만으로 다른 사용자의 에디터를 종료하지 않는다. 라이선스·Hub 같은 공용 프로세스도 일괄 종료 대상이 아니다. [33]

Gateway와 Host의 수명주기는 분리한다. 상주 Editor는 에이전트 연결 종료만으로 닫지 않는다. Host 재시작 후 세션을 회수할 모드에서는 이름 있는 Job을 사용하고 KILL_ON_JOB_CLOSE를 기본 활성화하지 않으며, PID·시작 시각·작업공간 세션을 대조해 다시 연결한다. 작업 취소 시에만 소유 프로세스를 명시적으로 종료한다. 이 정책과 자식 프로세스의 실제 동작을 중단 시험으로 검증한다. [33]

6.2 통신과 메인 스레드 실행

현재 작업별 파일 IPC를 사용한다. 통신 확장 후보로 사용자 ACL을 제한한 로컬 named pipe를 제안한다. 전송 계층은 교체 가능하게 두고 메시지는 JSON Schema로 정의한다. Unity 브리지는 외부 명령을 수신하되, Unity API를 호출하는 부분은 큐에 넣고 EditorApplication.update에서 실행한다. I/O 대기·명령 처리 완료 대기를 메인 스레드에서 동기적으로 막지 않는다. Editor의 갱신 이벤트와 상태 조회 API를 이 실행 루프의 관찰 지점으로 사용한다. [6]

연결 시 workspaceId, 정규화된 프로젝트 경로, 프로세스 식별자와 시작 시각, 프로토콜·브리지 버전, 실행 세대, 인증 토큰을 대조한다. 명령마다 작업공간과 실행 세대가 맞는지 다시 확인한다. 토큰은 로그나 Git 결과에 포함하지 않는다.

브리지 핵심 어셈블리는 프로젝트 게임 코드에 의존하지 않게 한다. UTF 연결도 선택적 별도 어셈블리로 분리해 테스트 패키지 불일치가 기본 통신 전체를 깨뜨리지 않도록 한다. 최소 부트스트랩을 사전 컴파일 DLL로 배포할 수 있지만, DLL이면 컴파일 오류나 Safe Mode를 무조건 우회한다는 가정은 금지한다. Safe Mode는 패키지를 포함한 프로젝트의 managed code 실행을 막는다. [12]

6.3 명령을 함수 호출이 아니라 지속되는 작업으로 취급한다

모든 장시간 명령은 먼저 외부 저널에 기록하고 operationId를 반환한다. 이후 조회·이벤트로 완료를 확인한다. 하나의 MCP 연결이나 Unity 객체가 계속 살아 있어야만 결과를 받을 수 있는 구조를 만들지 않는다.

필드 의미
operationId, workspaceId 중복 요청 식별과 작업공간 귀속
editorSession, domainEpoch 프로세스 재시작과 도메인 재생성을 구별
expectedRevision, payloadHash 오래된 소스나 다른 인자로 명령을 잘못 재사용하지 않도록 검사
status, phase, lastProgress 큐·실행·리로드 대기·완료·실패·불확실 상태
artifacts, diagnostics 실제 결과 파일과 구조화된 오류
retryPolicy, deadline 재시도 가능 여부와 명령 종류별 제한

Accepted는 완료가 아니다. 일반적인 상태 흐름은 다음과 같다.

Accepted → Running → WaitingForReload → Reconciling → Succeeded
                   └→ Failed / CancelRequested / OutcomeUnknown

에셋 생성이 끝났지만 응답 전 리로드가 발생할 수 있다. 이때 같은 생성 명령을 무조건 재실행하면 중복 에셋이나 덮어쓰기가 생긴다. 경로·GUID·내용 등 사후조건을 조회해 조정하고, 결과를 판정할 수 없으면 OutcomeUnknown을 반환한다. 임의 프로젝트 스크립트에 대해 일반적인 exactly-once 실행을 보장하지 않는다.

6.4 도메인 리로드와 준비 상태

AssemblyReloadEvents로 리로드 전후를 관찰하고, InitializeOnLoad에서 연결과 콜백을 재등록한다. 이 초기화 시점에는 에셋 임포트가 완료되지 않았을 수 있으므로 바로 에셋을 로드하지 않는다. 에셋을 필요로 하는 후속 작업은 임포트 상태와 OnPostprocessAllAssets를 함께 관찰해 재개한다. SessionState는 리로드 사이의 보조 상태로만 사용하고, 프로세스 재시작까지 필요한 기록은 Host에 보관한다. [9][10][11][14]

준비 상태는 단일 boolean 대신 두 축으로 표현한다. 수명주기: Starting / Connected / Reloading / Unresponsive / Exited. 작업 상태: EditIdle / Importing / Compiling / EnteringPlay / Playing / ExitingPlay / Testing / Blocked. 현재 phase와 마지막 성공 소스 상태를 함께 반환한다.

EditIdle은 단순히 isCompiling == false라는 뜻이 아니다. 해당 소스 변경이 반영됐고, 필요한 컴파일·리로드와 임포트가 정리됐으며, 알려진 오류와 진행 중인 변경 명령이 없는 상태여야 한다. 상태 이벤트가 잠시 멈춘 것만으로 이 조건을 충족했다고 판단하지 않는다.

7. 코드 변경 → 컴파일 → 실행 가능한 상태

7.1 파일 편집 계약

작업공간마다 한 명의 작성자만 파일을 바꾸도록 예약한다. AI가 직접 파일을 수정할 수 있지만, 테스트나 에셋 저작 명령이 진행 중인 동안에는 새 편집을 시작하지 않게 한다. 외부 파일 쓰기와 에디터 변경의 경계를 edit.begin / edit.commit으로 표현한다.

파일은 가능하면 프로젝트 밖에서 완성한 뒤 작업공간 내부로 반영한다. 짧은 반영 구간에만 자동 refresh를 제어하고 반드시 복원한다. 네트워크 왕복이나 AI 응답을 기다리면서 에셋 임포트·어셈블리 리로드를 잠그지 않는다. 편집 계약을 우회한 수정이 감지되면 진행 중 검증 결과를 오래된 결과로 표시한다.

7.2 동기화 명령의 절차

  1. 진입 조건 확인: Play와 테스트를 끝내고 편집 소유권을 확인한다. 변경된 파일과 설정에 대한 소스 상태 식별자를 기록한다.
  2. 패키지 처리: manifest 변경이 있으면 해당 버전의 UPM 절차로 해결한다. Client.Resolve는 변경할 것이 없으면 이벤트가 없을 수 있으므로, 호출했다는 이유로 반드시 완료 이벤트가 올 것이라고 기다리지 않는다. 설치 결과·잠금 상태·진행 중 요청을 확인한다. [38]
  3. 변경 알림: AssetDatabase.Refresh 또는 대상별 임포트를 호출한다. .cs, .asmdef, .asmref, .rsp, DLL, define·타깃 설정 변경을 코드 관련 변경으로 분류한다. refresh 자체가 코드 컴파일과 추가 임포트를 유발할 수 있다. [13]
  4. 컴파일 추적: CompilationPipeline의 시작·어셈블리별 완료·전체 완료 이벤트를 수집한다. 필요한 경우 RequestScriptCompilation을 사용하되, refresh가 이미 같은 변경을 처리한 경우 중복 요청하지 않는다. 매번 clean rebuild를 기본으로 하지 않는다. [7][8]
  5. 진단 보존: 파일·행·열·오류/경고·어셈블리와 소스 상태를 기록한다. 리로드 전에 결과를 외부로 전달하거나 영속화한다.
  6. 리로드·임포트 조정: 컴파일 성공만으로 종료하지 않고 새 도메인 연결과 후속 임포트를 확인한다. 사용자 postprocessor가 추가 파일을 생성하면 다시 상태를 수렴시킨다.
  7. 최종 확인: 예상 소스 상태가 유지됐고 해당 코드가 반영됐음을 확인한 뒤 완료한다. 알려진 성공 상태와 같은 무변경 요청은 no-op으로 처리한다. 근거 없는 상태에서는 한 번의 명시적 재컴파일 또는 재시작으로 확인한다.

RequestScriptCompilation은 변경 여부를 검사해 필요한 스크립트를 재컴파일하고, 성공 후 어셈블리를 다시 로드한다. 따라서 “함수에서 반환됨”, “컴파일이 멈춤”, “새 타입을 사용할 수 있음”을 동일한 시점으로 취급하지 않는다. [8]

7.3 완료 판정과 오류 복구

현재 NTFS 증거: unity-refresh의 요청 접수와 같은 ID/fingerprint의 validation 완료를 구분한다. 초기 callback 보고서는 후속 reload에서 오래된 값으로 남을 수 있으므로 ready Editor에서 현재 로드된 함수를 직접 호출하고 domain generation·assembly MVID를 확인한다. probe 한 파일에서 확보한 이 증거를 일반 프로젝트 전체 검증으로 확대하지 않는다.

완료 응답에는 sourceRevision, compiledRevision, domainEpoch, 컴파일 진단, 실제 변경 반영 범위를 포함한다. 검증 중 파일이 다시 바뀌면 결과를 재사용하지 않는다. 컴파일이 필요 없었던 경우에도 왜 기존 성공 상태를 재사용할 수 있는지 기록한다.

컴파일 오류가 나면 Blocked:CompilationFailed로 전환하되 작업공간은 유지한다. 살아 있는 브리지가 있으면 진단을 제공하고, 없다면 Host가 Editor.log와 종료 상태를 수집해 AI가 파일을 수정하게 한다. 이후 재시작 또는 재동기화로 회복한다. 로그 파서는 Unity 버전별로 시험하고, 파싱 실패 시 원문과 불확실 상태를 반환한다.

깨진 프로젝트의 최초 실행은 별도 시험 항목이다. Safe Mode에서는 브리지도 실행되지 않을 수 있고, batch 모드에서는 컴파일 오류 시 종료한다. 이 경우 내부 복구 명령을 기다리지 않고 외부 수정·재시작 경로를 사용한다. -ignoreCompilerErrors를 정상 작업 경로의 해결책으로 사용하지 않는다. [12]

8. 에셋 생성·수정·임포트

8.1 두 종류의 작성 경로

원시 파일은 파일시스템으로 작성하고, Unity 직렬화 객체는 Unity API로 작성한다. PNG나 텍스트 파일을 AssetDatabase.CreateAsset으로 만드는 식으로 기능을 혼동하지 않는다. 이 API는 Unity 네이티브 에셋용이며 프리팹에는 별도 API를 사용해야 한다. [16]

프리팹의 분리 편집과 저장·해제 절차, 에디터 씬 관리, 임포터 재임포트 API는 공식 기능을 사용한다. 내부 에디터 클래스에 대한 reflection이나 YAML 수작업 생성을 기본 경로로 삼지 않는다. [17][18][19]

CreateAsset은 기존 경로의 에셋을 덮어쓸 수 있으므로, 도구 계약은 기본적으로 fail-if-exists로 둔다. 덮어쓰기 요청에는 기존 GUID나 내용 해시 같은 전제조건을 받는다. 재시도 가능한 생성 작업은 목적지와 내용에 기반한 사후조건을 가져야 한다. [16]

8.2 “새 코드를 쓰고 그 타입의 에셋 만들기”를 일급 흐름으로

AI가 DoorConfig : ScriptableObject를 새로 작성했다면 먼저 7절의 동기화를 완료한다. 새 도메인에서 타입과 어셈블리를 찾고, 컴파일한 소스 상태가 현재 요청과 일치할 때만 객체를 생성한다. 도메인 리로드 전의 Type, Object, InstanceID를 다음 명령에 그대로 재사용하지 않는다.

장시간 참조는 에셋 경로·GUID·로컬 식별 정보처럼 재해석 가능한 형태로 저장한다. 런타임 객체 식별자는 현재 플레이 세션에만 유효한 것으로 취급한다. 타입을 찾지 못하면 에셋 생성을 강행하지 말고 컴파일·어셈블리 참조·define 조건을 진단한다.

8.3 임포트 완료를 확인하는 방법

refresh 과정은 postprocessor나 생성 파일 때문에 다시 시작될 수 있다. 단 한 번의 OnPostprocessAllAssets 호출이나 isUpdating의 한 번의 false 값만으로 전체 완료를 선언하지 않는다. [13][14]

작업 대상별 예상 경로, GUID, 타입, 필요한 임포터 설정을 기록하고 다음을 함께 확인한다. 관련 파일 반영 완료, 알려진 후속 변경 없음, 컴파일·리로드 작업 정리, 대상 에셋의 실제 로드와 요청 사후조건 통과. 긴 임포트에는 진행 상황과 원인별 timeout을 제공한다. 특정 프로젝트의 비동기 생성 작업은 별도 ready 훅으로 완료를 알려야 한다.

StartAssetEditing/StopAssetEditing은 짧은 배치에만 사용하고 finally 또는 검증된 scope로 항상 균형을 맞춘다. 임포트가 멈춘 구간에서 새 에셋이 이미 완전히 로드될 것이라고 가정하지 않는다. 예외로 멈춘 상태를 다음 에이전트가 수동으로 풀게 하는 설계는 금지한다. [15]

8.4 에셋과 메타데이터, 저장 책임

기존 에셋을 작업공간에 복제할 때는 GUID를 그대로 보존한다. 새로운 에셋의 GUID는 Unity가 생성하게 한다. 이동·삭제·결과 회수에서는 파일과 .meta를 함께 다룬다. Unity는 폴더의 메타데이터도 생성하므로 디렉터리 이동 시험도 포함한다. [37]

“메모리에서 변경됨”과 “디스크에 저장됨”을 구별한다. 씬·프리팹·일반 에셋에 맞는 저장 API를 명시적으로 호출하고, 완료 후 재개방 검증을 한다. 플레이 중 만들어진 객체나 변경된 씬 상태를 일반 소스 변경으로 자동 저장하지 않는다. 저장되지 않은 사용자 변경이 있으면 명시 정책 없이 폐기하거나 전체 저장하지 않는다.

9. 실제 Play Mode 진입과 게임 동작 확인

9.1 테스트 실행과 라이브 플레이를 구별한다

tests.run(mode=PlayMode)는 테스트 프레임워크의 실행이고, play.enter(scene=...)는 지정한 게임 씬을 실제 Editor Play로 실행하는 기능이다. 전자를 구현했다고 후자를 완료한 것으로 간주하지 않는다. 프로젝트 부트스트랩, 여러 씬의 구성, 입력과 UI, 저장 데이터 등을 실제 게임 실행 경로에서 확인할 수 있어야 한다.

9.2 Play 진입 절차

  1. 해당 작업공간의 에디터 예약과 최신 동기화 성공을 확인한다. 실행 중 테스트가 있으면 종료될 때까지 기다린다.
  2. 현재 씬 구성과 dirty 상태를 기록한다. 무명 씬·프리팹 편집 모드·미저장 변경은 지정된 정책에 따라 저장하거나 진입을 중단한다.
  3. 요청한 시작 씬 또는 씬 구성을 연다. playModeStartScene이 설정돼 있으면 요청한 씬과 충돌하는지 검사하고, 원래 값을 기록한 뒤 작업별로 조정한다. [18]
  4. 명령 상태를 저장하고 EditorApplication.EnterPlaymode를 호출한다. playModeStateChanged에서 실제 진입을 확인한다. 재연결이 필요하면 같은 operation을 이어간다. [6]
  5. 에디터 진입과 게임 준비를 구분한다. EnteredPlayMode와 실제 프레임 진행을 확인하고, 게임별 부트스트랩 완료·씬 로딩 완료 조건을 추가로 기다린다.
  6. 준비된 플레이 세션 ID를 반환한다. 부트스트랩 오류나 프레임 정지가 있으면 “Play 버튼이 눌렸다”는 이유로 성공 처리하지 않는다.

게임별 준비 조건은 프로젝트가 제공하는 명명된 훅, 특정 씬 로딩, 정해진 상태 질의 등으로 표현한다. 단순한 기본 템플릿에서는 몇 프레임 진행을 검증할 수 있지만, 이를 네트워크 로그인·Addressables 로딩 등 모든 게임 준비의 보편적 완료 조건으로 취급하지 않는다.

9.3 플레이 중 제공할 기능

기능 초기 구현 정책
상태 관찰 플레이·일시정지 상태, 프레임 카운터, 로드된 씬, 제한된 객체 질의, 로그와 예외를 제공한다.
정지·재개·한 프레임 진행 isPaused, Step 등 공개 API를 사용하고 실제 프레임 변화로 완료를 확인한다.
프로젝트 동작 호출 프로젝트가 등록한 이름 있는 런타임 훅을 호출한다. 단순한 게임 함수를 호출한 시험과 실제 입력 경로 시험은 구별한다.
입력 Input System 프로젝트는 테스트 전용 장치와 입력 이벤트를 쓰는 확장부터 시작한다. 물리 키보드·마우스의 전역 주입은 기본 경로가 아니다.
화면 확인 그래픽 사용 세션에서 게임 프레임을 캡처한다. 파일 생성뿐 아니라 디코딩·크기·현재 플레이 세션 귀속을 검사한다.
종료 ExitPlaymode 요청 후 실제 Edit 상태와 필요한 리로드 완료를 기다린다. 등록한 런타임 장치·객체·세션 상태를 정리한다.

Input System은 코드로 입력을 구동하는 자동화 시험과 격리된 InputTestFixture를 제공한다. 다만 이 fixture는 입력 시스템 상태를 초기화하므로 실행 중인 일반 게임에 그대로 삽입하는 범용 입력 프록시로 취급하지 않는다. 라이브 입력 모듈과 테스트 fixture를 분리하고, 해당 프로젝트의 입력 업데이트·포커스 설정에 맞춰 검증한다. Legacy Input은 자동 지원한다고 주장하지 않는다. [31]

스크린샷은 ScreenCapture 등 공개 API를 우선한다. 카메라 전용 렌더 결과와 UI까지 포함한 최종 게임 화면은 다른 산출물로 표기한다. WaitForEndOfFrame은 batch Editor에서 동작하지 않고 Game/Scene 뷰 전환의 영향을 받을 수 있으므로 모든 실행 모드에서 같은 대기법을 쓰지 않는다. 캡처 가능 상태와 timeout을 갖추고 GUI 경로에서 검증한다. [35][36]

9.4 설정 조합과 그래픽 실행 모드

Enter Play Mode의 domain reload·scene reload 설정은 프로젝트 값을 기본으로 존중한다. 첫 적합성 시험은 두 리로드가 켜진 설정으로 시작하되, domain reload 꺼짐에서도 재등록·상태 초기화가 정상인지 필수 시험한다. 이 설정을 꺼도 코드 변경에 따른 도메인 리로드가 사라지는 것은 아니다. [27]

GUI 세션을 실제 플레이·입력·화면 검증의 기준으로 한다. batch 모드는 순수 로직과 지원되는 테스트에 사용하고, -nographics는 GPU가 필요 없는 작업에만 허용한다. 해당 옵션은 그래픽 장치를 초기화하지 않으므로 렌더링 검증의 동등한 대체물이 아니다. 포커스 의존 테스트는 별도 자원 예약을 요구한다. [5]

10. 테스트 작성·발견·실행

10.1 두 종류의 테스트를 분리한다

도구 자체의 테스트는 CoW 격리, 명령 상태, 리로드 복구, 다른 에디터 침범 방지를 검증한다. 프로젝트의 테스트는 AI가 수정한 게임과 에디터 기능을 검증한다. 전자가 통과했다고 게임 수정이 올바른 것도 아니고, 게임 테스트가 통과했다고 작업공간 격리가 올바른 것도 아니다.

AI가 테스트를 작성할 때는 먼저 기존 테스트·어셈블리 구조를 조사하게 한다. EditMode는 순수 로직과 에디터/에셋 작업, PlayMode는 프레임 진행·컴포넌트 생명주기·물리·실행 중 상호작용을 검증하는 용도로 구분한다. UnityTest는 PlayMode에서 코루틴으로 실행되므로 프레임을 기다려 확인하는 시험을 작성할 수 있다. [24][25]

10.2 테스트 어셈블리를 올바르게 구성한다

프로젝트가 이미 쓰는 Unity Test Framework 버전을 유지하고 해당 버전에 맞는 테스트 어셈블리 템플릿을 사용한다. 테스트를 추가한 뒤에는 파일 존재만 확인하지 말고 컴파일 성공과 Test Runner의 실제 발견을 확인한다.

별도 asmdef 테스트는 테스트 대상 runtime/editor 어셈블리와 올바른 참조 관계를 가져야 한다. 프로젝트 코드가 Assembly-CSharp 같은 predefined assembly에만 있는 경우, 새 custom asmdef에서 그 어셈블리를 직접 참조할 수 없다. 도구가 이를 해결하려고 프로젝트 전체에 asmdef를 자동 삽입하지 않는다. 기존 시험 구조 재사용, 블랙박스 시험 또는 명시적으로 검토한 어셈블리 재구성이 필요하다. [26]

Editor 전용 테스트 코드와 Player에서 실행할 코드를 분리한다. 패키지의 테스트는 해당 패키지·manifest 설정을 확인한다. Input System 테스트에는 추가 테스트 의존성이 필요할 수 있으므로 일반 UTF 테스트와 선택적 입력 테스트 템플릿을 분리한다. [24][31]

AI에게 요구할 테스트 산출물은 다음과 같다. 요구사항과 assertion의 대응, 재현 가능한 setup/teardown, 제한된 대기 시간, 생성한 에셋·장치·씬의 정리, 성공뿐 아니라 실패 조건, 필터로 재실행 가능한 테스트 이름. 오류를 잡아서 무조건 통과시키거나, 실패 테스트를 삭제·skip 처리해 성공으로 만드는 변경은 결과 검토에서 드러나야 한다.

10.3 상주 Editor의 테스트 실행

Unity 브리지에 tests.list, tests.run, tests.cancel, tests.results를 둔다. TestRunnerApi와 ExecutionSettings/Filter를 버전에 맞게 감싼다. 에디터가 열려 있는 작업공간을 테스트하려고 두 번째 Editor를 실행하지 않는다. [20]

UTF의 콜백 등록은 도메인 리로드 이후 그대로 유지되지 않으므로 재등록이 필요하다. 결과는 SaveResultToFile 또는 해당 버전에서 지원되는 결과 직렬화 경로로 수집한다. 파일 경로 제약에 맞춰 프로젝트 안의 비임포트 임시 위치에 먼저 썼다면 Host가 제어 영역으로 회수한다. [21][22]

10.4 성공 판정

요청한 테스트가 발견되지 않았으면 기본적으로 NoTestsMatched 실패다. 테스트 파일 컴파일 실패, runner 초기화 실패, 결과 파일 누락, timeout, 중간 프로세스 종료를 “테스트 0개 성공”으로 표현하지 않는다.

결과에는 선택한 테스트 목록과 실제 실행 목록, passed/failed/skipped/inconclusive 수를 함께 저장한다. 필수 시험의 skip과 assertion 실패를 구분하고 검증 정책에 따라 차단한다. 명시적으로 빈 테스트 집합을 허용한 진단 명령만 예외다.

한 번의 성공 재시도가 최초 실패를 지우지 않게 한다. 재시도는 별도 attempt로 남기고 불안정성을 보고한다. 소스가 테스트 도중 변했으면 결과를 Stale로 표시한다. 성공 결과에는 사용한 소스·에셋 상태, Unity/UTF 버전, 타깃, Play 설정, 입력·그래픽 모드가 연결돼야 한다.

10.5 CLI/batch 대체 경로

프로젝트의 Editor를 닫은 상태에서 -runTests, -testPlatform, -testResults, -logFile을 이용하는 경로도 제공한다. EditMode와 Editor PlayMode를 먼저 지원하고 실제 Player 빌드 테스트는 별도 확장으로 남긴다. 공식 CLI는 Editor의 PlayMode 테스트와 특정 타깃으로 빌드한 Player 테스트를 구분한다. [23]

테스트 runner가 완료를 처리하도록 하고, 일반 실행용 -quit를 모든 명령에 관성적으로 붙이지 않는다. 버전별 종료 동작을 검증한다. 종료 코드만으로 판정하지 않고 결과 XML·완료 이벤트·실행 manifest를 함께 확인한다. 그래픽이 필요한 시험에 -nographics를 강제로 적용하지 않는다.

취소 API의 범위는 고정한 UTF 버전에서 확인한다. 테스트가 메인 스레드를 막으면 정상 취소도 실행되지 않을 수 있으므로 Host의 watchdog을 최종 경계로 둔다. 강제 종료한 결과는 보존하고 Interrupted로 보고한다. 이전 검증의 XML 파일을 이번 결과로 오인하지 않도록 run마다 새 디렉터리를 사용한다.

다음 행동은 명령 ID와 타입 있는 인자로 반환한다. 새 명령의 정확한 이름·입력/출력 schema·fake·적합성 시험은 해당 구현 단위에서 함께 고정한다. 플러그인이나 MCP도 같은 CLI/Core 계약을 사용한다.

11.2 현재 대화와 작업공간의 연결

첫 Codex 연결의 목표는 이미 진행 중인 대화에서 Splinter를 사용할 수 있게 하는 것이다. Core의 일반 task/workspace ID와 Codex의 대화 locator를 분리하고, 프로젝트·task key·workspace 루트·상태 저장소·기준 revision·owner 세대·검증·완료 의도를 영속 기록한다.

같은 대화의 후속 요청은 같은 작업을 사용한다. 재시작·문맥 압축 뒤 기록과 실제 상태를 대조하고, 다른 대화로 인수할 때는 기존 작성자의 상태·소유권을 확인한다. 현재 활성 창이나 전역 마지막 세션에 연결하지 않는다.

workspace ID나 shell의 cd만으로 에이전트의 모든 파일 도구·권한이 바뀌었다고 간주하지 않는다. 반환된 절대 경로와 실제 쓰기 권한·IPC 접근을 검증한다. 지원하지 않으면 필요한 행동을 반환하며 원본 편집·sandbox 해제·Codex worktree 중첩·강제 새 작업자 실행으로 우회하지 않는다.

선택적 자동 위임을 추가할 때만 별도 Runner/DAG가 같은 작업 계약으로 하위 작업자를 시작한다. 기존 인증·모델·권한을 재사용하되 자격증명을 작업공간에 복제하지 않는다. 이러한 확장의 예산·이벤트·재개 검증은 기본 대화 사용의 완료 기준과 분리한다.

11.3 작업 요청과 응답의 최소 구조

아래는 계획의 개념 필드다. 현재 schema와 동일한 실행 예제가 아니며 선택적 DAG 제출 없이 작업 하나를 식별할 수 있어야 한다.

  ownerGeneration / sourceSnapshotId / validationState
  providerSessionLocator?  # Codex 어댑터가 관리하는 선택적 정보

  requestedScope / operationId / observedOutcome

응답 접수, 검증 성공, 원본 반영, 자원 회수와 폐기 완료는 서로 다른 상태다. 현재 계약의 일반 status는 새 검증 응답 또는 명시적 소스 확인 때만 프로젝트 파일을 읽는다. 변경 명령은 현재 상태와 근거를 다시 확인한다.

11.4 기계가 해석 가능한 입출력

공통 옵션은 --project, --workspace, --request-key, --json/--jsonl, --non-interactive를 기준으로 설계한다. 작업 변경 명령은 명시한 작업공간 또는 검증된 세션 manifest를 반드시 요구한다. 현재 디렉터리 추론은 최초 프로젝트 발견에 사용하되 전역 “현재 작업공간” 선택을 공유하지 않는다.

--json은 stdout에 버전 있는 JSON 응답 하나만, --jsonl은 이벤트 한 줄당 JSON 하나만 출력한다. 진행 장식·색상 코드·로그는 기계용 stdout에 섞지 않는다. 사람용 출력은 별도 모드이며, 필요한 진단은 stderr 또는 로그 산출물로 제공한다.

--non-interactive는 입력 대기·브라우저 열기·대화상자를 금지하고 필요한 승인을 구조화된 NeedsUserAction으로 반환한다. --help와 schema는 입력·출력·사후조건·권한·부작용·재시도 규칙을 공개한다. 경로는 공백·한글을 지원하고 시간은 명시된 시간대 또는 UTC, 크기는 바이트처럼 단위를 고정한다.

종료 코드 제안의미
0조회 성공 또는 요청 접수 성공. 장기 작업의 완료 여부는 반드시 response.status로 구분한다. operation wait는 최종 성공일 때만 0.
2 / 3 / 4입력·스키마 오류 / 권한·정책·사용자 조치 필요 / 기준 버전·소유권·중복 키 충돌.
5 / 6실제 작업 실패 / 일시적인 연결·자원 문제. 6이어도 부작용 명령을 무조건 재실행하지 않고 operation을 조회한다.

세부 원인은 CompilationFailed, NoTestsMatched, DiskBudgetExceeded 등 안정된 코드로 구별한다. 설명문을 정규표현식으로 파싱해야만 복구 가능한 API를 만들지 않는다. CLI 호출 제한 시간과 실제 Unity 작업 제한 시간을 분리한다.

11.5 AI에 의한 모니터링과 관리

요약에는 작업별 branch/worktree·담당 AI·Editor 상태·최근 진전·대기 자원·오류·다음 안전한 행동을 포함한다. 컴파일 중인지, 입력을 기다리는지, 메모리가 부족한지, 테스트가 실패했는지 구별할 수 있어야 한다. 각 대화의 AI는 자기 작업의 로그를 반복해서 전부 읽지 않고 이벤트와 증거 ID를 따라 필요한 부분만 가져온다.

이벤트는 증가하는 ID와 cursor를 가지고 영속화한다. 재연결은 마지막 cursor 이후부터 재생하고 중복 이벤트는 ID로 제거한다. 이벤트 보존 기간을 넘겼으면 전체 상태 snapshot에서 재동기화한다. 장기 watch의 연결 종료나 Ctrl+C는 관찰만 끝내며 실제 작업 취소는 명시적인 cancel로 분리한다.

pause/resume, 안전한 Editor 재시작, operation 조회, 실패 로그 회수, 작업 보존, 정리 계획은 CLI로 가능해야 한다. 에이전트가 사라져도 Host는 승인된 실행·관찰·저널을 계속 관리하되, 새로운 의미 판단이 필요한 실패는 보존 상태로 둔다. lease 만료를 삭제 승인으로 사용하지 않는다.

11.6 스킬·플러그인과 사용 판단

스킬의 description은 명시적 Splinter 병렬 요청, 다른 작업의 싱글 인스턴스 점유로 독립 실행이 필요한 상황, 이미 연결된 작업의 재개/종료를 대상으로 한다. 일반 개발 요청이라는 이유만으로 생성 명령을 호출하지 않는다. 필요 없으면 기존 프로젝트에서 직접 작업한다. [48]

프로젝트용은 저장소 범위 스킬, 전역용은 사용자 범위 스킬이나 스킬을 묶은 플러그인으로 연결할 수 있다. 실제 버전의 설치·발견 범위를 확인하고 기존 사용자 지침·다른 플러그인을 보존한다. CLI를 호출하는 최소 연결부터 시작하며 MCP는 필수가 아니다. [50]

새 대화에서 명시 요청·점유 상황의 암묵 선택·불필요한 요청의 미사용을 모두 검증한다. 지침 파일 복사만으로 연결 성공을 기록하지 않는다. 실제 편집 경로·권한·작업 재개도 확인한다. 선택된 병렬 경로에 Codex의 별도 worktree 생성을 중첩하지 않고 Splinter API를 사용한다.

스킬은 각 대화가 자기 작업을 지속하고, 사용자의 완료 요청에 반영·정리하거나 명시적 폐기 요청에 반영 없이 제거하는 절차를 안내한다. 스킬 문장은 경로·소유권·삭제 안전성의 프로그램 검사를 대체하지 않는다.

11.7 Unity 저작 능력을 제한하지 않는 확장 경로

테스트 assertion과 프로젝트별 생성 로직은 AI가 작성한다. 도구는 테스트 어셈블리·컴파일·발견·실행을 검증한다. 특수 에셋·애니메이션·게임 데이터에는 명명된 Editor 작업 스크립트를 지원한다. AI가 검토 가능한 파일로 작성하고 동기화한 뒤 등록된 entrypoint를 메인 스레드에서 실행한다. 긴 작업은 단계별로 진행 상황을 저장한다.

임의 문자열을 평가하는 C# eval을 기본 기능으로 하지 않는다. 실행 코드 해시·진입점·전제 상태·사후조건을 기록하며, 부작용 판정이 없는 작업은 자동 재시도하지 않는다. 일반 브리지를 매 작업마다 수정해야만 새 에셋을 만들 수 있는 구조도 피한다.

작업자 AI: 코드 · 테스트 · Editor 작업 스크립트 작성
CLI/Host: edit commit → unity sync → 새 소스 상태 고정
Bridge: 등록된 저작 작업 실행 → 저장 → 임포트·사후조건 검사
CLI/Host: 실제 Play·테스트 → 결과 회수 → Git 변경과 증거 연결

11.8 선택적 MCP

CLI 기반 기능이 완성된 뒤 같은 Core 계약을 로컬 STDIO MCP로 제공할 수 있다. Codex는 로컬 STDIO와 Streamable HTTP MCP 연결을 지원한다. 작업공간 토큰과 동일 권한 검사를 적용하며 외부 네트워크 공개를 기본으로 하지 않는다. MCP에 workspaceId를 전달한 것만으로 에이전트의 일반 파일 편집 경로까지 바뀌었다고 간주하지 않는다. [34]

12. 병렬 실행 자원과 프로젝트 밖 상태

12.1 스케줄링의 최소 모델

작업공간 수, 활성 Editor 수, 컴파일/임포트 작업 수, GPU 작업 수, 실제 GUI 입력 사용권을 별도 자원으로 관리한다. 첫 설정은 Editor 두 개의 독립 실행을 검증하되, 고정 수치가 모든 PC의 안전한 한도라고 주장하지 않는다. 메모리·디스크 여유·임포트 비용을 관찰해 동시 실행 수를 제한한다.

한 Editor에서는 소스 변경·에셋 저작·테스트·Play 전환을 단일 변경 큐로 직렬화한다. 상태·로그 조회는 안전한 범위에서 계속 제공한다. 여러 에이전트가 같은 Editor의 활성 프로젝트를 번갈아 바꾸는 구조를 만들지 않는다.

첫 버전에서는 살아 있는 worktree를 다른 작업의 이름으로 돌려 쓰는 슬롯 풀을 기본으로 하지 않는다. worktree의 소유 기간 동안 Editor를 닫았다 다시 열어 자원만 회수할 수 있다. 반복 준비 비용은 불변 스냅샷 읽기와 범위별 변경 저장으로 줄이고, 작업별 소스·Library 변경 저장소는 결과 보존 후 worktree와 함께 회수한다. 장래 풀 구현도 이전 결과 보존과 Git 소유권 전환을 검증해야 하며 git clean -xfd를 무조건 실행하지 않는다.

12.2 중요한 한계: 폴더 복제로 저장 데이터까지 분리되지는 않는다

Windows의 Editor PlayMode PlayerPrefs는 회사·제품 이름에 기반한 레지스트리 경로를 사용한다. Application.persistentDataPath도 보통 회사·제품 이름을 사용하는 사용자 데이터 경로이며 읽기 전용 속성이다. EditorPrefs 역시 프로젝트 밖 사용자 레지스트리에 저장된다. 프로젝트 디렉터리만 바꾸거나 %TEMP%를 분리해도 이 상태들이 자동 격리되지는 않는다. [28][29][30]

외부 상태 기본 정책
자체 저장 파일·테스트 데이터 프로젝트별 저장 경로 주입 훅으로 작업공간별 위치를 사용한다. 원래 경로와의 차이를 검증 기록에 남긴다.
PlayerPrefs 프로젝트의 저장 추상화/테스트 훅을 우선한다. 회사·제품명 변경은 명시적 검증 프로필에서만 허용하고 원본 제품의 동등한 시험으로 취급하지 않는다.
EditorPrefs 전역 설정을 자동 변경하지 않는다. 도구 설정은 별도 파일로 보관한다. 전역 설정을 바꾸는 프로젝트 도구에는 별도 예약/제약을 둔다.
네트워크 포트·외부 서비스 작업별 포트·테스트 계정·데이터 네임스페이스를 할당하고 실제 바인딩/접속 결과를 확인한다.
임의 플러그인의 외부 쓰기 관찰·프로젝트 어댑터 훅·명시적 승인으로 다룬다. 식별되지 않은 외부 상태까지 격리됐다고 보고하지 않는다.
라이선스·인증 이미 정상 사용 가능한 설치를 이용한다. 토큰·활성화 파일을 프로젝트 복제·결과 내보내기·공개 테스트 fixture에 넣지 않는다.

격리 수단이 없는 프로젝트에서는 해당 외부 상태를 사용하는 Play/테스트 단계만 직렬화한다. 이 예약은 도구가 관리하는 프로세스끼리만 유효하므로, 사람이 연 원본 게임이나 다른 프로그램까지 멈춘 것으로 간주하지 않는다. 원본 플레이와의 충돌 가능성이 있으면 보호 정책을 명시하고 동시 실행을 허용하지 않는다.

GUI 포커스에 의존하지 않는 API·가상 입력을 먼저 사용한다. OS 키보드/마우스가 꼭 필요한 시험은 공용 데스크톱 입력 자원을 단독으로 예약한다. 프로세스마다 자유로운 물리 입력을 병렬 주입하는 기능은 첫 버전 범위가 아니다.

12.3 보장 수준을 명확히 표시한다

v0의 보장은 프로젝트 파일과 에디터 작업 상태의 운영상 격리다. 일반 사용자 권한의 프로젝트 코드가 원본 절대 경로를 직접 쓰는 것까지 CoW가 차단하지는 못한다. Host의 경로 검사와 원본 해시 검증은 각각 통제와 사후 감지이며, 둘을 OS 샌드박스로 표현하지 않는다.

더 강한 보안이 필요하면 별도 사용자·제한된 실행 환경을 제공하는 ExecutionIsolationProvider를 추가할 수 있도록 계약만 둔다. v0에서는 isolationLevel=project-operational과 격리하지 않은 외부 자원을 상태 응답에 노출한다.

13. 변경 회수·통합·실패 복구

13.1 명시적 반영·보존·폐기

여러 차례 대화 중의 checkpoint와 작업 종료를 구분한다. 사용자가 해당 병렬 작업의 원본 반영·정리를 요청하면 새 쓰기 정지 → 현재 소스 검증·독립 결과 보존 → 최신 원본의 통합 후보 검증 → 원본 반영 확인 → 해당 소유 자원 회수 순서로 완료한다. A만 끝내면 B의 Editor·작업공간·시작 기준은 유지한다.

결과는 작업 시작 snapshot에서 실제로 바뀐 소스·에셋·.meta·패키지/설정·테스트와 검증 증거다. 상속된 사용자 변경, 도구 overlay, Library·임시 파일·토큰을 구분한다. 원본에 파일을 단순 덮어쓰거나 상속 변경을 중복 merge하지 않는다.

통합은 저장소 단위로 순서를 제어하며, 최신 대상 HEAD·dirty/staged·미저장 Editor 상태와 branch 사용을 재검사한다. 필요하면 별도 Splinter 통합 작업공간에서 3-way 후보를 검증한다. 이미 반영된 A 결과 때문에 B의 과거 검증을 그대로 재사용하지 않는다. 충돌은 해당 대화의 AI가 해결하고 다시 검증한다. 조건 불일치·실패에는 결과를 보존한다. 원격 push는 별도 요청 범위다.

“결과만 보관하고 정리”는 독립 결과 참조와 증거를 남기고 작업 자원만 회수한다. “나중에 이어갈게”, 대화/응답 종료, Editor만 종료한 경우는 작업을 유지한다. 시간 만료·공간 압박은 삭제 승인으로 사용하지 않는다.

반영 없는 명시적 폐기: 사용자가 정확한 작업을 버리라고 요청하면 미커밋·컴파일 실패 작업도 폐기할 수 있어야 한다. discard는 현재 미구현이며 보존형 release와 별도 계약이다. 정확한 workspace·owner 세대·변경 상태·사용자 의도에 연결한 intent를 저장하고, 새 쓰기와 소유 프로세스를 정지한 뒤 해당 mount·Git 등록·delta·전용 캐시·요청 범위의 전용 결과 참조를 회수한다.

다른 작업이 의존하는 snapshot·기준본·Git 객체와 원본은 보존한다. 모르는 자원을 0으로 취급하지 않고, 중단 시 같은 폐기 intent의 남은 단계만 재개한다. 폐기 전 성공한 컴파일/통합을 요구하지 않는다. 이미 원본에 반영한 변경의 취소는 별도 요청이며 자동 revert하지 않는다. 최소 영수증은 남기되 폐기 payload를 숨은 사본으로 보관하지 않는다. 세부 계약을 따른다.

14.1 시험 환경

현재 집계: SO-01~06은 독립 NTFS fixture로 통과했다. 현재 NTFS workspace 코드 후보의 .NET 자동 검증은 97 통과·0 실패·ReFS 전용 1개 skip이다. NI-01~08의 자동/fixture 증거와 실제 dirty 원본 통합 차단·최종 회수를 확인했다. 이 숫자는 서로 다른 시험 집합이며 아래 공개 제품 48개 전체 통과를 뜻하지 않는다. ReFS 알파·NTFS fixture·공개 시나리오의 현재 상태는 검증 추적표에서 각각 관리한다.

필수 시나리오 48개. 기존 Unity 기능 검증에 설치·AI 발견성·CLI 운영·Git worktree 수명주기 시험을 추가한다. 기능이 코드에 존재하는 것과 사용자가 지시만으로 사용할 수 있는 것을 별도 기준으로 판정한다.

직접 만든 최소 Unity fixture와 실제 사용 프로젝트를 분리한다. fixture는 작은 runtime 어셈블리, Editor 도구, EditMode/PlayMode 테스트, 씬, 프리팹, ScriptableObject, 텍스처를 포함한다. 대형 저장소 시험은 별도 합성 파일 집합으로 수행하고 유료 에셋이나 개인 프로젝트 데이터를 공개 저장소에 넣지 않는다.

14.2 성능 평가

같은 소스·Unity 버전에서 최초 등록부터 회수까지 전체 추가 저장을 측정한다. 원본 크기·읽기량·쓰기 범위를 독립적으로 바꾸고 snapshot 보존, delta, 메타데이터, 캐시, Git/LFS 결과를 분해한다. 일반 전체 복사는 명시적 비교군일 뿐 fallback이 아니다.

PV-02는 실제 Codex 기본 worktree의 독립 Editor, Codex worktree와 Unity Agent Coordination의 단일 Editor 순차 검증, Splinter를 비교한다. 같은 커밋·실제 3D 모델/텍스처·Unity 설정으로 각 방식의 A/B 두 작업을 실행한다. 새 작업의 Library 준비와 기존 작업 재개, 에셋 유지·코드 수정과 지정 텍스처/모델 재임포트를 나눠 시간·물리 저장량·읽기·메모리·운영 개입을 비교한다. 합성 큰 파일은 보조 저장소 시험이며 실제 임포트를 대체하지 않는다. 캐시·setup/ignored 파일 복사·반복 조건, 결과 보존과 회수 후 남은 비용을 함께 기록하며 성능 우위는 측정으로 판단한다. 대표 프로필과 판정은 직접 비교 계획을 따른다.

지표 해석

전체 소스 해시 계산과 파일 트리 순회에도 비용이 있으므로 복제 시간에서 숨기지 않는다. 안정적인 snapshot 식별과 콘텐츠 검증 기록을 재사용하고, 도구가 추적한 변경은 증분 계산하되 최종 회수에서 실제 파일을 재검증한다. 외부에서 변경했거나 추적 신뢰성이 깨진 경우 보수적으로 다시 스캔한다. 저장 계약 확인은 최초 준비·전체 읽기·일부 쓰기의 물리 증가량, 원본/A/B의 시점 격리와 회수 증거를 함께 사용한다.

“항상 즉시 복제”, “추가 공간 0”, “재임포트 없음” 같은 성능 문구를 목표로 삼지 않는다. 실제 프로젝트에서 최초 전체 복제 없이 스냅샷과 변경 저장이 동작하는지 확인하고, 그렇지 않은 원인을 파일 수·경로 종속 캐시·대형 재생성 파일별로 분해한다.

첫 공개 릴리스 기준: 사용자 요청 범위로 설치·Codex 지침 연결을 마치고, 각 대화가 명시적 요청 또는 실제 독립 실행 필요에 따라 Splinter를 사용하며 불필요하면 직접 작업한다. 여러 차례 편집·검증·재개 후 명시적 완료 요청에 최신 원본 반영·해당 자원 회수, 명시적 폐기 요청에 반영 없이 해당 작업 제거까지 완주한다. 다른 대화·원본·공유 자원 보존, 실제 Unity 저작·Play·테스트와 오류/장애 보존도 검증한다.

자동 하위 작업자 Runner·DAG, 필요가 입증되지 않은 daemon/DB 전환, 다른 OS/엔진, 자체 커널 드라이버·범용 GUI 조작·의미적 무충돌 병합은 선택적 후속이다. 설치·사용 판단·대화 지속·원본 반영·명시적 폐기·CLI/Git·필수 Unity 기능은 기본 제품 범위다.

16. 여러 OS·개발환경으로 확장할 기반

Windows + Unity는 제품의 정체성이 아니라 첫 지원 조합이다. 저장소 백엔드, 프로세스 실행, 애플리케이션, VCS, AI 실행기를 따로 구현하면 다른 OS·프로그램·개발 도구를 조합할 수 있어야 한다. 첫 버전에서 Unreal이나 다른 OS를 실제 지원한다고 표시할 필요는 없지만, 포크가 코어를 복제·수정하지 않고 모듈을 추가할 경계와 시험은 제공한다.

프로토콜은 버전과 capability를 협상한다. 코어는 workspace.mount, operation.observe, result.collect 같은 공통 계약을 처리하고 Unity는 unity.source.sync, unity.play.live, unity.tests.playmode 등을 제공한다. 다른 앱은 자기 기능을 등록한다. 서로 다른 완료 조건을 같은 이름으로 위장하지 않는다.

프로필에는 project / user-machine / task-runtime 범위를 나눈다. 프로젝트 프로필에는 이식 가능한 상대 경로와 정책을, 로컬 설정에는 설치 경로·볼륨·허용 에이전트를, 작업 상태에는 일회 ID·포트·세션 토큰을 둔다. Windows 경로·드라이브 문자·named pipe·Unity 폴더 이름이 범용 계약에 필수가 되어서는 안 된다.

코어 적합성 시험은 Unity·Win32·실제 Git 없이 fake 모듈로 실행한다. 소스 모듈에는 Git이 아닌 가상 VCS도 연결해 필드·상태의 Git 종속성을 검사한다. 실제 OS별 보장은 각 백엔드 시험 결과로만 표시한다. 포크는 작은 모듈 manifest, 버전/기능 선언, 공통 시험부터 시작할 수 있게 템플릿을 제공한다.
