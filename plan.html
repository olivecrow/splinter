Windows / NTFS의 병렬 작업공간 · 외부 VCS 유무와 독립적인 제품 목표

AI가 효율적으로 병렬 작업공간을 만들고, 원할 때 폐기한다

Splinter는 Unity처럼 프로젝트·Editor 점유로 독립 작업이 제약되는 개발 환경을 위한 로컬 도구다. 각 대화의 AI가 필요할 때 자기 작업을 만들고 여러 차례 이어 간다. 작업 내용의 판단·편집·게임 기능 검증은 해당 AI와 기존 개발 도구가 담당한다.

제품 범위사용 흐름완료와 후속완료 기준검증 정책

현재 구현은 foundation, 축소한 후속 책임은 구현 계획, 실제 자격·제한은 검증 안내와 추적표에서 확인한다. 한정 M0는 scoped-complete-with-limitations로 마감했다. 시작점은 AI 시작 안내이며 설치 연결·대화 인계는 AI 사용 절차로 다룬다.

1. 제품 범위

필수제품의 책임
독립 작업공간원본 NTFS 위치와 파일시스템을 유지하며 최초 전체 복제·읽기 hydration·파일 전체 copy-up 없이 불변 snapshot과 작업별 변경 범위를 사용한다. 원본은 계속 편집 가능하다.
외부 VCS 공존Git·Unity VCS/Plastic SCM 등의 관리 정보·등록·잠금·공유 기준을 안전하게 다뤄 Splinter의 원본/peer 격리와 병렬 작업을 보호한다. VCS 사용으로 추가되는 복제·인덱스·cache·결과 저장·메모리 비용도 효율 요구에 포함한다.
AI용 진입점비대화형 CLI·JSON/schema, 안정된 key/id/home과 반환된 절대 경로로 자기 작업만 조작한다. 독립 실행이 불필요하면 직접 작업한다.
지속 작업새 CLI·대화 재개에도 기준과 변경분을 유지한다. 다른 작업이나 전역 마지막 작업을 추측해 연결하지 않는다.
필요한 Editor정확한 작업공간의 Editor 실행·관찰·정지를 제공한다. refresh·컴파일·Play·테스트·빌드·캡처는 외부 MCP/Unity CLI로 수행한다. 선택적 Library/cache view는 개발 경로의 저장소 수명 관리로 제한한다.
명시적 종료반영·결과 보존형 회수·반영 없는 폐기를 구분한다. 실패하거나 미커밋인 작업도 폐기할 수 있어야 하며 A 종료는 B에 영향을 주지 않는다.
효율과 안전전체 생성·준비·재개·반복 편집·종료 비용을 판단한다. 승인된 쓰기·원본/peer·공유 자원을 보호하고 unknown을 성공이나 0으로 바꾸지 않는다.

첫 지원 조건은 Windows x64의 등록된 로컬 NTFS/Git 프로젝트, 검증된 clean 입력과 일반 파일, 기존 제한 VSS 서비스, 정확한 Unity 6000.3.22f1 fixture다. 일반 프로젝트·다른 패치·ARM의 지원은 각각 실제 자격이 필요하다. 미지원 파일·ACL·LFS/filter/dirty 조건의 사전 거부를 유지한다.

외부 VCS가 있건 없건 Splinter는 병렬 작업을 제공하고, Git·Unity VCS/Plastic SCM 등을 사용할 때 저장 공간·메모리·병렬 작업에 문제가 생기지 않도록 처리해야 한다. 병렬 격리는 Splinter의 기본 기능이고 VCS별 처리는 이 기능을 안전하고 효율적으로 유지하기 위한 호환 책임이다. 현재 --source git|none|plastic을 선택한다. 일반 폴더의 한정 자격은 실행 검증, Plastic regular/static 환경의 작은 T: A/B·마지막 회수는 PC 검증을 따른다. 선행 C: 회수 보류와 partial/dynamic·원본 반영 미자격은 유지한다. 병렬 편집과 원본 통합을 분리하고 VCS가 없어도 독립 결과를 보존한다. 원본 반영은 시작 기준·결과·최신 원본의 내용 비교로 이후 원본 변경을 보호하며 자동 git init이나 단순 덮어쓰기로 대신하지 않는다.

후속 개발은 1. 물리 공간 절감 → 2. 메모리 절감 → 3. 안정적인 병렬 작업 순서로 판단한다. 새 Editor의 몇 분 이내 준비는 허용 비용이며 에이전트의 코딩 계획·분석과 병행할 수 있다. 준비 시간 단축은 낮은 우선순위로 두고, 수십 분 이상 지연하거나 실제 진행을 막을 때만 해당 병목을 다룬다. 상세 기준은 저장공간 우선 계획이 소유한다.

프로그램은 작업공간·소유 Editor의 수명·범위 저장·독립 결과·안전한 반영/회수/폐기를 담당한다. AI가 기존 파일/Git 도구·MCP·Unity CLI로 수행할 작업 방법과 판단은 사용 지침으로 제공한다.

2. 사용 흐름과 수명

필요할 때 생성/재개 → 독립 편집·필요한 Editor 사용 → 보존 / 명시적 반영 후 회수 / 명시적 폐기

반환된 workspace 경로에서 AI의 파일 도구·CLI·Editor가 같은 작업을 사용한다. 작업이 이미 연결돼 있으면 원본이 비어도 같은 작업을 이어 간다. 별도 조정 AI·Codex worktree 중첩·작업 그래프 제출은 필요하지 않다.

대화·Editor 종료, timeout·임대 만료·디스크 압박은 통합·폐기의 승인이 아니다. release는 독립 결과를 보존한다. discard는 성공 검증·checkpoint 없이도 명시적 intent와 정확한 소유권을 대조해 해당 작업만 제거한다. 공유 view/cache/snapshot 의존성이 있으면 차단과 다음 행동을 반환하고 자동 연쇄 삭제하지 않는다. 회수 대기는 완료와 구별한다.

3. 첫 버전 완료와 후속 범위

아래 다섯 단위는 등록된 작은 Windows x64 NTFS/Git/Unity 환경에서 마감했다. 핵심 수명주기의 구현과 한정 실사용 완료를, 다른 프로젝트에서의 효율·일반 설치·지원 확대와 구분한다.

  1. 명시적 discard. 실패·미커밋 작업의 폐기, 같은 intent 재개·중복 요청과 peer 보호를 확인했다. 현재 모든 native 강제 중단의 자격은 별도다.
  2. 최소 AI 연결. 기존 개발 CLI·소스 스킬로 stable key·반환 경로·같은 작업 재개를 사용한다. 설치 연결·인계는 AI 절차이고 전용 installer·자동 binding은 구현 제외다.
  3. 대표 A/B 흐름. 실제 독립 Editor의 여러 차례 수정·오류/재개, A 보존/반영/회수 중 B 지속과 실패 B 폐기를 확인했다.
  4. 유한한 비용 판단. 작은 warm 입력의 생성·준비·재개·종료 시간과 추가 파일 할당으로 지속 독립 작업에 한정 채택했다. 메모리 부담이 남고, 대형 효율·총 물리 공간 절감은 미확인이다. 관측한 몇 분 이내 Editor 준비 자체는 허용 비용이다.
  5. 한정 버전 납품. 시작 안내·지원 전제·현재 복구 근거·제한을 제공한다. 광범위한 공개 지원 완료와 구분한다.

남길 후속은 구현 계획의 종료 기준으로 선택한다.

  • 한정 마감: VCS 없는 기본 수명주기. 공통 계약·일반 폴더 생성/재개·소유 Editor·내용 검사·독립 결과·release/discard와 기존 Git 사용 환경의 보호 경계를 연결했다. 원본/peer·범위 저장·회수 guard를 유지한다. 실제 작은 A/B 한 묶음과 후보별 제한은 검증 기록, 상세 범위는 확정한 개발 단위를 따른다.
  • 한정 마감: VCS 없는 안전한 원본 반영. 정확한 독립 결과와 현재 원본을 시작 기준과 비교하고 변경 경로만 조건부 반영한다. 충돌·동일 intent/부분 수행 복구·원본/peer 보호와 추가 공간/메모리 비용을 확인한다. 명시적 계획/intent와 조건부 파일 게시를 제공한다. 첫 실제 제품 자격은 승인한 서비스 Update·등록 뒤 Editor 없는 작은 NTFS A/B 한 묶음으로 확인했다. A 반영/회수 중 B 지속·B 충돌/독립 결과/회수와 비용을 한정 마감하며 native 강제 중단·Unity/Plastic·대형/OS 지원으로 확대하지 않는다. 구현·일반 권한 파일 시험은 현재 계약과 검증 기록을 따른다. 포함/제외·종료 기준은 확정 범위를 따른다.
  • 한정 마감: Plastic 호환 처리. regular/static 원본의 관리 정보·등록을 격리하고 등록하지 않는 Splinter 파일 작업공간을 제공한다. 작은 T: A/B·독립 결과·peer 지속·release/discard·마지막 소유 snapshot 회수는 PC 검증을 따른다. 기존 C: 보류와 partial/dynamic·원본 반영 미자격은 유지한다.
  • 한정 마감: Unity CLI 인계. 작은 T: Plastic 입력의 정확한 반환 경로/PID·loaded 편집·A 정상 종료 뒤 B 지속·두 독립 결과/회수는 UH 검증을 따른다. 목록 누락·초기 읽기 eval 타임아웃을 유지하며 MCP·다른 입력/버전·Play/Test/build로 확대하지 않는다.
  • 데이터 보존과 게임 검증의 분리. 자체 refresh·컴파일/포커스 처리·내부 성공 gate·중복 preserve-worker를 제거했다. 외부 검증 뒤 같은 checkpoint를 사용하며 seal·독립 결과·target guard를 유지한다. 개발용 view는 저장소 수명만 관리한다.
  • 저장·메모리. 실제 사용할 입력의 관측 병목 하나를 개선하고 정확성과 전후 비용으로 마감한다. 압축 저널 연결은 SJR2/overlay v2/candidate v3·자동 회귀·작은 T: A/B·동일 journal raw 대조의 NTFS 할당으로 한정 마감했다. JP의 직접 근거를 전체 workspace 공간/RAM·대형/OS 지원으로 확대하지 않는다.
  • AI 사용 절차. 발견·같은 작업 재개·외부 도구 선택·보존/반영/폐기를 스킬과 예시로 제공한다.

현재 worker 브리지는 실행 관측·정상 종료·Coplay peer 보호만 담당한다. checkpoint/integrate는 컴파일 증거를 요구하지 않으며 데이터 보존·통합 guard를 유지한다. 외부 MCP/Unity CLI 인계의 실제 자격은 도구별 확인이 필요하다. 상세 제약은 사용 계획을 따른다. 파일/Git/복구 지원 검증은 사용할 환경의 필요한 경계나 재현 안전 결함만 선택한다.

4. 첫 버전 완료 기준

실제 AI 두 작업이 같은 프로젝트에서 독립 작업공간을 만들고 여러 차례 편집·필요한 Unity 검증을 수행한다. 한 작업을 보존하거나 폐기해도 다른 작업과 원본은 유지된다. 같은 작업을 재개할 수 있고 공간·시간 비용으로 해당 조건의 사용 가능성을 판단한다.

M0-01~08의 입력·절차·증거는 첫 버전 계획, 실행 상태는 M0 추적표가 소유한다. 기존 NI/LV/WF/LB/NR의 하위 성공을 새 사용 흐름의 전체 통과로 자동 승계하지 않는다.

이전 48개 시나리오는 장기 지원/확장 카탈로그로 보존한다. Unity 저작·Play·테스트는 기존 Unity 도구가 담당한다. 재부팅·전원·물리 공간 장애·ARM·파일 지원 확대는 미실행 상태를 유지한다. 모든 카탈로그 항목을 통과해야 첫 실사용 버전이 완료되는 방식은 사용하지 않는다.

5. 검증 정책과 중지 조건

  • pwsh ./scripts/build.ps1의 locked restore·Release·기존 자동 시험과 변경한 schema/fake 적합성을 유지한다. 승인 쓰기·원본/peer 보호·잘못된 삭제 방지는 필수다.
  • 실제 시험은 변경된 부작용 경계나 재현 결함에 맞춰 선택한다. 첫 후보의 대표 A/B 흐름 한 묶음을 수행하며 무관한 문서/발견 변경마다 과거 Unity/VSS 전체를 재검증하지 않는다.
  • 새 장애 harness·전체 조합·반복 확대에는 답할 질문과 종료 조건을 먼저 정한다. 선택한 후속 단위를 마감하며 M0나 대형 C/S/Q 비교를 자동 재개하지 않는다. 기존 NotRun·Partial·실패/unknown은 보존한다.
  • 지원 경로의 데이터 손실·원본 오염·타 작업 종료/삭제가 재현되면 해당 경로를 차단하고 수정한다. OS 장애 미자격은 제한으로 공개하고 불확실한 상태는 보존한다.
  • 작업별 delta·Library·Git 결과·임시 파일과 공유 VSS를 구분한다. 관측하지 못한 순간 물리 peak·VSS 귀속을 0이나 임의 절감률로 표시하지 않는다.

기능 계약: NTFS · validation · source · VSS 권한. 후속 지원: NR · SF · SW.
