Splinter product requirements

Splinter gives a development task its own project path and, when needed, its own Unity Editor. A task can continue across conversations using the same identity. Agents use their existing tools to edit and validate work.

1. Product scope

RequirementProduct responsibility
Independent workspacesKeep the original at its NTFS path and editable. Share immutable basis data and store private changed ranges. Avoid an initial full copy, read hydration, and whole-file copy-up.
Source control coexistenceSupport Git, Unity Version Control / Plastic SCM, and folders without version control. Keep each provider's management state separate and protect original and peer data.
Agent interfaceExpose a noninteractive CLI with discoverable schemas and structured JSON responses. Bind operations to the explicit task identity, home, basis, and returned path.
Continuing workRetain the task path, basis, changes, and any attached Library across resumption and intermediate results. Recover interrupted operations with the same request.
Unity executionLaunch, observe, and normally stop the exact owned Editor. Agents use existing tools for target selection, refresh, compilation, Play, tests, builds, capture, and acceptance.
Explicit completionPreserve independent results, check the current target against the basis and applied history before publication, and reclaim only resources owned by the task. Support explicit discard even if work failed or remains uncommitted.
Efficiency and safetyAccount for full lifecycle cost, including VCS, Library, private changes, results, and temporary state. Protect acknowledged writes, original and peer data, and shared dependencies.

The product scope is the CLI, storage and owned-resource lifecycle. Agents handle setup, conversation handoff, tool selection, and conflict resolution. Dedicated installers, automatic conversation binding, scheduling, shared-original-Editor orchestration, general Unity authoring APIs, and a daemon or execution platform are outside scope. 2. Usage flow and lifetime

Create or resume → Edit and validate independently → Preserve, apply, or discard explicitly

Use a workspace when work needs independent execution. Continue an existing task at its returned path. A checkpoint preserves a fixed source result while work continues. Original application requires a reviewed result and guarded publication. Releasing the workspace preserves its result. Explicit discard applies only to the named task, and shared resources remain protected while dependents exist.

Ending a conversation or Editor, a timeout, lease expiry, or disk pressure does not authorize application or deletion. Completion requires proof of reclamation or a report that it remains pending. Workflow and handoff · Original application · Discard

3. Remaining work

Prioritize physical storage cost, then memory cost, then parallel workflow stability. Assess preparation, editing, validation, and completion together. Address demonstrated bottlenecks first using bounded reproductions.

Native scale and fault qualification remain open for SCAL-01–08. Large lifecycle costs, peak resource usage, and OS-failure behavior require separate evidence. Retained large fixtures require an explicitly scoped follow-up. SCAL plan · Validation scope

4. Acceptance criteria

Two tasks can independently edit and validate work on the same Unity project. Each task resumes with the same identity and changes. Preserving or discarding one task leaves the original and peer intact. Guarded application preserves conflicting changes for explicit resolution. Report the time and resource costs for the measured conditions.

5. Verification policy

  • Run locked restore, Release compilation, and the default automated suite through pwsh ./scripts/build.ps1. Keep schemas, fakes, and conformance tests aligned with contract changes.
  • Use native checks for changed side-effect boundaries and reproduced defects. Keep platform, input, failure, and performance qualification tied to the cases that actually ran.
  • Estimate each phase before execution, stop safely at twice its estimate, and preserve incomplete or unknown state. Block affected operations when evidence shows acknowledged-write loss or damage to the original or peers.
  • Measure per-task changes, shared bases and Library, results, temporary files, and resource peaks as separate costs. Report unknown quantities explicitly.
