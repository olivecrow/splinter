# 현재 Unity 병렬 작업 비교

[English](../../verification/unity-current-comparison.md)

RC-01 · 2026-10-14 · 제품 `7630970`. Codex 앱의 A/B 대화 경로에 새로 만든 일반 Git 워크트리와 원본 Library를 참조하는 새 Splinter A/B를 같은 고정 소스·한 줄 수정으로 비교한다. Codex는 새 Library를 임포트하고 Splinter는 기존 원본 Library를 참조한다. 완료한 Splinter 실행과 후속 Codex 재측정을 비교하며, 이전 진단 시도는 보존하되 제외한다. 이전 UT의 875.2초에 이번 Codex 측정을 단순 연결하지 않고 양쪽을 다시 측정했다.

AMD Ryzen 5 5600X (6 cores / 12 threads), 68,628,553,728 bytes physical memory; Windows 11 Home 10.0.26200; NTFS; Unity 6000.3.22f1.

소스 `b09fa58e9d40a560d4fe1af7a213f8ac23e8e3b1`: 추적 파일 1,602개 / 2,804,772,822 bytes. 변경하지 않은 원본 Library는 파일 42,420개 / 3,141,660,252 bytes다. 양쪽 모두 커밋의 원시 소스 바이트를 사용하며 Codex 워크트리는 명령에 한정한 `core.autocrlf=input`으로 checkout 변환을 방지했다. 원본 checkout과 전역 설정은 유지했다.

## 시간과 실행 순서

양쪽 모두 독립 A/B Editor를 병렬 실행한다. 작업공간 생성 구간도 겹치며 보존·회수는 기록된 명령 순서를 따른다. Editor 네 개가 자원을 경쟁하지 않도록 방식별 실행은 분리했다. 각 작업은 격리된 C# 한 줄 수정·명시적 refresh·컴파일 준비·선택 에셋 확인을 수행한 뒤 정상 종료한다. AI 추론·기능 개발 시간이 아닌 자동화한 작업공간·Unity 연산의 측정이다.

| --- | ---: | ---: |
| Library 기준본 준비 | 해당 없음 | 1분 0.2초 |
| A + B 작업공간 생성 | 13.4초 | 2분 48.8초 |

| 두 Editor 정상 종료 | 3.6초 | 1분 56.8초 |
| 결과 보존 + 작업공간 파일 회수 | 23.3초 | 3분 19.5초 |
| A/B 소스 결과 합치기 | 0.7초 | 0.7초 |

| **전체 과정** | 13분 39.7초 | 15분 35.2초 |

Splinter는 전체에서 115.5초(14.1%) 더 걸렸으며 초기 Editor 준비 구간은 451.2초 짧았다. Codex 전체 시간은 병렬 생성과 중단 없는 Editor 시작부터 정리까지를 더하고 저장 공간 조사를 뺀 값이다. 생성과 실행 사이의 읽기 전용 원시 입력 확인은 제외했다. Splinter는 Library 준비부터 복원까지에서 저장 공간 조사 시간을 뺐다. A/B 중첩은 한 번만 계산하고 짧은 명령 전달 간격은 포함한다. 대화 생성·Codex 앱 아카이브는 측정하지 않았다. 방식별 완료한 비교 실행은 한 번이며 OS 캐시 초기화·순서 무작위화는 하지 않았다. 이전 875.2초와의 차이를 특정 변경의 인과 효과로 해석하지 않는다.

이 시점의 Splinter 추가 파일 할당은 **98.64% 적다**. 읽기 전용 Windows `FILE_STANDARD_INFO` 조사로 작업·제어 파일, 작업별 소스·Library 데이터, 소유 Git 등록, 공유 runner/Library 메타데이터를 한 번씩 합산했다. 모든 측정 root는 읽기 오류·unknown 없이 완료했다. 이동한 원본 Library 본문·원본 소스·공유 Git 객체·디렉터리/MFT 메타데이터는 제외한다. 컴파일 준비 후 유휴 시점의 파일 할당이며 볼륨 최대 사용량은 아니다. 조사 시간은 Codex 33.0525초·Splinter 9.5116초로 양쪽 모두 작업 시간에서 제외했다.

## 결과·회수와 검증 한계

각 개별 결과는 계속 참조 가능하다. 충돌 없는 Git `merge-tree` / `commit-tree`로 각 A/B를 별도 결과 ref에 합쳤으며 양쪽 모두 tree `756e0a926577c9bcff036c823b4816b3b2d5fb19`다. 원본은 덮어쓰지 않았다. 개별 컴파일·에셋 확인, 정확한 소유 Editor 종료, Splinter provider/자원 회수, 원본 Library의 일반 NTFS 디렉터리 복원을 확인했다. 실제 Splinter 응답 12개 모두 현재 응답 schema 검증을 통과했다. 병합 결과 컴파일·Play Mode·Unity 테스트·게임 빌드·충돌 해결은 **NotRun**이다.

일반 워크트리도 병렬 개발이 가능하다. 개별 작업 속도가 같고 독립적인 작업이라면 `min(A, B)`가 순차 실행 대비 추가 준비·병합·정리·자원 경쟁 비용보다 클 때 병렬화가 시간을 줄인다. 이는 모델이며 실측한 손익분기가 아니다. 긴 작업은 준비 비용을 분산할 수 있지만, 동일한 병렬성에서 Splinter가 결국 더 빨라진다고 단정할 수는 없다. 반복 읽기·쓰기와 정리 비용은 작업량과 함께 증가할 수 있다.

## 비교에서 제외한 진단 시도와 남은 빈 디렉터리

Codex 결과 보존의 raw EOL 상태 검사 오탐 뒤 첫 A 결과를 별도 ref에 보존하고, 내용 변경 없이 인덱스를 정정해 해당 단계만 재측정했다. 이후 같은 소유 Codex 경로를 raw Git 입력으로 다시 준비해 전체 과정을 중단 없이 측정했다. 첫 실행·진단·복구 대기는 주 비교에서 제외한다. 두 Codex root는 비어 있지만 다른 프로세스가 경로를 열고 있어 삭제되지 않았고(점유 프로세스 미확인) Git은 파일/등록 삭제 뒤 exit255를 반환했다. 이 빈 디렉터리 한계를 보존한다. 개별 명령·관측 비용, 실제 파일 할당과 root별 unknown 여부, 결과 tree·소유 회수·원본 hash·schema 검증은 JSON 데이터가 소유한다. Codex 소유 대화의 list_artifacts가 빈 목록을 반환해 앱 archive는 실행하지 못했다. 정확한 자기 작업공간·소유 Editor 부재·전체 원시 파일/커밋 일치·독립 ref를 확인한 뒤 일반 git worktree remove로 회수했다. 기존 원본·이전 작업공간·이전 refs를 보존했다. 관리자 권한·VSS·서비스·패키지·전역 설정을 변경하지 않았다. 기존 fixture와 설치된 의존성을 유지했으며 외부 도구의 새 자격을 주장하지 않는다.
