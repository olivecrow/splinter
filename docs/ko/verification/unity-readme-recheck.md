## 진단과 남은 큰 비용

1. 첫 제어 스크립트가 과거 `bd23-a/b` 키를 재사용했다. 기존 결과 브랜치 때문에 작업 mount/Editor 생성 전 등록이 실패했지만 Library 참조 두 개는 붙어 있었다. 정상 restore가 거부했고 이 준비 중 단계는 현재 discard/release로 회수할 수 없다. 사용자의 명시적 승인 후 정확한 task/basis 잠금과 부재·identity·ref 증명을 거쳐 이번 참조 영수증 두 개만 백업·별도 보존했다. 정상 Library 복원과 전체 바이트/mtime/속성 검사가 통과했다. `.local/rr26-old`의 실패 기록과 새 basis pin 두 개는 남기고 과거 브랜치·결과는 보존했다. 최종 검사 포함 복구 63.6초이며 제품의 자동 복구 지원 자격이 아니다.
2. 다음 구버전 실행은 작업을 완료했지만 원본 Library 일치 검사에서 5바이트 `MCPForUnity/RunState/mcp_http_8080.pid`만 사라져 실패했다. 제어자는 이 파일을 변경하지 않았고 실제 작성자는 계측하지 않았다. 변경된 Library 복원은 **360.0초**, 해당 진단 연산 구간은 **878.5초**였다. 읽기 전용 진단 검사도 겹쳐 깨끗한 기준 실행으로 쓰지 않는다. 소유 Editor/mount/작업공간은 회수됐고 소스·설정·기존 refs는 보존됐다. 자연스럽게 남은 Library를 새로 고정했으며 서버·패키지·run-state 파일을 수동 변경하지 않았다. 최종 세 방식은 그 전체 입력과 일치한다.
3. 현재 최초 Editor 준비 **164.6초**가 가장 큰 단일 단계이며 컴파일·자산 검사 **48.8초**도 공유 **26.0초**보다 크다. Editor 초기화/import/flush의 내부 원인을 분리하기 전 새 알고리즘 효과를 단정하지 않는다.
4. 현재 checkpoint/release도 **90.2초**다. 50.5초까지 정상 종료를 관측하고 나머지 보존·회수는 같은 구간 안에 있다. 세부 내부 비용은 분리하지 않았다. 구버전의 164.2초 종료는 편차·타임아웃 복구도 중요함을 보인다.
5. 현재 `ManagedDirectoryRestore.ExecuteAsync`도 원본 Library가 바뀌면 일반 파일 복원 경로를 선택한다. 작은 삭제 하나로 `ManagedUnchangedDirectoryRestore`를 쓰지 못할 수 있다. 일반 경로는 전체 파일 계획·이동/범위 복원·영속 진행 기록·최종 확인을 수행한다. 대부분 그대로인 root를 옮긴 뒤 변경 항목만 복원하는 방법은 향후 후보지만 복구·identity 증명이 필요하며 이번에는 구현하거나 현재 코드로 그 변경 경로를 계측하지 않았다. seal·내구성·진행 보호를 생략할 근거가 아니다.
