# 병렬 코드 작성과 공유 Unity Editor

[English](../../verification/unity-shared-editor.md)

SE-01 · 2026-10-14. 독립 Codex 하위 에이전트 두 세션이 Editor 없는 Git 워크트리에서 코드를 준비하고, 기존 프로젝트의 Editor 하나가 결과를 순차 검증한다. 일반 워크트리와 Splinter **양쪽 모두** 독립 Editor 두 개를 사용한 [RC-01](unity-current-comparison.md)과 구분한다.

## 입력과 방법

소스는 `b09fa58e9d40a560d4fe1af7a213f8ac23e8e3b1`, Unity 6000.3.22f1이며 RC-01과 같은 Windows/NTFS 장비다. 공유 Editor 실행 전 소스 1,602개 파일과 원본 Library 42,420개 파일(3,141,660,252바이트) 전체를 RC-01 입력과 대조했다. 제품 소스와 고정 실행 파일 hash도 `7630970`과 같고 현재 문서 HEAD는 `37cfa01`이다. 따라서 기존 완료한 RC-01 Splinter 실행을 재사용했다. **Splinter를 짝지어 새로 실행하지 않았다.** 실행 순서를 무작위화하거나 OS 캐시를 비우지 않았다.

A는 `Increment(3)`을 4에서 5로, B는 `Double(3)`을 6에서 9로 바꾼다. 각 에이전트가 자기 Git 워크트리의 지정 파일만 편집·커밋했다. 실제 독립 하위 에이전트 코드 작업이며, 새 Codex 앱 대화나 앱 관리 워크트리 생성은 아니다. AI 추론·기능 구현·대화 생성·앱 인계 지연은 측정하지 않는다.

원본 Editor는 기존 Library를 사용한다. 공통 검증 시작점에 두 후보가 모두 준비돼 있다. 제어자 하나가 A를 적용·새로고침하고 로드된 assembly와 선택 에셋을 확인한 뒤, A 소스 복원과 B 적용을 **한 번의** 새로고침으로 수행한다. B를 독립 검증하고 원본 소스를 복원·재컴파일한 뒤 정상 종료한다. A→B 전환을 묶어 불필요한 중간 기준 상태 컴파일을 피한다. RC-01의 기존 외부 계측 probe를 사용하며 새 패키지·MCP·Unity CLI·서비스 설정은 추가하지 않는다. 과거 Unity Agent Coordination Q 패키지 검증과 별도이며 Q 패키지나 어댑터의 성공을 주장하지 않는다.

공유 Editor는 PID 51996, 시작 ticks `639275472228263809`였다. 모든 성공 관측에서 해당 identity와 원본 프로젝트 경로를 확인했다. A/B 확인에는 최신 준비 상태, 일치하는 refresh 요청의 성공 응답, 컴파일 오류 없음, assembly MVID/generation 변경, 값 `(5,6,13)`·`(4,9,13)`과 기준 `(4,6,13)` 복원이 필요했다. 에셋 GUID·mesh/texture/scene 정보·dependency hash·렌더 preview hash는 RC-01과 같고 요청별 preview 경로와 렌더 시간만 다르다.

## 비교의 의미

코드 작성은 양쪽 모두 병렬로 할 수 있다. Editor 사용을 겹쳐서 줄일 수 있는 것은 Editor 의존 연산이다. 개별 속도가 같고 각 연산이 `E_A`, `E_B`가 걸린다면 순차 구간은 대략 `E_A + E_B`, 병렬은 `max(E_A,E_B)`다. 겹쳐 아끼는 시간이 추가 준비·보존·병합·정리·자원 경쟁 비용보다 커야 한다. AI 추론이나 코드 작성만 길어지는 것은 이 조건을 충족하지 않는다. 긴 연산의 손익분기는 측정하지 않았고 테스트/빌드에서는 CPU·메모리·디스크·GPU·외부 서비스의 경쟁과 증가 양상이 다를 수 있다.

별도 프로젝트 경로와 Library를 사용하는 일반 Unity 워크트리도 RC-01에서 독립 Editor를 동시에 실행했다. 따라서 Splinter는 Unity Editor 두 개 실행의 필수 조건이 아니다. 실측한 저장 이득은 독립 상태를 유지하면서 소스/Library 중복을 줄이는 데 해당한다. 프로그램 전체의 단일 인스턴스 제약이나 공유 외부 도구 제어 채널은 별도 제약이며 저장 격리만으로 자동 해소되지 않는다.

[공식 Codex 워크트리 안내](https://learn.chatgpt.com/docs/environments/git-worktrees)는 한 인스턴스만 가능한 앱 등 로컬 checkout에서 검증해야 하는 경우 Local 인계를 권한다. 모든 Unity 프로젝트가 Editor 하나를 공유해야 한다고 하지는 않는다. 워크트리의 파일·의존성·캐시 디스크 비용도 별도로 설명하지만, 그 저장 비용이 단일 인스턴스 문구의 이유라고 밝히지는 않는다. Unity [명령행 문서](https://docs.unity3d.com/6000.3/Documentation/Manual/EditorCommandLineArguments.html)도 이미 열린 동일 프로젝트와 다른 프로젝트 경로를 구분한다.

## 보존과 한계

A 결과 `3fc085588117a2d52093a19c868ce959b26e7993`과 B 결과 `79ac646af81f70d057b42acb48805bf4c0fdca6b`는 `refs/splinter-benchmark/20261014-shared/` 아래 보존한다. 병합 결과 tree는 RC-01과 같은 `756e0a926577c9bcff036c823b4816b3b2d5fb19`다. 원본 branch/HEAD와 소스 1,602개 파일 바이트가 그대로이며 기준 상태 컴파일·Editor 정상 종료가 성공했다. 새 코드 워크트리 두 개와 등록을 회수했고 기존 refs/워크트리는 보존했다.

원본 Library는 일반 NTFS 폴더다. 공유 Editor가 정상적으로 캐시를 재생성했으며 그 캐시 바이트를 **되돌리지는 않았다**. 다음 정확한 입력 비교에서는 현재 Library를 새로 고정해야 하며 과거 RC-01 manifest와 여전히 같다고 가정하면 안 된다. 패키지·서비스·전역 설정·관리자 변경은 없었다.

Play Mode·Unity 테스트·게임 빌드·병합 결과 컴파일·새 공유 Editor 저장 공간/peak RAM 측정·긴 작업 손익분기는 **NotRun**이다. RC-01의 추가 할당 98.64% 절감은 독립 Editor 방식 두 개의 비교이며 이번 Editor 하나 방식 대비 실측 저장 절감이 아니다.
