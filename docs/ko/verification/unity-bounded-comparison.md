# 현재 bounded 저널의 Unity 비교

## BC-01 — 같은 입력의 병렬 Editor와 공유 Editor

**2026-10-23 KST**, 제품 커밋 `c4fa5063964e7b8456de4ea7735c042fb9af8930`에서 측정했다. 현재 bounded 기본값의 전체 작업은 **537.6초**, 병렬 코드 준비 뒤 공유 Editor 하나로 순차 검증한 전체 작업은 **82.1초**였다. Splinter는 과거 [FU-01](unity-finalization-rerun.md)보다 **230.7초 적게**, 이 작은 작업의 공유 Editor보다 **455.5초 더** 걸렸다. 관측한 실행의 차이이며 작업량에 따른 증가 법칙을 실측한 값은 아니다. 과거 공유 Editor 값을 재사용하지 않고 양쪽을 새로 측정했다.

정확한 값·후보/소스/실행 파일 hash·단계 구간·결과 identity·회수 근거는 [데이터셋](../../../reports/benchmarks/unity-bounded-comparison-20261023.json)에 있다. 원시 근거는 로컬 `artifacts/unity-bounded-comparison-clean-20261023`, 중단된 진단 실행은 별도 `artifacts/unity-bounded-comparison-20261023`에 보존한다.

## 입력과 계측 경계

- 원본 fixture는 `splinter-unity`, 커밋 `b09fa58e9d40a560d4fe1af7a213f8ac23e8e3b1`, **추적 파일 1,602개 / 2,804,772,822바이트**다. Unity **6000.3.22f1**, Windows 11 Home **10.0.26200**, Ryzen 5 5600X **6코어 / 12스레드**, 설치 RAM **68,628,553,728바이트**다.
- 새 비교의 양쪽은 바이트가 같은 소스와 **Library 42,424파일 / 3,142,485,226바이트**로 시작했다. 전체 파일 hash로 기준본 캡처와 공유 Editor 실행 전 복원을 증명했다. FU-01과 비교하면 Library는 **추가 6개·삭제 0개·변경 37개**다. FU-01은 42,418파일 / 3,141,789,464바이트였으므로 과거와 현재 Library까지 동일한 것은 아니다.
- 양쪽은 같은 자동화된 A/B 한 줄 변경과 병렬 코드 준비를 사용했다. Splinter는 독립 `workspace ensure`, `git-snapshot`, 명시적 공통 Library 기준본과 반환된 프로젝트 경로를 사용했다. 실제 A/B 응답에서 `journalStorageMode=bounded`, `journalOptimizationEnabled=false`, **16MiB / 4,096-frame** suffix 제한을 확인했다. 모드 강제 변경이나 제품 수정은 없었다.
- 각 Editor에서 기준 값, 명시적 refresh 후 새 컴파일 generation·assembly MVID, 격리된 기대 값, 컴파일 오류 없음과 같은 선택 에셋/장면 검사를 확인했다. 공유 방식은 한 번의 refresh에 A 복원과 B 적용을 함께 수행하고, 마지막에 원본을 복원·재컴파일했다. fixture의 기존 외부 검증 제어자가 수행했으며 제품 Unity API나 MCP/Unity CLI 자격은 아니다.
- Splinter는 Library 준비부터 복원까지, 병렬 `checkpoint --release`와 Editor 정상 종료를 포함했다. 공유 방식은 병렬 코드 워크트리 생성, 후보 편집/보존 구간의 합집합, 연속된 Editor 작업, 소스 결과 병합과 워크트리 회수를 포함했다. 겹치는 A/B 구간은 한 번만 세며 구간 안 명령 전달 간격을 포함했다. AI 추론/대화 시작·빌드/시험·읽기 전용 입력/최종 확인은 제외했다.

## 조건부 손익분기

같은 길이인 각 작업을 공유 Editor에서 단독 수행하는 시간을 `E`, 병렬 실행 시 소요 시간 배수를 `r`, 해당 작업 밖의 추가 수명주기 비용을 `H`로 두면 `2E`와 `H + rE`를 비교한다. `r < 2`이고 `E > H / (2 - r)`일 때만 Splinter가 더 빠르다.

실측 컴파일/에셋 구간을 빼면 다음과 같다.

`H = (537.600687 - 32.346453) - (82.060419 - 26.397176) = 449.590990초`.

과거 FU-01의 전체 정밀도 데이터로 계산한 값은 **656.887147초**다. 새 추정치는 **31.6% 감소**, 약 **10분 56.9초 → 7분 29.6초**다. 최초 Editor 준비와 복원도 포함하며 `ensure`나 종료 명령만의 비용은 아니다.

| 병렬 소요 시간 배수 `r` 가정 | 과거 작업당 기준 | 현재 작업당 기준 | 현재 공유 순차 합계 |
| --- | ---: | ---: | ---: |
| 1.00배 | 10.95분 | **7.49분** | 14.99분 |
| 1.25배 | 14.60분 | **9.99분** | 19.98분 |
| 1.50배 | 21.90분 | **14.99분** | 29.97분 |
| 1.80배 | 54.74분 | **37.47분** | 74.93분 |
| 2.00배 이상 | 손익분기 없음 | **손익분기 없음** | — |

이번 짧은 컴파일/에셋 검증 한 쌍은 병렬 실행이 **5.949278초 더** 걸렸다. 같은 길이로 환산한 비율 `2 × 32.346453 / 26.397176 = 2.45`는 이 관측만 설명한다. 작업량이 늘어도 비례해서 느려진다거나 추가 시간이 고정됨을 입증하지 않는다. 데이터셋의 `observedCompilePatternCrossoverExists=false`는 이 비율을 모델에서 일정하게 유지하는 조건의 결과이며, 긴 작업의 실측 결론이 아니다. 같은 한 쌍을 반복할 때마다 5.949278초의 손해가 유지된다면 누적되겠지만 반복은 측정하지 않았다.

덧셈 형태의 대안으로 병렬 작업 구간을 `E + D(E)`로 쓰면 손익분기는 `E > H + D(E)`다. `D(E)`가 병렬 작업 구간마다 고정 20초라면 작업당 조건부 기준은 `449.590990 + 20 = 469.590990초`다. `D(E) = (r - 1)E`일 때만 위 비례 표를 적용한다. refresh별 고정 비용·작업량 비례 비용·혼합 형태를 구분하려면 연산 횟수와 작업량을 달리해 측정해야 한다. 준비·종료는 작업공간 수명주기별로 발생하지만 그 값 자체도 프로젝트 크기와 누적 변경량에 따라 달라질 수 있다. 표는 `H` 고정과 실제 중첩을 가정하며 긴 작업에서는 checkpoint/복원 비용도 증가할 수 있다. 작업 길이가 다르면 `E_A + E_B > H + r × max(E_A, E_B)`가 필요하다. 양쪽 모두 코드 준비는 병렬이므로 AI 코딩 시간만 길어져서는 이득이 생기지 않는다.

## 중단된 진단과 최종 회수

앞선 진단 실행은 정상 전체 시간에 포함하지 않았다. 과거 PNG 바이트 일치 assertion에서 현재 전경 픽셀 **9,457개**, 과거 **9,529개**의 차이가 발생했다. 선택 에셋 identity·장면/의존성 검사와 유효 렌더링은 일치했으며 픽셀 차이 원인은 미확정이다. 수정한 제어자는 정확한 에셋 검사·요청/hash 검증·비어 있지 않은 렌더·장면 복원을 유지하고, 과거 이미지 바이트 일치를 요구하는 대신 픽셀/hash 차이를 기록한다. 최종 새 비교의 네 이미지 SHA-256은 모두 `df94cefbc5f0d2fa6b46b878badb8848bc0221d66130778347349725a47b632d`로 같고 대표 Splinter/공유 PNG를 시각 확인했다.

진단 회수 중 한 Unity Editor가 `Editor-5.x/Preferences/Overlays/CanvasesSaveData.asset` 사용자 환경설정 저장에서 접근 거부 팝업을 표시했다. 다른 Editor가 종료된 뒤 **Try Again을 한 번** 눌렀고 팝업과 Editor가 종료됐다. 파일/ACL/전역 환경설정을 수동 변경하거나 Force Quit을 사용하지 않았다. 실패한 `EditorStopTimeout` 응답을 보존하고 같은 workspace의 checkpoint/release를 재개해 완료한 뒤 원본 Library를 복원했다. 접근 거부의 원인이나 Unity 공통 환경설정 문제의 영구 해결까지 입증한 것은 아니다.

새 계측 비교는 팝업 조작·시간 초과·복구 없이 완료했다. 두 Splinter Editor의 정상 종료 영수증(exit code **0**, active job processes **0**), 독립 결과 보존, 소유 mount/delta 부재와 provider 종료를 확인했다. 공유 검증 전 원본 Library는 일반 NTFS이며 입력과 바이트가 같았다. 공유 검증 후 **1,602개** 소스 파일, 원래 HEAD/브랜치/설정, 기존 ref/워크트리, 기준 컴파일과 소유 Editor/워크트리 회수를 검증했다. 공유 Editor가 정상 재생성한 Library 캐시는 유지했다.

양쪽은 같은 병합 소스 tree `756e0a926577c9bcff036c823b4816b3b2d5fb19`를 원본에 적용하지 않고 독립 보존했다. `scripts/build.ps1`은 **1,691개 통과·실패 0개·24개 건너뜀**이다. 선택한 현재 응답 객체 **17개**(**runtime 8 / discovery 9**)가 현재 schema 검사를 통과했다. 최초 시험 입력 선택기에 배열이 포함된 오류를 수정했으며 응답 payload는 바꾸지 않았다.

**한계:** 진단 실행 이후 Splinter → 공유 순서의 한 묶음이며 OS 캐시 초기화·무작위 순서 반복은 하지 않았다. 진단 최초 준비는 약 **251.6초**, 최종은 **187.2초**로 편차가 크며 최종 값은 cold-start 보장이 아니다. 저널만의 인과 절감률·일반 Unity 지원·긴 작업의 실제 손익분기·Play Mode·Unity 테스트·게임 빌드·병합 결과 컴파일·공간 peak·전체 RAM·Editor 3–4개 확장은 미자격이다. 과거 공간 수치는 원래 RC-01 경계를 유지한다.
