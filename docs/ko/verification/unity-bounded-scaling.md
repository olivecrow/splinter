# Bounded 저널의 Unity 컴파일 작업량별 측정

## BS-01 — 실제 작업량 변화 순서

**2026-10-23 KST**, 제품 `c4fa5063964e7b8456de4ea7735c042fb9af8930`, fixture `b09fa58e9d40a560d4fe1af7a213f8ac23e8e3b1`, Unity **6000.3.22f1**에서 측정했다. 현재 bounded SJR2 기본값과 [BC-01](unity-bounded-comparison.md)의 동일 runtime을 사용했다. **추가 시간을 일정한 초수나 일정 배수 중 하나로 확정할 수 없다.** 큰 컴파일 구간에서는 병렬 실행의 이득이 나타났지만, 8개 구간에서 절약한 **142.0초**보다 이번 준비·종료의 추가 비용 **783.7초**가 컸다. 계측한 전체 연산은 **1,582.4초 / 940.6초**, Splinter가 총 **641.8초 더 걸렸다.**

[정확한 데이터](../../../reports/benchmarks/unity-bounded-scaling-20261023.json). 원시 명령·소스 입력·DLL·요청별 증명·로그는 `artifacts/unity-bounded-scaling-20261023`에 보존한다. 아래의 입력 예외와 복원 비용을 포함한 결과이며, 전체 Library가 완전히 같은 새 양쪽 실행으로 표현하지 않는다.

## 작업량과 관측값

각 작업은 담당 일반 C# 파일을 수정하고 **0·4,096·16,384·65,536개 메서드**를 추가한다. 실제 순서는 `0 → 4096 → 16384 → 65536 → 65536 → 16384 → 4096 → 0`이다. 매 구간 각 작업은 refresh를 정확히 한 번 명시적으로 요청하고 같은 에셋·장면·렌더 검사를 수행한다. 인위적 대기를 작업량으로 넣지 않았다. 합성 컴파일 부하이며 게임플레이·테스트·게임 빌드나 대표 기능 개발의 벤치마크는 아니다.

| 작업당 추가 메서드 | 공유 Editor A/B 시간, 증가 / 감소 | Splinter A/B 시간, 증가 / 감소 | Splinter 추가 시간, 두 관측 평균 |
| --- | ---: | ---: | ---: |
| 0 | 26.0 / 25.9 | 35.6 / 38.6 | +11.2 |
| 4,096 | 27.0 / 27.3 | 34.1 / 37.1 | +8.5 |
| 16,384 | 29.4 / 192.3 | 62.2 / 236.7 | +38.6 |
| 65,536 | 212.6 / 347.6 | 65.7 / 236.0 | -129.3 |

각 셀은 A/B 두 작업의 실제 구간을 초 단위로 각각 표시한다. 추가 시간이 음수면 Splinter의 절약이다. Splinter의 A/B 중첩은 한 번만 세고 공유 Editor는 A/B를 순차 실행한다. 작은 파일 전달과 동일 에셋 검사는 포함하며 별도의 DLL·해시 증명은 양쪽 타이머에서 제외한다.

메서드 수가 같은 65,536개에서도 Splinter는 **65.7 / 236.0초**였다. 공유 Editor에서도 시간이 달랐으며 직전 로드 어셈블리·순서·누적 상태를 별도로 통제하지 않았다. 따라서 메서드 수만의 함수로 읽을 수 없다. 독립 작업은 자신의 이전 소스를 유지하고, 공유 Editor는 상대 작업을 원복하면서 다음 작업을 적용한다. 공유 B 직전에는 현재 A가 있지만 독립 B 직전에는 자신의 이전 구간이 있다. 이 측정은 서로 다른 상태 전환까지 포함한 두 연속 작업 흐름의 비교이며, 전후 Editor 상태까지 동일하게 맞춘 저널 단독 비용 실험이 아니다.

데이터에는 네 수준의 평균과 `E = 공유 A/B 시간 / 2`를 이용한 `S = E + d`, `S = rE`, `S = c + rE` 진단 적합값도 보존한다. 여기서 E는 균형 잡힌 경우로 환산한 기술 값일 뿐, 작업별 이전 상태까지 통제한 독립 실행 시간은 아니다. 반복·이력 편차, 수준별 2회 관측과 이 상태 차이 때문에 적합 계수를 인과적인 비례 법칙으로 해석할 수 없다. 보편적인 추가 초수나 고정 배수 모두 자격이 없다. 원인 분리에는 시작 상태와 반복을 별도로 통제한 실험이 필요하며 이번 실행이 그 근거를 제공한 것으로 쓰지 않는다.

## 통제 조건과 검증

- BC-01과 같은 PC: Windows 11 Home 10.0.26200, Ryzen 5 5600X, 6코어 / 12스레드, 설치 RAM 68,628,553,728바이트. 실행 전 제품·계약 237개 파일과 runtime 32개 파일의 동일 해시를 확인했다. 제품 코드·Unity 버전·패키지는 바꾸지 않았다.
- 원본은 고정 raw Git 입력 **1,602개 파일 / 2,804,772,822바이트**다. Splinter 최초 Library는 **42,421개 파일 / 3,144,431,511바이트**다. 공유 실행 전 나머지 **42,420개 파일**은 모두 동일하며, 삭제된 외부 서버의 5바이트 PID 파일 예외는 아래에 명시한다.
- `git-snapshot`, 동일 Git 기준, 명시적 Library 기준본 하나, A/B 병렬 ensure와 반환 경로를 사용했다. 양쪽 응답은 `journalStorageMode=bounded`, `journalOptimizationEnabled=false`를 확인하며 suffix 제한은 16MiB / 4,096프레임이다.
- **32개 작업 검증** 모두 정확한 Editor 프로젝트/PID/시작 identity, 새 generation·assembly MVID, 기대한 A/B 로드 값, 보고된 컴파일 오류 없음, 에셋 검사, 요청별 유효 렌더와 장면 복원을 요구한다. DLL에는 요청 수와 정확히 같은 모든 생성 메서드 이름과 기대한 생성 클래스가 있어야 한다. DLL 해시와 사본은 계측 밖에서 보존했다.
- Splinter 순서 하나 다음 공유 순서 하나이며 OS 캐시 초기화·독립 묶음 무작위 반복은 하지 않았다. 방식 사이 원본 소스를 복원하고 임시 Git 설정도 되돌렸다. 양쪽은 같은 최종 병합 소스 트리를 보존했으며 그 병합 결과를 다시 컴파일하지는 않았다.

## 준비·종료와 손익분기

소수 한 자리 초 단위이며, 대화 경과 시간이 아닌 연산 구간 합계다. 생성 입력 준비·읽기 전용 증명·AI/도구 대기와 별도의 첫 준비 실패·서버 복구는 제외한다. 수명주기 비용은 8회 검증 전체에 한 번 부과한다.

| 구간 | Splinter | 공유 Editor |
| --- | ---: | ---: |
| 준비와 최초 Editor 준비 | 316.5s | 33.9s |
| A/B 검증 구간 8회 | 746.2s | 888.1s |
| 결과 보존·정상 종료·소스 복원 | 114.0s | 15.5s |
| 소스 결과 병합 | 0.4s | 0.3s |
| 원본 Library 복원 / 코드 워크트리 회수 | 405.4s | 2.8s |
| 계측한 전체 연산 | 1,582.4s | 940.6s |

일반적인 계산은 다음과 같다.

```text
순 절약 시간 = 합계(공유 검증 구간 - 병렬 검증 구간)
               - 추가 준비·종료 비용
```

이번 순서는 **142.0초 − 783.7초 ≈ −641.8초**(원시값으로 계산 후 반올림)로 손익분기에 도달하지 못했다. 최대 작업량 두 구간은 평균 **129.3초**를 절약했다. 같은 절약과 이번 수명주기 비용이 그대로 반복된다고 가정할 때 산술 기준은 **그러한 A/B 구간 7회**다. 실제로는 2회만 측정했으므로 이는 조건부 반복 횟수이며 긴 세션의 실측 손익분기나 일반적인 작업 시간 권고가 아니다. 준비 비용을 매 수정에 다시 부과하지 않지만, 최종화 비용은 누적 상태와 복원 경로에 따라 달라질 수 있다.

## 보존한 중단과 입력 예외

첫 Library 준비는 **17.5초** 뒤 실패했다. 이전 BC-01 공유 Editor(PID 33948)의 자식 계보에 있는 MCP 서버가 `Library/MCPForUnity/Logs/server-launch-8080.log`를 쓰기 점유하고 있었다. 사용자 명시 승인 후 서버 PID **43056**만 종료했다. Windows가 비강제 taskkill을 거부해 서버 강제 종료를 사용했으며 Unity Editor를 강제 종료하거나 패키지·전역 설정을 바꾸지 않았다. 같은 home `.local/bs23`, key `bs23-library`, basis `b91d15db564e3a2e1c85623a`와 보존한 준비 intent를 재개했다. 성공한 준비는 **59.5초**였다. 서버 종료 후 로그의 최종 바이트를 실행 전에 다시 고정했으며, 첫 실패와 승인·복구 대기는 에디터 작업 계측에서 제외한다.

정상 A/B release 뒤 Library 복원은 **405.4초**에 성공했으나, 사전 선언한 전체 Library 완전 일치 검사가 실패했다. 차이는 `MCPForUnity/RunState/mcp_http_8080.pid`, 즉 **`43056`을 담은 5바이트 파일**의 삭제 하나였다. 다른 파일 추가·삭제·내용 변경은 없었으며 원본 소스도 모두 일치했다. 오래된 PID 파일을 다시 만들지 않았다. 검사 실패를 보존하고 이 예외를 명시한 범위에서 공유 측정을 이어 갔다.

기록된 일반 `restore-plan.json` 경로를 사용했다. `ManagedUnchangedDirectoryRestore.Eligible`은 durable mutation 0과 불변 entry를 요구하므로 PID 삭제가 빠른 복원 경로를 배제한다. 이는 BC-01의 불변 Library 복원 58.8초와 **경로가 달라진 설명이며, 증가한 모든 초수의 원인을 단독 분리한 것은 아니다.** 관측한 405.4초를 수명주기 합계에 포함하며 코드 양의 비례 비용이나 보편적인 정리 상수로 쓰지 않는다.

소유 Splinter Editor 둘은 종료 코드 0·job 프로세스 0으로 정상 종료했고 mount·provider·delta를 회수했다. 원본 Library는 일반 NTFS로 복원됐다. 공유 실행은 원본 소스 복원·재컴파일, Editor 정상 종료, 확인한 소유 코드 워크트리만 회수했다. 원본 HEAD/branch·소스 1,602개·기존 ref/worktree·Git 설정을 확인했다. 공유 Editor가 정상 재생성한 Library 캐시는 유지한다. 외부 MCP 서버 수명은 이 소유 Editor·작업공간 회수 주장과 별도다.

변경 없는 제품의 앞서 완료한 build gate는 **1,691 통과 / 0 실패 / 24 skip**이며 문서·계측 제어 변경 때문에 다시 실행하지 않았다. 새 실행 응답 9개와 동일 후보의 discovery 응답 9개, 총 18개를 현재 응답 스키마로 검증해 통과했다. 새 전체 RAM·물리 peak, Play·Test Runner·게임 빌드, 3–4 Editor, 다른 프로젝트/도구/OS와 저널만의 인과적 속도 개선은 미측정이다. 과거 그래프는 양쪽 root README에서 제거하고 역사적 근거 파일은 보존했다.
