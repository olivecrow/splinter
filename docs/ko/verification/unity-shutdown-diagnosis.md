# Unity 종료 지연 진단

[English](../../verification/unity-shutdown-diagnosis.md)

**SD-01, 2026-10-23:** 사용자가 통제된 작업량 비교를 중단하고 비정상적인 종료 지연을 작은 단위부터 조사하도록 요청했다. 완료된 Splinter/공유 Editor 성능 비교가 아닌 진단이다. 제품 코드는 `c4fa506`, Unity는 Windows/NTFS의 `6000.3.22f1`이다.

## 관측과 통제 조건

긴 종료는 Splinter mount가 없는 일반 NTFS 프로젝트에서도 재현됐다. 이미 시작했던 65,536개 메서드 진단은 **컴파일 후 대량 리플렉션 검사를 생략하면 444.55초**, **검사를 하면 437.79초**에 정상 종료했다. 그 검사만 제거해서는 지연이 없어지지 않았다. 일반적인 Editor 종료 시간이나 Splinter의 고정 추가 비용으로 해석하지 않는다.

작은 사례는 매번 소스 1,602개와 Library 전체 42,038개 파일(3,105,800,655바이트), 실제 로드된 기준 DLL hash·MVID·IL fingerprint를 같게 맞췄다. 새 batch Editor에서 소스 변경 한 번, 실제 컴파일/재로드와 같은 에셋 검사를 수행했다. 코드는 컴파일 전에 디스크에 저장했다. 실험용 복제본에서 MCP와 이전 종료 hook을 제외했으며 원본 프로젝트·설치 도구·정상 원본 서버는 보존했다. OS 캐시는 초기화하지 않았다.

| 생성 메서드 | 생성 클래스 | 클래스당 메서드 | 컴파일/재로드 | 정상 종료 |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 0 | — | 7.23초 | 1.64초 |
| 1,024 | 1 | 1,024 | 6.93초 | 1.81초 |
| 4,096 | 1 | 4,096 | 6.33초 | 1.67초 |
| 16,384 | 1 | 16,384 | 7.23초 | 17.34초 |
| 16,384 | 64 | 256 | 6.05초 | 1.60초 |

같은 산술 메서드 16,384개를 64개 클래스로 나누자 종료 시간이 **15.75초** 줄었다. 코드 배치가 중요한 입력임을 확인했지만 일반적인 계산 복잡도나 실제 대형 프로젝트의 동작을 입증하지는 않는다. 구성별 관측은 1회다. 컴파일 구간은 약 6–7초인데 종료만 크게 달라져 합성 메서드 수를 유용한 Editor 작업량의 대리 지표로 쓰기 어렵다.

긴 `Cleanup mono` 구간에서는 한 스레드가 CPU를 사용했고 실행 주소 대부분은 JIT로 생성된 관리 코드였다. 단일 클래스 16,384개 사례의 명령 포인터 샘플링에서 스레드를 잠깐 중지한 시간은 합계 **0.01342초**다. 저장 대화상자 대기보다 관리 코드 실행이 관측됐지만 네이티브 심벌만으로 호출자를 특정하지는 못했다. 추가 계측은 진단이며 위 표에서 제외한다.

## 종료 시간의 의미

외부 실험 제어자가 종료 요청을 한 번 기록하고 정확한 Editor 프로세스의 exit code 0을 기다렸다. Editor 안의 처리기는 dirty 씬과 실행/진입 중인 Play Mode를 거부한 뒤 `EditorApplication.Exit(0)`을 호출했다. 종료 직전에 `SaveAssets`나 씬 저장을 별도로 호출하지는 않았다. 따라서 확인된 씬 상태에서 종료하는 시간이며, 명시적인 저장부터 종료까지의 시간은 아니다. Unity 문서도 [이 API는 저장 여부를 묻지 않는다](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/EditorApplication.Exit.html)고 설명한다. 정상 측정에 포함한 Editor를 강제 종료하지 않았다.

앞선 Splinter 65,536개 pilot에서는 제어자의 300초 대기를 초과했다. 별도 관측으로 계속 기다려 기록된 종료 요청 이후 약 553.1초/555.1초에 두 프로세스가 정상 종료함을 확인했다. 같은 작업의 결과 보존/회수와 정확한 Library 복원을 마쳤다. 타임아웃/복구와 미완료 비교 쌍은 정상 비교 통계에서 제외한다. 사용자가 비교 중단을 요청한 뒤 새 65,536개 작업을 시작하지 않았다.

## 종료 대기·병렬화와 현재 제품

`Cleanup mono`는 Splinter 함수가 아닌 Unity 종료 단계다. 관리 콜백과 런타임 정리가 포함될 수 있다. 로그 한 줄은 소스/캐시 쓰기·파일 핸들·실행 이미지 매핑이 모두 끝났다는 증명이 아니다. Splinter 작업 스레드를 늘려 이 내부 단계를 직접 병렬화할 수는 없다. 특정 앱/패키지 콜백이 원인이면 소유 코드에서 최적화를 검토할 수 있지만, 식별 전에 스레드 수부터 늘릴 근거는 없다.

현재 범위 저널 checkpoint는 `applications.StopAsync`와 `RequireStopped`를 기다린 뒤 결과를 보존한다([coordinator](../../../src/Splinter.Runtime/WorkspaceCoordinator.cs)). 수집 전후 저널 seal을 비교한다. release도 소유 앱 프로세스 0 확인, 독립 결과 검증, unmount, 최종 seal 비교, provider 핸들 0 확인 이후 delta를 삭제한다([수명주기](../../../src/Splinter.Runtime/SnapshotWorkspaces.cs), [Windows backend](../../../src/Splinter.Platform.Windows/NtfsSnapshotWorkspaceBackend.cs)). 작업 잠금은 연산 전체에 걸쳐 유지된다. 현재 `integrate`도 stop을 호출한다. 종료 타임아웃은 자원 보존 사유이며 정리를 건너뛸 승인이 아니다.

| Editor 종료 중 겹칠 작업 | 현재 경계 |
| --- | --- |
| 다른 독립 작업 진행·이미 종료한 peer의 완료/회수 | 각 작업의 guard 안에서 가능하다. A/B 완료는 중첩할 수 있지만 공통 기준본은 마지막 사용자가 끝날 때까지 유지한다. |
| 이미 보존한 불변 commit의 Git 병합 계산 | 살아 있는 Editor 파일과 독립적인 외부 Git 작업이다. 현재 같은 작업의 `integrate` stop/target guard를 우회한다는 뜻은 아니다. |
| 종료 중인 이 Editor의 최신 소스를 보존하고 통합 | 현재 checkpoint 경로에는 없다. 별도 불변 소스 세대 계약이 필요하다. |
| mount/private 저널 삭제·사용 중인 기준본 해제·공유 Library 조기 복원 | 현재 수명/핸들 계약에서는 안전하지 않다. 최종 회수는 부재 관측과 안정된 seal을 기다려야 한다. |

향후에는 **저장 후 명시적 독립 소스 결과 고정 → 정상 종료 요청과 고정 결과 처리 중첩 → 종료/최종 쓰기 확인 후 자원 회수**로 분리할 수 있다. 고정 결과와 이후 쓰기를 구별하고 소스/Library 의존성·대상 보호·중단 시 같은 게시/회수 intent 복구가 필요하다. 여기서 구현하거나 검증한 기능은 아니다. 기존 호출을 단순히 `Task.WhenAll`로 묶으면 현재 보장을 약화한다. 같은 작업공간을 반복 사용하면 원래부터 매 수정마다 종료할 필요가 없다.

통제 pilot 두 건의 Git 병합은 **0.27초·0.25초**였다. 병합만 겹치면 숨길 수 있는 비용도 그 정도이며 수백 초를 해결하지는 못한다. 소스 보존과 종료 자체의 중첩 효과는 미측정이며 위의 별도 수명 설계가 필요하다.

## 근거와 처리 결과

[데이터셋](../../../reports/benchmarks/unity-shutdown-diagnosis-20261023.json)은 5개 사례 결과·기준 identity·정상 종료/오프라인 코드 검사와 `artifacts/unity-controlled-batch-scaling-20261023/`의 로컬 원시 근거 hash를 보존한다. 이 로컬 원시 artifacts는 보고서와 함께 배포하지 않는다. 5개 사례 묶음의 소스/Library 정확한 복원은 확인했다. 추가 네이티브 JIT 테이블 탐색 두 번은 진단 계측 내부에서 충돌했다. 측정에서 제외하고 로그를 보존했으며 임시 복제본 스크립트를 제거한 뒤 소스/Library를 정확히 복원했다. 이벤트만 기록한 계측은 정상 종료했으나 지연 주소의 함수명을 해석하지 못했다. 설치된 Unity/패키지 코드는 수정하지 않았다.

디버거 클라이언트 연결 실패는 정상 시간과 분리한다. 마지막 raw protocol 시도는 batch mode에서 Unity의 Debug Mode 연결 대화상자를 발생시켰다. 제어자는 1,200초 뒤 타임아웃됐고 컴퓨터 제어도 사용자에 의해 중단됐다. 이 시도의 정상 종료와 최종 복원 영수증은 없다. 회수 상태는 **미확인**이며 앞선 성공한 복원으로 대신하지 않는다. 정확히 지연을 일으킨 관리 함수는 미확정이고, 이 문서 커밋을 준비하면서 추가 진단을 실행하지 않았다.

중단한 통제 비교는 고정 추가 비용·일정 배수·일반 손익분기를 확정하지 않는다. 이전 BS-01 표와 조건부 7회 계산은 과거 근거로 보존하되 루트 README의 현재 성능 설명에서는 제거했다. BC-01의 현재 후보·짧은 작업 비교는 원래 한 묶음의 자격을 유지한다. 과거 그래프도 계속 제외한다. 새 Play/Test/build·GUI 속도·저장 공간/RAM·일반 도구 지원·완료된 작업량별 성능 자격은 **NotRun**이다.
