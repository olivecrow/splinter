# Git project basis verification

[한국어](../ko/verification/git-project-basis.md)

The question is whether a project already recorded in Git can be read as an immutable basis while maintaining/reclaiming range workspaces without VSS. Scope is limited to the Git portions of VP-01/02 and VP-04/05 in the [implementation scope](../plans/project-scoped-basis-and-reclamation-review.md). Unity Editor/Library/MCP were NotRun for the initial implementation candidate below; subsequent reader fixes and actual Unity A/B are owned by [separate verification](git-unity-validation.md). This does not extend to Plastic, VCS-free transition, or large/ARM/OS-failure matrices.

<a id="자동-계약과-reader"></a>
## Automatic contracts and reader

The current no-progress read limit is verified in `GitProgressReadTests` with a controlled clock/partial stream. Verification lasting 160 seconds in total completes when each partial read finishes within 20 seconds; hashing/idle do not terminate the reader. One read stalled for 31 seconds produces one abort of that reader and `GitBasisReadTimeout`. Actual small loose/packed Git reads and nonpublication of corrupt request buffers remain covered. This controlled-stream test does not qualify actual large blobs/slow storage or overall Unity preparation performance. `RecoveryContractTests` verifies `requires-user-action`/`preserve` consistency for timeout/basis corruption.

`GitObjectSnapshotTests` verifies loose/packed objects in an actual small Git repository, fixed-range reads after original edits/branch movement, ignored-data exclusion, range-journal replay, reader release fence, peer/independent ref protection, symbolic/changed-ref rejection, reconciliation of lost create/delete responses, nonpublication of returned buffers on missing/corrupt blobs, and rejection of corrupt tree hashes/required receipt fields. `SnapshotWorkspaceCoordinatorTests.GitProjectModeUsesSharedJournalLifecycleAndSameRequestRecovery` verifies lost capture response, same request, compaction/independent result/release with a common fake. The fake is not WinFsp execution evidence.

Existing RunnerBundle/ContractAndCli, Git/original/peer, and discard/atomic-state regressions remain. Two reclaim tests in the first bounded execution failed because they compared array reference identity. They were corrected to compare serialized contents and are not classified as product failures. Failed TRX is preserved at `artifacts/git-basis-focused-classes/`. The first combined class/method filter ran 0 tests and does not count as a pass.

The first full run had 920 tests: 918 Passed, 1 Failed, and 1 test excluded at the time NotRun. A defect classified Git metadata-command failure due to tree corruption as generic `GitBasisUnavailable`; it was corrected to preservation-required `GitBasisObjectInvalid`. Blob/table hash checks and nonpublication of requested buffers remain. Failed TRX is preserved at `artifacts/git-project-basis-20261004/full-before-error-classification-fix.trx`; required full checks were rerun after correction.

Final `pwsh ./scripts/build.ps1` passed locked restore, Release build, and all 920 tests: 919 Passed/0 Failed/1 test excluded at the time NotRun. This automatic/actual Git unit is closed as scoped-complete-with-limitations, retaining NotRun/unknown below.

## Actual input and execution

Fixed input is a 1MiB binary, small text/ignore, and ignored Library sample at `.local/gb1004/source`, with Editor-free A/B in the exact same `.local/gb1004/home`. Execution/JSON are preserved in `artifacts/git-project-basis-20261004/native.ps1`, step responses, and `identity.json`. Original fixture, metadata, and independent results are not deleted.

The preparation script's `Git` function conflicted with the executable name and failed through recursion. The initially empty source/error were preserved; it was corrected to `git.exe` and continued in the same fixture. A state publication in restricted execution was rejected as AccessDenied/StateWriteIncomplete; diagnostics/temporary files were preserved. The same project/key/home resumed outside the sandbox with ordinary Windows user privileges. No service installation, grant, UAC elevation, or VSS capture workaround was used.

At B compaction's `compact-connect`, the mount reconnected, but workspace file publication failed with Win32 1175/StateWriteIncomplete, statePublication=unknown. Existing state/temporary files were preserved; the same compact request for exact B id/home continued to ready. No destination-file deletion/attribute change, new key, or replacement snapshot workaround was used. This single recovery does not establish/resolve the general cause of atomic-publication errors.
