# Latest-state journal with optimization ON

[한국어](ko/latest-only-journal.md)

`workspace compact --optimize-journal true` selects latest-state storage for the current journal after normal stop/unmount. `--revert-base-ranges true` selects the same input `revertBaseRanges`. New ordinary Windows providers default to the [bounded journal](bounded-journal.md). Existing tasks retain their saved format, including writer reconnects with the same ID/home. Later `compact` calls with the option omitted retain the current choice; explicit `false` switches to OFF. The stored choice cannot change during an operation.

```powershell
pwsh ./scripts/splinter.ps1 schema workspace.compact
pwsh ./scripts/splinter.ps1 workspace compact --id <id> --home <home> --optimize-journal true
pwsh ./scripts/splinter.ps1 workspace compact --id <id> --home <home> --optimize-journal false
```

The earlier default ON was explicitly selected by the user on 2026-10-06, considering both 1,536 actual 128KiB range writes across 32 PNGs taking 22.389s total (about 14.6ms average) and a 93.61% reduction in file-data allocation. These figures are not Unity Editor save/import times or improvements in cumulative managed allocation/RAM. Development Library caches and fixed SJR2 write probes retain OFF under separate contracts.

A new ON journal first fixes the exact identity/attempt choice in `journal-initialization.json`. Empty object seed, identity, and SJL4 root are each flushed and published by an initial move in the same directory; writes are allowed only after removing intent. Interruption before completion resumes creation only for the same identity/attempt. Existing empty SJR2 journals retain OFF. Damaged seeds, different owners, and unknown objects are preserved/rejected; initialization intent supports v1 with required NodeFormat=3 only. Missing/older node-format discriminators in roots and initialization intents are rejected before recovery or publication, without migration.

ON aims to retain the immutable original basis and **current private changed ranges** only on disk. While replacing B with C, B coexists with recovery records for incomplete C. Write success returns only after durable C publication and reclamation of prior payload. Completed writes leave no superseded B payload or earlier metadata versions on disk. Other files, peers, and the original basis are not reclaimed. It does not infer whole-task completion; acknowledgement boundaries apply to individual mutations.

## Current representation and writes

Overlay identity/workspace are v2; ON journals are **SJL4/root v4 with required NodeFormat=3, SJN3 nodes and SJP2 metadata pages**; OFF and independent candidate v3 journals are **SJR2**. Current compaction intent supports **v3 only**. Earlier NodeFormat=2/SJN2/SJP1, SJL1/SJL2/SJL3, SJT2/SJT3, and other pending/root/intent versions are preserved/rejected without automatic migration. Ensure or reads alone do not convert OFF to ON.

The initial SJL4 `delta.journal` root references a `latest-<attempt GUID>` directory and current seed node/bucket/block within the same delta. After the first mutation, root itself is the current mutation's capsule. Capsules contain a 128B owner/generation/previous-state/data-hash header, bounded private blocks followed by SJM2 metadata-page blocks, current node/bucket metadata, and a whole checksum. Each SJB1 block includes raw/Brotli payload up to the transfer limit (at most 1MiB) and an 80B identity/block-ID/length/hash header. Nodes locating current ranges and last path sequences/whiteouts describe current state, not an edit-history stack.

Payload locations retain only their physical address, length and optional current metadata; they do not retain historical capsule frames. Metadata validation resolves the current frame for that physical file. An in-memory file-to-object index limits publication/reclamation membership searches to affected files and is rebuilt from validated storage on reconnect. Footer comparisons use at most 64KiB of temporary buffer, and metadata hashing does not clone the validated byte array. These changes preserve the SJL4 format, complete validation and per-mutation flush/ACK; see [startup journal optimization verification](verification/journal-startup-optimization.md).

SJN3 nodes reuse unchanged logical pages of 1–32 extents after both appends and overwrites; the inline tail remains below 32 extents. A changed short prefix is combined with the next unchanged page when their total fits 32 extents, so descending inserts do not create one page per write. SJP2 metadata pages have separate `page-*.bin` names and SJM2 block headers. User payload precedes metadata pages in every capsule. Replacing a page preserves the preceding private bytes in place and carries only still-current objects after the earliest changed object. A retained prefix binds its original header hash in its owned backup name and revalidates every complete block's identity, bounds and payload hash; node/page references and exact inventory remain independently checked. Partial blocks and changed/missing prefixes are rejected. Carried objects are read once and hashed from those same bytes. Full-file and retained-prefix retirement hashes share one streamed read; final reclamation still rehashes its target. Page-reference arrays still scale with page count; total per-write metadata is not constant. Exact ownership, current-only reclamation, individual flush/ACK, independent candidate export and recovery remain. See [LC-01](verification/lifecycle-cost-optimization.md) for costs and limits; the earlier [SJN2 append comparison](verification/startup-time-optimization.md) is historical.

Write order is:

1. Prepare C extents using only existing private ranges. Partially replaced blocks repack remaining private slices into bounded blocks. When part of a capsule is replaced, move only still-valid private ranges/metadata from that capsule, leaving no previous version. There are no original reads, whole-file copy-up, or read hydration.
2. Record C payload/current metadata, exact put/remove inventory, previous owned-file hashes, and reclamation plan once in one `transaction.pending`. Capsule limit is 256MiB. After writing the whole checksum, **call `Flush(true)` once on that file**. Do not combine other mutations' flush/ACK.
3. Publish pending as current root through `File.Replace`, moving the previous root to a generation-specific backup in the same owned directory. Do not copy the old root or rewrite C payload.
4. Delete previous files with exact hashes, or truncate the replaced metadata-page/footer suffix when only still-valid private blocks remain. Reclaim replaced payload/metadata before successful return. Close private-read/root handles before publication and reopen current root after success. No disk payload cache is created.

Range reads use a lazy decoded-payload LRU in RAM, with a default **64MiB budget per `JournalDeltaStore`** and at most **4,096 entries**. The budget charges each decoded array plus a conservative **512B per entry**, including an in-flight miss before allocation. It is not a whole-process/GC/working-set cap; read scratch and other provider memory are separate. Every hit still reads the current encoded block through the owned journal and revalidates its SPB1 header, lengths and SHA-256. Only decompression of matching validated content is reused. Retired content may remain in the bounded LRU until eviction, but a physical address alone cannot authorize reuse or replace current storage checks.

The cache is cleared on encoded-read/decode failure, writer poison and close. Replay, seal and visitor-based full-stream validation bypass it; publication, reclamation, formats and individual durable flush/ACK are unchanged. `readCacheBytes=0` continues to describe absent disk hydration, not absent RAM use. See [time/memory optimization verification](verification/time-memory-optimization.md) for cache costs and limits; historical Unity timings do not qualify this newer cache.

After atomic publication, capsule validation and block/reference indexing use one short-lived read handle for the exact published root, avoiding a second open/close. On Windows its sharing mode prevents writes or path replacement between those passes. The handle closes before reclamation, including on validation failure or interruption. Full checksum, owner, format, namespace, metadata, length, range and generation checks remain; no validation pass or per-mutation durable flush/ACK is omitted. Failure still poisons the writer until the same journal reconnects. See [SA-02](verification/startup-additional-optimization.md#changes-and-guards); this change's isolated Unity preparation-time saving remains unmeasured. The subsequent combined candidate's actual timings are recorded in [UF-01](verification/unity-final-lifecycle.md).

Publish only after one flush makes **both data and metadata** durable. Compression selection, checksums, entire encoded-stream validation, and individual mutation ACK remain. Reclamation deletion/truncation is retryable owned cleanup backed by existing durable C, without additional payload copying or flush. Publication/reclamation and rewriting remaining private slices can make ON slower than OFF. Owned-writer byte counts for budget/ACK are fixed from initial inventory and incrementally updated only by exact published/reclaimed lengths. Explicit observations, seals, and reconnects inspect actual file inventories; metadata bookkeeping does not replace content-hash validation.

Same-writer reconnect checks generation order, exact owner, previous-state hash, and capsule bounds/checksum. For a known pending with an incomplete tail and root still at B, reclaim only pending and retain B. A complete C is reflushed, published, and owned reclamation completed, preserving the existing contract where a complete write interrupted before response may survive. After publication, resume only the root's exact reclamation plan. A backup with metadata already truncated is checked against its retained payload-prefix hash. Complete-checksum corruption, different identity, unknown files, missing current root after publication, and changed reclamation targets are preserved/rejected. Missing root does not select a historical backup as B or create a new OFF journal. Earlier SJL1/2/3 and SJT2/3 are preserved/rejected without migration. Confirmed Windows publication sharing/lock/replace-remove errors (32/33/1175) retry only the same flushed temporary file for at most 1 second. Directory/deletion/truncation durability under OS power loss is NotRun.

## Deletion, results, and observations

A deleted file remains readable with current content while its last open file context remains. WinFsp counts contexts per file ID and calls `ReleaseUnlinkedFile` on the last Close. ON reclaims only payload/node of that deleted current ID, retaining whiteout and last path-change sequence. Still-open replacement targets follow the same rule. Direct Runtime users must explicitly signal final context closure. Unlinked records lacking close notifications because of interruption are cleaned up by the next explicit stopped compact/release, without automatic sweeping.

For an ordinary linked file or unknown ID, `ReleaseUnlinkedFile` checks local disposed/poison/journal-length state under the mutation gate and returns without querying basis availability, because there is nothing to reclaim. Actual unlinked reclamation retains the complete basis-availability check and serialized commit. WinFsp's external mutation/retention locking remains. This [SA-02](verification/startup-additional-optimization.md#changes-and-guards) fast return does not waive any read, mutation, seal or recovery proof.

Seal bytes/hash include root **and every current object file**. Observed `journalOptimizationEnabled` describes actual writer storage format. `snapshot.compaction.journalOptimizationEnabled` is the receipt for a completed choice. `JournalBytes`, payload/metadata, and allocation sum multiple files; root length alone is not reported as cost. Read-only restore, checkpoint stable seals, release/discard exact inventories/interruption resumption, and peer/dirty/target guards remain.

SJL4 sealing hashes the exact bytes already streamed for capsule validation in ordinal physical-file order. Root bytes and the existing name/length framing, complete or retained-prefix validation, seed files, final head/membership/pending checks and separate before/after/post-unmount seals remain. No prior seal or writer metric substitutes for reading current content. Windows seals and reclamation inventory observations pin object-directory ancestry for the operation, then check every leaf. Reclamation validates plan paths before fencing and content after fencing; immediate predelete hashes remain because fences permit delete sharing. A resumed inventory without its already-reclaimed owner lock uses full path walks. [LC-03](verification/lifecycle-cost-optimization.md) records the bounded qualification.

Independent candidates and explicit OFF conversion write a single SJR2 **current-state initialization prefix**. Node/write/hidden/path sequence/projection state and a complete footer restore current state; subsequent OFF mutations continue the original append method. Partial initialization without footer is preserved/rejected as corruption. ON-to-OFF representation can grow due to metadata costs.

[Base reversion](journal-base-reversion.md) removes 4KiB units matching the fixed basis only during explicit compact. It does not compare against the original basis on every save. Therefore, live B→C→original bytes may leave one latest private range until the next explicit compact. Retaining only current payload regardless of save count and removing basis-identical payload have separate costs.

[Historical SJL2 costs](verification/latest-only-journal.md) remain separate; existing Unity/VSS/large-input/total-RAM qualification does not establish a new SJL4 pass.
