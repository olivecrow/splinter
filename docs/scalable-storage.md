# Scalable source, result and metadata storage

[Plan](plans/scalable-storage.md) · SCAL-01–08 verification

**Candidate implementation; mandatory qualification remains in progress.** Current candidate formats are task v4, managed basis v3, product overlay v3 and metadata-store format 2 (`SPM2`). Earlier state, including `SPM1` stores from the preceding task-v4 candidate, is preserved and refused; finish it with its matching binary. Historical RI/MX/GCO evidence belongs to its recorded candidate/input. The verification owner decides completion after every mandatory gate and the final build.

Large synthetic runs are stopped with state preserved. Actual 17GiB, full 100k publication/reclamation and matched large-input ABBA remain unqualified; recorded multi-hour tiny-file phases do not establish current large-project usability. The [verification index](verification/README.md) owns the default functional gate, and the [matched native A/B measurement](verification/parallel-workspace-performance.md) owns current small editorless performance evidence. Neither qualifies the remaining SCAL lifecycle, capacity or OS/power-loss scope.

The candidate replaces project-wide file/directory counts, path sums, flat result/plan JSON and fixed journal budgets with disk indices and streaming. The product has no `--max-journal-bytes` option. Filesystem path/file/capacity limits, unsupported metadata, checksum/identity checks and actual I/O errors remain. Necessary unique data and immutable history can grow: no quota does not imply constant disk use or time.

## Representation and processing

Current source scans refresh each enumerated leaf once and use that observation for type, length, time and the leaf path check. Ancestors still receive one current attribute query each; hashing rereads the file and checks one fresh post-read metadata observation. Managed None preparation combines nested VCS/incomplete-publication checks with full NTFS admission under ordinary native root/ancestor/directory pins before moving the source.

A live paged journal writer keeps at most 512 decoded nodes and an estimated 1MiB object/path charge, separately from the metadata-page cache; neither charge is an RSS limit. Root replacement, discarded pending admissions and native container-fence epoch changes invalidate the cache. Container-reader eviction and append-container writer closure advance that epoch. Read-only, derived and write-shared readers use the ordinary verified lookup instead. Frozen cursors keep their exact records; source availability, poison, page/native checks and durable ACK boundaries remain. Full original/basis/workspace scans still exist; preparation verification separates small comparisons, resumed tasks and first-task large observations.

File comparison/history spools use checksummed binary metadata with their sole path in the spool key. Directory-listing sort keys retain original spelling and use the immutable path policy's comparer in every run/merge; values store fixed metadata without a duplicate component/full path. Availability, overlay precedence, hidden/excluded paths and fixed roots remain checked. Multi-entry pages are deferred: this candidate still writes one key per node and does not claim lower tree depth or large-workflow elapsed-time improvement.

The ST-36–40 follow-up extends journal batching to component names, hierarchical namespace inserts and WinFsp Create. At most 64 changes share ancestor updates; deep paths retain the iterative fallback. Root export flushes pending pages, and successful Create handles are retained under the mutation gate only after durable completion. Original progress groups up to 64 waiting entries with one page flush and one control persist, acknowledging none before both succeed; failure poisons pending/later admission. Dense applied-history updates and retained-parent membership use sorted merges; sparse history keeps point updates and the whole original scan remains. Metadata graph reachability and relocation use exact operation-local caches under shared scratch and the sort-run ceiling, with 512/256-byte per-entry accounting. Exhaustion retains the original disk frontier/map fallback. Complete page/root/native proofs, same-request recovery and ownership-checked deletion remain. No command, capability or persisted/wire version changes.

The throughput follow-up adds operation-scoped sorted spools, payload-index reuse and bounded durable publication. Adoption batches contain at most 64 frames; packing combines 63 relocation frames with its progress frame. Up to 64 raw range objects/references publish together while exact native source fences remain open; backing pin intents still precede links and result roots. Full independent hashes and publication boundaries remain. Payload hashing uses a cancellable 1MiB buffer per bounded worker, separately from metadata-cache accounting. This is not a file-count, aggregate-byte or history limit.

Directory records store component names, types, required metadata and content/child references. Logical binary pages are at most 64KiB and share append containers with a 64MiB rollover target. These are processing units, not whole-project limits. Logical hashes exclude physical addresses and relocation. Disk sorting, path interning and cursors avoid joining the complete catalog in memory. Git/Plastic listings stream; large Git blob chunk proofs can spill hash metadata to private disk.

The qualified Plastic reader batches up to 64 exact small revisions and 4MiB decoded bytes through one serialized private child. Every record retains ID/segment/length/MD5 checks and the tree's durable SHA-256 chunk proof; larger files stream ordinary segments. This bounded payload batch, vendor packet/decoder buffers and total child private memory are separate from the metadata-cache gauge. Equal hashes never substitute another revision or mutable original file.

The optional Core `ISnapshotAvailabilityScope` binds observations to an already opened immutable reader and its exact snapshot/read access. Windows Plastic readers pin the manifest, native basis/catalog directories and every physical catalog file against writes/deletion before the full admission proof. Heartbeats then revalidate those native paths, identities, lengths and physical namespace instead of repeatedly walking every entry. Full manifest proof remains at read/publication boundaries; ordinary observations and unqualified Git/None readers keep their existing full checks. The scope creates no ownership receipts and never adopts a catalog. Its linked native handle bindings scale with physical metadata files, separately from the page-cache budget.

Data-scaled Git record commands may remain silent until a complete clean-tree walk finishes. Their records stream without the blob protocol's 30-second output-read deadline; caller cancellation still terminates and drains the exact owned command, checks its exit status and rejects torn/oversized records. Fixed-object readers retain their existing 30-second blocked-read guards. R19's combined focused run passes 186 of 187 entries, with one subprocess-only actor entry executed by passing mandatory parents; actual large-input continuation and the final whole gate remain separate.

The 2026-11-01 user-authorized resource policy replaces the earlier 32MiB cache ceiling. `StorageResources` derives a process-local working target from one eighth of available memory, clamped to 128MiB–4GiB (512MiB when availability is unknown). It allocates on demand: metadata cache accounting uses five eighths of the target, and shared sort/spool scratch uses one eighth. At the 4GiB target these are 2.5GiB and 512MiB; each sort run/spool is limited to 128MiB/64MiB and spills when its own or shared allowance is exhausted. Merge buffers and a 64KiB fallback sort run (or one larger legal record) remain outside pooled scratch, avoiding nested-cursor deadlock and one-file-per-record spill amplification. This is neither a reservation nor an OS working-set or multi-process aggregate cap. Payload buffers, GC overhead and native bindings need separate headroom. Whole-tree input fences and all-target original locks can retain resources proportional to the pinned set; actual large-project private memory remains unqualified.

Each metadata store retains 16–64 container-reader handles according to the resource policy (48 at the 4GiB target), in explicit access order; handle use and cached-page hits mark the retained handle as recent, and eviction closes the least recently used handle. A handle shared with an append writer is reused without caching its pages; every read still checks the current container prefix, length, page checksum, logical hash, count and backward references. Only a handle that denies writes permits page caching. Cache invalidation directly visits the selected scope/container partition rather than scanning unrelated process-wide cache entries. Its partition/list index overhead is included in cache accounting. Eviction and disposal release the exact handle. Bound source-change views and inspection proofs own disposable reader references; record copies retain independent references, cursors retain their admitted reader, and completion/failure closes them before same-process reclamation.

`BoundedParallel` overlaps ordinary-file and concurrent-capable immutable-source enumeration, cancellable hashing and catalog construction without waiting for a whole hash batch. Final catalogs own sorting. Hash workers follow logical CPU count (1–32); independent payload I/O uses twice that count, clamped to 8–32. The fixed Plastic revision stream remains serial. Early disposal and failures cancel and join admitted work. Directory listings reuse their returned immutable metadata while retaining availability and overlay checks. Journal batches combine insert/update paths for both nodes and changed-path indices before durable ACK; ordinary-file change inspection merges ordered catalogs and bulk-builds the changed set. Persisted formats and complete publication proofs remain unchanged.

Read-only metadata stores with native pins retain an ordinary-ancestry guard for their reader lifetime, inspect mutable leaves on every lookup and release their own guard at disposal. A single result-verification call shares catalog summaries only while its native page fences remain held; later lifecycle boundaries open fresh proofs. Readers acquire store admission before identity/location/path fences. Collection and reader admission wait at most five seconds on actual native sharing/lock conflicts, with cancellable collection waits and no request-state mutation before admission. Writable stores retain their exclusive single-writer sharing contract. This coordinates short peer collection overlaps without deleting locks or weakening page/hash/identity proofs.

Reader teardown closes enclosing identity/location headers, page/container handles and ancestry guards before releasing store admission. A collector can replace location controls immediately after admission succeeds. Catalog and immutable-proof readers therefore keep admission through their complete native teardown, including cancellation/failure cleanup; a reader still closing a guard cannot admit collection.

Source manifest construction completes input enumeration and hashing into the existing checksummed, bounded binary spool before acquiring the home-wide metadata pool writer lock. Peers can scan/hash independently while only catalog/index publication remains serialized. The spool spills under the shared scratch budget and adds no second input scan or sort; it is operation scratch, never a recovery root.

Flat directory-record encoding/decoding is independent of a page store. Synthesized directory/path-marker sort streams keep the same field, alias and collision checks without creating an unused scratch writer. Git's comparison-only path lists retain checked sorting/spooling and the materialized catalog's path/component/page limits, but build an index only when searched. These are transient accelerators; product catalog publication, native proofs and durable flushes are unchanged.

Offline journal replay reads the original index without appending to it. Derived pages use a separate scratch store with the same logical store identity and a disjoint container range. Source pages are verified in place; creating the derived store does not copy the source catalog or file payload. Native directory/control identities and a durable owner precede derived page writes. Admitted cursor leases retain the derived store, source reader and owned basis until the final reader releases them. Recovery excludes active readers, reclaims only verified owned scratch and preserves unknown creation gaps outside the delta.

WinFsp directory reads retain one fixed cursor per open handle and serialize the whole native output packet. The next packet replays its single unreturned overflow entry before advancing; restart/seek or an explicit changed pattern binds a new cursor, while an omitted continuation pattern keeps the existing one. EOF, Cleanup, Close and errors release the reader exactly. No directory-wide native buffer or project-sized array is added. Installed WinFsp.Net 2.2.26215 component tests cover 10,000 generated members through actual 256-byte native buffers, linear member visits, overflow, concurrent mutation, restart, punctuation/dot markers and reader cleanup. This component evidence does not complete the separate 100,000-item mounted-provider qualification.

Small control JSON holds lifetime, pending requests and roots. Results/request/apply histories, last-applied paths, plans/selection/progress and large Library preparation/restore inventories use page indices. CLI returns previews/counts or root-bound pages, refusing cursors from another root.

## Accepted writes and immutable results

Product overlay v3 uses segmented raw SJR2 frames under SJS1 control. A 16MiB/4,096-frame append unit rolls to another segment and fixed metadata roots. Capture persists accepted writes, roots and protection at its boundary; payload reads/hashes and independent preservation run outside that boundary. The same request returns its first fixed result; later edits remain in the live workspace.

A live direct journal with native file pins and a pinned journal directory retains up to four sealed-segment read handles. Admission verifies the exact descriptor, physical length, whole-segment SHA-256 and opened native path and identity. Retained handles exclude writes and deletion. When the catalog root changes, reuse requires the same descriptor. Eviction closes the least recently used handle. Read-only journals and journals with mutation observers use one reader. A fresh capture closes the cache and pending captures use one reader until alias completion. Fresh and resumed segment retirement close the readers before unlinking, and journal disposal closes the remaining handles.

A same-sequence checksummed `capture-freeze` frame records a chunked control root in the pending-capture index before `capture.json` and pins. Recovery replays that index first, repairs the exact missing/torn capture-control prefix, then restores pins before GC. Cross-store frozen index references remain protected even without the external header. Capture completion needs an exclusive native reader fence before its materialized marker/alias cleanup; immutable historical reads use the result store. Live index roll and closed-segment collection retain these protections and use bounded outside-boundary copy/tail replay.

The accepted source seal chains actual checksummed source frames, accepted source-frame bytes and sequence. Same-sequence CAS adoption, journal forgetting, segment/index relocation and reclamation preserve this logical seal. Physical backing identity, hashes, pages and exact inventory remain separate proofs: equal logical identity never authorizes deleting changed or unowned data. `physicalJournalBytes` and accepted `sealJournalBytes` measure different quantities.

For a live direct segmented journal, the owned provider flushes and verifies the physical seal under the journal writer gate. It checks the native head, length and frame checksums against the live accepted chain before replying with the exact request and provider lifetime. The gate serializes this proof with segment rolls. Final release compares the before/after seals and verifies the stopped journal and reclamation inventory.

Library/managed-original journals also pack partially live closed segments without a CAS reader. A new opportunistic plan admits a source with live ranges and at least 4 KiB of reclaimable physical bytes. A normal journal segment also needs at least 4 KiB of dead payload or reclaimable bytes totaling at least 25% of its physical length. Already packed raw backing uses the 25% condition. Forced packing keeps the 4 KiB physical threshold, and recovery resumes the accepted request and its frozen roots.

The frozen plan sorts binary extent records in bounded scratch and coalesces their live physical intervals. It constructs the durable relocation map only for admitted sources and advances through targets up to 16MiB. Data-only negative IDs are excluded from normal SJR2 replay. Conditional original-block/offset relocation preserves concurrent edits. Native identity and hash checks precede exact old-alias deletion. Capture- or reader-protected backing stays retained and accounted until deletion succeeds. Temporary COW metadata can grow during an accepted packing request and is reclaimed after it drains.

Live metadata collection defers before preparing or replaying a shadow while an admitted index cursor prevents publication. An existing collection intent remains fixed for recovery, including forced calls; this postponement does not claim completed collection. Once readers drain, collection resumes with all accepted writes and its final caught-up-root/reader checks. This avoids rebuilding an unpublished shadow repeatedly during a long directory traversal without weakening reader protection. Focused qualification is recorded below; upgrade and measurement of the retained 100,000-item providers remain pending, and no actual speed improvement is claimed.

Resuming that same copy reconstructs process-local read admissions from the complete fixed node cursor once; journal-backed nodes still come from replay. An unrecorded replaced basis read can retire without a frame only when it is deleted, unlinked, absent from current and durable inventories, has its deterministic basis ID and owns no private ranges. Completed range-adoption receipts are checkpointed separately from source mutation frames. Catch-up admits only additions from their exact accepted checkpoint root, preserving every earlier receipt and proving the owned capture identity and complete adoption map before the ordinary page/graph copy. Final source seals, all logical roots, range/storage accounting, native backing and same-point publication checks remain. Missing proofs or other divergence preserve the existing request and both stores; recovery does not reset the intent or start a replacement collection.

Offline product-overlay-v3 replay reads the fixed source index through a retained read-only store and writes derived COW pages only to a separately owned scratch store. The scratch uses the same logical store identity and a non-overlapping container-address domain; it neither appends to the source index nor copies the complete metadata graph. Windows restore callers supply native file pins. Scratch directories are exclusively created relative to a pinned parent, record the exact created native identity, and retain a read/list fence that allows child operations while excluding directory replacement. Native path opens use absolute extended Windows/UNC paths; existing content, ownership and ancestry checks remain.

An admitted restore cursor retains its source index, owned basis, journal backing and derived scratch until its last reader closes, even if the originating journal owner has been disposed. Only then can exact owned scratch reclamation run. Interrupted ownership publication or conflicting files remain preserved and observable. Offline overlay-v3 `ObserveChanges` returns `SourceObservationUnavailable`: use the exact owned live provider for rebindable change roots. The separate overlay-v2 development-candidate path does not provide a product fallback.

Immutable whole content, private ranges and metadata are shared within the home. Results can compose a fixed basis with private chunks/slices; mutable originals never replace retained content. Adoption checks the fixed file/block/range before changing a live reference, preserving later edits. Frozen roots, readers, pending captures and adoption progress protect metadata and backing segments before sweep.

Whole-object and raw-range pools each deduplicate exact immutable content. A new private chunk can reference an already owned whole object with the same complete SHA-256 and length. Before its first generation-basis header is published, a non-Git basis file can instead acquire a peer reference to an exact owned raw chunk covering that entire file. Composed-file descriptor codec v3 records this raw-basis choice separately from the protected external-Git-basis choice; the two flags are mutually exclusive. Existing fixed headers/roots are unchanged, and arbitrary partial-hash/subrange matching is not used. Earlier whole/raw copies can therefore coexist. Storage observations distinguish pool kinds; actual physical sharing is measured by native file-identity union.

A managed None input basis has a different lifetime from permanent result storage: its files retain the single-link input guard and later return to an ordinary mutable original. Preparation establishes it by rename and indexing without copying payload. The first independent checkpoint can copy every unique basis version into the whole-content pool unless an exact owned object is already available. A/B and later results share those canonical objects. While the input basis remains active, basis/CAS bytes can coexist; this is lifetime-separation overhead, not eliminated duplication or entirely unavoidable data. Allocation reports keep preexisting basis identities and additional CAS identities separate. The fixed 100k fixture has only sixteen 32-byte variants (512 unique logical payload bytes); that does not predict the retention cost of a project with mostly unique assets.

Git original-file publication preserves HEAD/index/branch. Normal capture retains file/range results and a protected immutable Git basis; commit/tree/ref materialization is deferred until explicit branch integration requires it. Required protected objects remain; Splinter does not run repository GC or remove non-owned objects. Plastic retains fixed revision, registration, administration and lock guards without automatic check-in.

Git data operations, including silent index refresh and streamed object creation, follow caller cancellation without an absolute elapsed-time quota. Fixed control queries retain their bounded deadline. Cancellation or a failed producer terminates only the owned subprocess and drains its input/output tasks before returning. A timeout never authorizes deleting an outstanding Git lock or creating another task to bypass it.

## Original publication and maintenance

Every target and required ancestor is checked/pinned before mutation. The resource policy selects 8–32 workers to prepare/publish independent files, retaining topology/companion order, serialized durable progress batches and failure/cancellation drain. Staging permits at least one largest payload for existing recovery. Additional parallel staging is bounded by the worker count, one quarter of the working target and one quarter of observed free disk space; per-file disk-space checks remain. This is a disk allowance, not preallocation or RAM consumption. Full selection is indexed; its preview is at most 100 entries/4,096 UTF-16 characters and can be empty for long paths. Same-intent/digest retry may omit paths to recover fixed selection; omitted paths on a new intent still mean full scope.

`NotContentIndexed` is the original path's local indexing policy. Atomic application saves can drop this bit; publication preserves the observed target bit for Git, None and Plastic. Review digests and conditional publication still bind the exact observed target metadata/identity. Hidden/System/ReadOnly, unsupported storage attributes and content guards are unchanged.

Maintenance freezes authoritative roots before the store's exclusive collection fence. Workspace stores use their operation lock; shared metadata holds its publication lock and reads anchors before all retained headers; canonical content/range catalogs retain their operation locks. Collection intents/receipts use checksum-protected internal protocol v2 and refuse previous/corrupt state. Copied target pages and native identities are checked before location publication and old-container deletion. Graph copying and a checksummed one-hop location index preserve published references/logical hashes while reclaiming unreachable owned pages. Native creation receipts precede container payload, and deletion verifies that recorded native identity.

Use `workspace maintain --id <id> --request-key <key> --scope workspace|shared|content|ranges|all`. Capture/apply schedule it after sufficient new metadata; the 4MiB scheduling trigger never rejects input. Final release forces it after delta removal and retained-result maintenance, before shared-basis release. Pending requests block changed keys/scopes and new mutations; normal Editor stop remains available. Status observes the fixed stage/next action without collecting. Completed historical maintenance retries return only their receipt.

Unknown unreferenced scratch/ownership-creation gaps remain protected in a durable paged inventory with a summary count; unknown replacements of live roots/containers still refuse collection. Read it with `workspace read --collection maintenance-residuals --id <id> --request-key <key> --store-scope <store>` and its root-bound cursor. Store scopes are `workspace-history`, `workspace-original`, `workspace-applied`, `workspace-results`, `shared`, `content`, `ranges`. Space/I/O failure retains the accepted request/root: restore capacity/access, then resume the same identity.

Deferred backing and retained-reference summaries use `workspace read --collection deferred-reclamation --store-scope content|ranges|content-references|journal-packing|journal-indices|read-only-replay`. Original publication scratch uses `--collection preserved-scratch --store-scope workspace-original`; it is not a deferred-reclamation scope. Journal queries bind ownership to the exact overlay identity and use disk-backed pagination; mandatory lifecycle qualification remains in progress. `read-only-replay` inventories active, pending or preserved offline scratch scopes without collecting them. For `journal-indices`, use a returned request key to page its preserved native inventory. Unknown container-header/control creation gaps are preserved outside the reclaimed delta. A separate stopped-restore recovery can retain an entire index intact after binding the existing segmented-reclamation receipt, fixed seal, all frame/control/root proofs and exclusive reader/native inventory fences. Its `stopped-source-index-retained-intact` inventory retains owned and unowned files alike; it authorizes neither payload pruning nor ownership adoption. Active roots, foreign replacements and unsupported pending/relocated domains still refuse recovery. Selection uses `--collection selection --plan-id <digest>`. Retain the schema's exact owner/scope/root-bound cursor. A referenced or deferred item is not permission to force-delete its backing.

Optional `SPLINTER_RESULT_GENERATION_DIAGNOSTICS=1` records per-stage timing under the task's `diagnostics` directory. It defaults off, never supplies recovery authority and does not change success if diagnostic logging fails. Capture request duration and the measured accepted-write pause are separate observations.

## Implementation ownership and qualification

Runtime owns page/catalog/sort/path/range indices, segmented journal/capture/history, immutable content/range stores and metadata collection. Files owns manifests/results, adoption, conditional publication and maintenance root discovery. Git owns fixed-object proofs, streamed interpretation and deferred branch results. Windows owns native fences, WinFsp, directory capture and paged Library restore. Core supplies portable ports/roots; Protocol/CLI supply schemas and cursors. No DB, daemon, new serializer or Unity integration package is added.

A pending live-index copy resumes before independent segment collection. A reader-deferred copy keeps its fixed request and blocks those catalog mutations. Recovery of an already committed earlier ordering change can remove only absent normal header-only descriptors from the shadow after every non-segment root, accounting value and accepted-write seal agrees; remaining descriptors receive full native/length/hash checks before the final same-point publication guard. It never unlinks source files, resets the intent or accepts retirement of a nonempty segment through this narrow route. Real killed-child tests cover both normal ordering and the already-trimmed empty-header case.

The R14 focused native run selected 34 tests: 33 passed, none failed and one subprocess-only actor entry was skipped in the parent listing; its parent test executed the real killed-reader recovery. This covers extended-path atomic creation, admitted-reader lifetime, source-index native identity/length/SHA-256 remaining unchanged, and a real 96MiB replay tail crossing the 64MiB scratch-container boundary through managed restoration and reclamation. R17's combined focused run selected 107 entries: 106 passed, none failed and one subprocess-only actor entry was skipped. It includes intact stopped-index recovery and the cache/LRU/collection guards; neither run is the final SCAL gate.

The separate Git Unity cleanup then resumed its existing plan/cursor once with R17 and restored the ordinary Library. All 1,477 planned files remained verified, the assembly MVID matched the earlier loaded Editor proof, original Git administration remained unchanged, and all six retained A/B results passed independent payload/Git-boundary verification. The earlier replay's three-container index remains intact: 156,775,860 logical bytes, including its previously owned container and two containers still without ownership receipts. The seven retained index files occupy 156,778,744 allocated bytes, with 20,632 further allocated bytes for preservation controls. The whole basis-control directory retains 169,801,528 allocated bytes, a separate scope that includes other retained metadata. Native identities and SHA-256 matched before/after preservation; no payload was pruned or adopted, and cleanup is not a zero-residual claim. Original-Editor preservation through workspace reclamation was proved before this separate experiment cleanup.
