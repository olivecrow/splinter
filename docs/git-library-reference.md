# Git source and original Library references

[한국어](ko/git-library-reference.md)

The Git commit/tree/blob basis of `git-snapshot` can be read together with an immutable basis of the original Library. Even though Git does not track Library, its separate basis's exact id, owner, manifest, and read proof are fixed in the mount and journal. No initial full copy, read hydration, whole-file copy-up, or VSS is used. Original and A/B read the same Library basis and write to their own range journals.

<a id="명시적-수명주기"></a>
## Explicit lifecycle

Application-specific Library descriptors, original reservations, and compatibility keys are selected by explicitly injecting the Unity policy. Managed-basis state and preparation intent support only v2, fixing application/directory kind; v1 is preserved/rejected. Common extension contracts follow [extension boundaries](extensibility-boundaries.md).

The user-authorized exception is **converting only Library into a managed mount**. Project root and source remain at the existing NTFS location. Save and normally shut down the original Editor for initial attachment and final restoration. Splinter commands do not automatically stop or reopen it.

1. `library prepare --project <original> --key <stable-key> --home <same-volume-home>` renames the existing Library to the owned `library-bases/<id>/base` on the same NTFS volume, then attaches an original-only writable WinFsp overlay at the existing `<original>/Library`.
2. Fix returned `data.basis.basis.id` in `workspace ensure --storage git-snapshot --library-basis <id>`. Preserve original/task home, project, and id. An omitted Library basis in an existing cold Git path is not automatically selected or changed.
3. `library status --id <id> --home <home>` reads durable state. It is not evidence of Editor, compilation, or MCP readiness. MCP/CLI must always compare the returned workspace path with actual Editor PID/start time.
4. Explicitly checkpoint/release or discard each task. Owned mount/provider/delta must actually be absent before removing generated-data dependencies. Reclaiming A does not remove B's basis or writes.
5. After normally shutting down the original Editor, run `library restore --id <id> --home <home>`. Task dependencies and all basis readers must be absent. Fix the final file-structure metadata plan and journal seal, then move existing files within the same volume and overwrite only private ranges. Reclaim the owned base and original delta after original Library is again an ordinary NTFS folder.

Use the same key/id/home, compatibility key, manifest, and request. If original and base both exist during preparation, or restoration encounters unexpected files, changed retained regions, or a different seal, preserve and reject. Initial file hashes and fixed metadata are checked; readers block direct writes/deletion of existing basis files. Reads use only the manifest and open basis handles. Missing/damaged generated data does not fall back to the mutable original or an empty Library.

The owned reader pins its immutable root with native directory read access and no write/delete sharing. Ancestor handles deny deletion but allow ordinary child-file publication; the held child chain prevents them from becoming empty and being converted to junctions. Availability uses these held handles instead of repeating directory-existence queries. Admission still rejects reparse paths; concurrent reads retain their file handles until every close has drained them, and observed read failures make availability fail. Unchanged-directory restoration explicitly hands the root to a moving handle and checks the same volume/file identity across that narrow handoff. Interruption/replacement preserves and rejects; new-reader same-plan recovery remains. See [SA-01](verification/startup-additional-optimization.md) for empty-root/ancestor protection and bounded qualification.

Before preparation metadata, fix project/key/paths/compatibility keys in current-version `prepare-intent.json`. A content-read failure before moving the original can resume with the same request only when the exact intent and classified metadata remain. Roots without intents, different requests, provider-execution traces, and unknown data are preserved/rejected. Explicit restore of an unpublished `preparing` state can return the original or moved base unchanged; unknown execution/nonempty deltas are not canceled.

If Library contains logs continuously written by an external server, its basis cannot be fixed. First handle that server's lifetime/log location through the caller's separately authorized procedure. Splinter neither automatically stops it nor omits input files.

## Restoration and cost boundaries

Restore resumes from a durable plan and completion cursor. Started file moves/range writes are verified/redone under the same plan; changes to already completed files are rejected. Retained length and private ranges prevent truncated basis tails from reappearing. New files write zero holes and new payload without copying the rest of existing file data. Owned payload is deleted only after independent verification of the final original Library content. Interruption injection in small-file tests does not qualify real OS power failures.

Current restore plan v2 verifies NTFS volume/file identities for existing files and creation receipts for new files. Move, range write, and metadata application occur while file/parent-path handles protect them. On resume before/after the completion cursor and before final reclamation, replacement files are rejected even if content matches. Interruption after new-file creation but before receipt publication requires preservation; path existence does not prove the same file. Preserve target, basis, journal, and receipts; do not automatically migrate earlier restore plans.

For an unchanged file, the verified/pinned basis manifest supplies the final and retained hashes during planning. Execution freshly verifies the saved file identity and full content, then moves and applies metadata under that same no-write/no-delete handle; renamed or metadata-only files use the same path. Changed files retain their private-range replay and durable data flushes. A retry already matching the final hash skips only the duplicate hash under the same exclusive output handle. Parent directories are canonicalized and pinned root-first without repeating full ancestor walks for every ancestor. Completion cursors advance every 128 files and at the final file; initial/final records, new-file ownership receipts and range-data flushes remain individually durable. A failed batch publication can leave up to 128 completed effects to revalidate on resume, alongside any in-progress effect. File identity/content, foreign-target, plan/seal and cleanup guards remain. This file-level route keeps the existing v2 plan/cursor format. See [verification and bounded costs](verification/lifecycle-read-optimization.md).

A fresh, completely unchanged original Unity Library with an SJL4 journal instead uses one no-replace directory rename. Sequence zero and exact logical manifest equality select this path; changed originals, SJR2, whole-project bases and started v2 file plans keep general restoration. The separate v1 directory plan fixes root/descendant NTFS identities, original/delta paths, overlay identity, manifest hash and seal. After the required descendant-handle gap, full identity/content/membership verification gates metadata restoration and exact SJL4 reclamation. Root and ancestor handles stay pinned; unexpected or replaced entries are preserved and rejected. Retries reprove content and reapply metadata, with a plan-bound verified receipt and resumable reclamation inventory. Optional absent plan/cursor records do not wait under the serialized restore lease. See [LO-09–11](verification/lifecycle-read-optimization.md) for recovery boundaries and small-input costs; no new large Unity result is claimed.

The shared basis is moved data, so it is not counted as new full-payload cost. Manifests, file handles, providers, and each journal have separate costs. Full read verification incurs I/O; Unity reimports or rewrites of its caches also store private ranges. File references do not establish shared Unity heap, graphics, or scene RAM. RAM measurement distinguishes Private Bytes, resident pages, and PSS estimates in `scripts/measure-process-memory.ps1`. This script queries page metadata/residency only, without reading original payload or performing GC/working-set trim. Retain the ShareCount cap of 7, non-atomic sampling, and unknown sharing attribution between Editors.

Pass exact `-WorkspaceIds` and `-GeneratedDirectoryIds <basis-id> -SkipOriginalLibrary` to existing `scripts/measure-workspace-storage.ps1` for file-allocation measurement. Compare selected state/project/owner/paths and count the shared basis root once. Long NTFS paths are also passed to Win32 queries. `moved-original-Library-payload` is moved pre-existing data, excluded from additional costs. Distinguish original delta, basis metadata, each task delta, shared runner/Git, and evidence costs. These file samples do not establish whole physical peak/VSS attribution.

Only ordinary NTFS files/directories are covered. Reparse, hardlink, ADS, EFS, NTFS compression, sparse inputs, separate security descriptors, and OS failures need additional qualification. Existing VSS/development single-view Library-cache qualification does not transfer to this path. Follow the [execution plan](plans/git-library-reference.md) and [verification](verification/git-library-reference.md) for selected scope and current qualification.

## Content-proven source timestamps

Preparing a new Unity Library from an ordinary Git repository root fixes a commit/tree and reads each eligible original file under the same no-write/no-delete-sharing handle. Only a matching raw Git blob hash admits its timestamps. Checkout CRLF conversion, changed/missing/busy files do not qualify. Source handles close after preparation, so the original remains editable afterward. This adds one full source-content read without copying payload or adding a cache. Non-Git inputs and linked roots with a `.git` file do not select this optimization; existing input admission remains unchanged. A damaged ordinary Git root, partial clone, shallow history or alternates is preserved and refused.

Atomically published `source-metadata.json` v1 includes a canonical-content `contentHash`. The complete Library tuple/manifest hash and whole-map `sourceMetadataHash` bind the map to the basis reference and Git receipt/snapshot identity. Pre-state retries also verify the same intent, paired Library manifest/proof and internal map proof, then reuse existing bytes. There is no mutable-original reread or automatic corruption repair. Only the same path/blob/length gets captured timestamps; unmatched entries and directories keep snapshot capture time. Existing bases without a map are not backfilled. See [SU-05](verification/startup-profile-optimization.md) for schemas, regression, additional read cost and the unexecuted new full A/B boundary.
