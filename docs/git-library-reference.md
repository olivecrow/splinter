# Git source and original Library references

**Recorded Unity costs:** UF-01 prepared the original Library in **115.9s** and restored it to ordinary NTFS in **126.0s**. This is one historical `116fd44` run using the 3,141,660,252-byte original Library; the complete A/B workflow took **1,083.0s**. These times have not been remeasured with the subsequent time and memory optimizations, and do not expand the separate small-fixture qualifications below.

The Git commit/tree/blob basis of `git-snapshot` can be read together with an immutable basis of the original Library. Even though Git does not track Library, its separate basis's exact id, owner, manifest, and read proof are fixed in the mount and journal. No initial full copy, read hydration, whole-file copy-up, or VSS is used. Original and A/B read the same Library basis and write to their own range journals.

## Explicit lifecycle

Application-specific Library descriptors, original reservations, and compatibility keys are selected by explicitly injecting the Unity policy. Managed-basis state and preparation intent support only v3, fixing application/directory kind; earlier versions are preserved/rejected. Common extension contracts follow [extension boundaries](extensibility-boundaries.md).

The user-authorized exception is **converting only Library into a managed mount**. Project root and source remain at the existing NTFS location. Save and normally shut down the original Editor for initial attachment and final restoration. Splinter commands do not automatically stop or reopen it.

1. `library prepare --project <original> --key <stable-key> --home <same-volume-home>` renames the existing Library to the owned `library-bases/<id>/base` on the same NTFS volume, then attaches an original-only writable WinFsp overlay at the existing `<original>/Library`.
2. Fix returned `data.basis.basis.id` in `workspace ensure --storage git-snapshot --library-basis <id>`. Preserve original/task home, project, and id. An omitted Library basis in an existing cold Git path is not automatically selected or changed.
3. `library status --id <id> --home <home>` reads durable state. It is not evidence of Editor, compilation, or MCP readiness. MCP/CLI must always compare the returned workspace path with actual Editor PID/start time.
4. Explicitly checkpoint/release or discard each task. Owned mount/provider/delta must actually be absent before removing generated-data dependencies. Reclaiming A does not remove B's basis or writes.
5. After normally shutting down the original Editor, run `library restore --id <id> --home <home>`. Task dependencies and all basis readers must be absent. Fix the final file-structure metadata plan and journal seal, then move existing files within the same volume and overwrite only private ranges. Reclaim the owned base and original delta after original Library is again an ordinary NTFS folder.

Use the same key/id/home, compatibility key, manifest, and request. If original and base both exist during preparation, or restoration encounters unexpected files, changed retained regions, or a different seal, preserve and reject. Initial file hashes and fixed metadata are checked; readers block direct writes/deletion of existing basis files. Reads use only the manifest and open basis handles. Missing/damaged generated data does not fall back to the mutable original or an empty Library.

Preparation and dependency changes hold the exact basis gate. Optional intent/request/dependency reads under that gate can establish absence immediately because another publisher is excluded. Actual native sharing conflicts retain the ordinary bounded read grace; complete receipt/request identity validation and same-request recovery remain required.

For a fresh delta, the client initializes journal metadata from the exact fixed root and Library manifest/read proof, holding their metadata leases and root namespace handles. It neither opens Library payload files nor provides a payload reader; its initialization proof permits only root metadata. A created delta is therefore not content-verification or mount-readiness evidence. The provider still opens, fences and hashes every Library file before publishing the mount. Current identity, initialization intent, individual durable flushes and same-request interruption recovery remain unchanged; mismatched metadata or identity is preserved and rejected. The initial Library capture still records its content hashes, with no payload copy or cache. See lifecycle cost optimization for this boundary and its bounded validation.

The owned reader pins its immutable root with native directory read access and no write/delete sharing. Ancestor handles deny deletion but allow ordinary child-file publication; the held child chain prevents them from becoming empty and being converted to junctions. Availability uses these held handles instead of repeating directory-existence queries. Admission still rejects reparse paths; concurrent reads retain their file handles until every close has drained them, and observed read failures make availability fail. Unchanged-directory restoration explicitly hands the root to a moving handle and checks the same volume/file identity across that narrow handoff. Interruption/replacement preserves and rejects; new-reader same-plan recovery remains. See SA-01 for empty-root/ancestor protection and bounded qualification.

Capture, provider admission and unchanged-directory restoration also pin every descendant directory root-first, including empty directories. Within that scope, a child open requires its direct parent to remain pinned instead of repeating the full ancestor walk. Native leaf opens still reject reparse/unsupported types and hardlinks and verify the handle's identity and final path. This uses one additional handle per descendant directory; it does not cache file contents. A proof is valid only while its handles are held and is not carried across their restoration handoff gap. The final post-move proof freshly verifies descendant identities, full contents and exact membership before metadata restoration and reclamation.

Capture, provider admission and directory restoration use **up to eight workers, each using a 64KiB hash scratch buffer**, after pinning the complete directory map. All workers finish before failed or cancelled operations release their handles; indexes and mounts remain unpublished until all required checks pass. Restoration retains fresh post-move identity/content verification and directory-last metadata. File fences block writes, deletion and replacement of existing leaves; they do not prevent new children. Complete membership proof must therefore still gate verified publication and reclamation. The lifecycle throughput verification owns the original parallelism measurements; the former two-worker admission measurements remain historical time and memory evidence. The new original-Unity-Library root-delta/topology routes below cover their eligible changes; whole-project, append SJR2 and fresh preference rejection retain general per-file restoration.

Before preparation metadata, fix project/key/paths/compatibility keys in current-version `prepare-intent.json`. A content-read failure before moving the original can resume with the same request only when the exact intent and classified metadata remain. Roots without intents, different requests, provider-execution traces, and unknown data are preserved/rejected. Explicit restore of an unpublished `preparing` state can return the original or moved base unchanged; unknown execution/nonempty deltas are not canceled.

If Library contains logs continuously written by an external server, its basis cannot be fixed. First handle that server's lifetime/log location through the caller's separately authorized procedure. Splinter neither automatically stops it nor omits input files.

## Restoration and cost boundaries

Restore resumes from a durable plan and completion cursor. Started file moves/range writes are verified/redone under the same plan; changes to already completed files are rejected. Retained length and private ranges prevent truncated basis tails from reappearing. New files write zero holes and new payload without copying the rest of existing file data. Owned payload is deleted only after independent verification of the final original Library content. Interruption injection in small-file tests does not qualify real OS power failures.

The general per-file restore plan v2 verifies NTFS volume/file identities for existing files and creation receipts for new files. Move, range write, and metadata application occur while file/parent-path handles protect them. On resume before/after the completion cursor and before final reclamation, replacement files are rejected even if content matches. Interruption after new-file creation but before receipt publication requires preservation; path existence does not prove the same file. Preserve target, basis, journal, and receipts; do not automatically migrate earlier restore plans.

Streaming restore plans build GUID-addressed file records from a bounded checksummed sort spool instead of repeatedly rewriting the file index. After an eligible root move, unchanged payload files reuse one root/ancestor/descendant-directory proof within the current batch scope. Up to eight workers verify exact native identities and full hashes and restore metadata for at most 128 files; every worker joins before the existing ordered durable cursor advances. Scope fences close before parent-relative moves or private-range writes use their ordinary guards. Retries reprove the original identities and bytes; final membership, metadata, interruption and reclamation checks remain. Started plans retain their fixed route and individual timeout bounds are unchanged.

For a fresh paged Unity Library with sequence zero, complete streamed namespace/metadata/range comparison must also prove exact equality with the fixed manifest. The unchanged variant of current paged plan v3 records a single bounded catalog containing all native identities and expected metadata/hashes. It omits unused GUID file records, path-name indexes and private-range plans. The initial fully hashed basis reader supplies identities from its still-held handles; catalog construction consumes a complete checked native-membership stream before publishing the plan or moving the root. The same-volume no-replace rename retains exact root and ancestor protection across the required descendant-handle gap. After the move, every native identity and byte is freshly verified by up to eight demand-driven workers fed from the exact native-membership cursor. Catalog production overlaps verification without a per-128-file join barrier or an unbounded metadata queue; only the required native fences persist in ordered handle chunks. Every worker joins before success, failure or cancellation can release fences. Directory-last metadata and a separate final membership pass precede the plan-bound verified cursor and exact journal reclamation. A retry before the move redoes the complete physical proof; retries after verification still reprove the final tree. Reclamation resumes only its existing exact inventory. A zero seal alone never substitutes for journal-effect or physical proof. Changed inputs and in-progress general plans retain general paged execution.

General paged planning bulk-builds path components through the bounded checksummed sort spool, validating duplicates before plan publication. Resolution can reuse one decoded parent prefix only for the exact immutable name root while the metadata store retains the same no-write/no-delete container proof epoch. Eviction, write-shared reads, root replacement and disposal revoke that reuse. Native membership merges one complete checked catalog traversal with sorted component cursors for its open ancestors, without rereading each directory's children, repeating root-to-parent lookup or descending into unknown directories. Directory sorts retain the shared bounded-memory/disk fallback. General restore still admits an existing subset while planned paths are absent; the unchanged route requires exact membership. A journal's empty hidden-path tree is validated once per directory cursor and needs no per-child path digest; nonempty hidden trees retain every ordinary lookup and backing check. These optimizations do not omit native leaf opens, complete hashes, final membership or durable publication.

In the general per-file route, the verified/pinned basis manifest supplies an unchanged file's final and retained hashes during planning. Execution freshly verifies the saved file identity and full content, then moves and applies metadata under that same no-write/no-delete handle; renamed or metadata-only files use the same path. Changed files retain their private-range replay and durable data flushes. A retry already matching the final hash skips only the duplicate hash under the same exclusive output handle. Parent directories are canonicalized and pinned root-first without repeating full ancestor walks for every ancestor. Completion cursors advance every 128 files and at the final file; initial/final records, new-file ownership receipts and range-data flushes remain individually durable. A failed batch publication can leave up to 128 completed effects to revalidate on resume, alongside any in-progress effect. File identity/content, foreign-target, plan/seal and cleanup guards remain. This file-level route keeps the existing v2 plan/cursor format. See verification and bounded costs.

A fresh original Unity Library with an SJL4 or bounded SJR2 journal and exact final logical manifest equality uses one no-replace directory rename, including a positive sealed sequence whose final state meets all equality conditions. The separate v2 directory plan fixes journal mode, root/descendant NTFS identities, original/delta paths, overlay identity, manifest hash and exact seal. After the required descendant-handle gap, full identity/content/membership verification gates metadata restoration and exact mode-specific reclamation. Root and ancestor handles stay pinned; unexpected or replaced entries are preserved and rejected. Retries reprove content and reapply metadata, with a plan-bound verified receipt and resumable reclamation inventory. Optional absent plan/cursor records do not wait under the serialized restore lease. LO-09–11 retains the original sequence-zero evidence.

If all directories and surviving file paths/lengths remain unchanged with no private ranges or additions, metadata changes and deletion of existing leaf files use a separate **sparse directory plan v1**. It binds final metadata, sorted deleted paths and every basis identity; the root moves once and deleted leaves move to predetermined receipt-root staging names. The full survivor proof remains pinned. Only after exact membership, metadata and the plan-bound verified receipt does an explicit staging-reclaim receipt authorize destruction of staged data; the exact journal inventory follows. Missing/duplicate staging locations, changed identities/content, unknown files, or conflicting/orphan modes are preserved and refused. Started plans keep their original route. Append SJR2 and whole-project restoration remain general; original Unity Library additions, ranges, directory deletion and renames follow the root-delta/topology rules below. No older plan is migrated. See BO scope and verification; component restore savings do not establish new Unity whole-lifecycle speed.

### MX05: root-first restoration of changed Library contents

A and publication-count-guarded B2 were adopted after ordinary-NTFS restore comparisons and the full gate. This section describes the current uncommitted implementation pinned by base commit and exact source hashes. Fresh priority is unchanged → sparse → root-delta → eligible and preferred topology → general. Root-delta/topology support requires `ApplicationKind=unity`, `DirectoryKind=Library`, `Basis.RelativePath=Library` and SJL4 or bounded SJR2. Whole-project restoration does not use these routes. Started current-format plans resume their original protocol independently of fresh policy; conflicting/orphan modes preserve/refuse, without format migration.

**Root-delta v1** transfers the root once when directory membership/spelling and source-backed file paths are unchanged, leaving stable files in place. It applies private ranges, truncation/extension/zero holes and new leaves; only deleted leaves stage at fixed receipt-root locations. Fixed plan/independent intent hash, sealed replay, existing NTFS identities, new-leaf ownership receipts and per-file write/complete records remain. Retained/private data before writes and completed files during resume are reverified; range data flushes durably before success receipts. Final full content/identity/membership proof, directory-last metadata and verified/reclaim authorization precede deletion and exact journal reclamation.

**Topology v1** plans minimal preserving/deleted units not explained by their parent mapping. Deeper split children stage first; shallow final parents/new directories install before file moves and range writes. The plan/intent and cursor zero publish durably before the root move; each topology effect is followed by a cursor publication, with separate identity receipts for new directories. Resume reconciles the same plan's k or k+1 inventory against actual type/path/identity. Syntactic inventory projection does not replace native proof. Deleted stages reclaim by exact handles only after final full proof, metadata and plan-bound reclaim authorization.

Fresh topology preference is `T < F && O + N <= G`, where `G=ceil(F / ManagedDirectoryRestore.CursorBatchSize)`. `CursorBatchSize=128` is shared by general execution and the policy. `F` counts surviving source-backed files; `T=1 + 2×live non-root units + deleted non-root units` counts preserving moves including the root; `O` counts topology operations; `N` counts new-directory receipts. New files do not increase F. These are structural floors, not elapsed-time guarantees or 128-operation topology cursor batching. Fresh requests failing the preference use general restoration; published topology intents do not reacquire this cost condition.

Original and receipt forests retain separate path/identity proof roots. Receipt-root sharing permits writes for control publication, denies delete sharing and retains pinned control files. After complete directory maps freeze, at most eight workers hash full contents through the same handles; errors/cancellation join all workers before disposal. The caller owns the borrowed original root, and deleted directories retain DELETE access. Final TreePins/current membership/metadata proof remains. Each worker's 64KiB scratch buffer does not bound total plan/proof/handle memory.

New file/directory creation and topology child staging/install bind the exact verified parent handle plus leaf name; creation is no-replace. Files use the same created handle as their stream and flush before identity receipt publication. Failure neither deletes the node nor adopts it merely by path existence. Empty parents can undergo FILE_WRITE_ATTRIBUTES reparse conversion; the data-write fence is not universal reparse prevention. Current type/path/identity rechecks and parent-relative native effects provide outside-path containment. Only a plain regular unpublished control temporary with an exact canonical stem, 32-digit GUID and `.tmp` suffix is ignored and preserved. It is never authority, ownership evidence or a deletion target; unknown names, directories and reparses refuse.

Final candidate comparison, full gate and resource disposition are complete. Ordinary-NTFS fixed restoration 46.05306965→14.73430160s and bulk 45.36571795→14.74108300s justify retaining A and guarded B2; leaf stays on general restoration and is effectively unchanged at 5.02044795→5.00588275s. Historical A/B1 measurements on distinct runtimes and failed/corrected runs remain in MX05 verification and the program plan. No whole Unity apply/discard, power-loss or peak RAM/CPU qualification is implied.

The shared basis is moved data, so it is not counted as new full-payload cost. Manifests, file handles, providers, and each journal have separate costs. Full read verification incurs I/O; Unity reimports or rewrites of its caches also store private ranges. File references do not establish shared Unity heap, graphics, or scene RAM. RAM measurement distinguishes Private Bytes, resident pages, and PSS estimates in `scripts/measure-process-memory.ps1`. This script queries page metadata/residency only, without reading original payload or performing GC/working-set trim. Retain the ShareCount cap of 7, non-atomic sampling, and unknown sharing attribution between Editors.

Pass exact `-WorkspaceIds` and `-GeneratedDirectoryIds <basis-id> -SkipOriginalLibrary` to existing `scripts/measure-workspace-storage.ps1` for file-allocation measurement. Compare selected state/project/owner/paths and count the shared basis root once. Long NTFS paths are also passed to Win32 queries. `moved-original-Library-payload` is moved pre-existing data, excluded from additional costs. Distinguish original delta, basis metadata, each task delta, shared runner/Git, and evidence costs. These file samples do not establish whole physical peak/VSS attribution.

Only ordinary NTFS files/directories are covered. Reparse, hardlink, ADS, EFS, NTFS compression, sparse inputs, separate security descriptors, and OS failures need additional qualification. Existing VSS/development single-view Library-cache qualification does not transfer to this path. Follow the execution plan and verification for selected scope and current qualification.

## Content-proven source timestamps

Preparing a new Unity Library from an ordinary Git repository root fixes a commit/tree and reads each eligible original file under the same no-write/no-delete-sharing handle. Only a matching raw Git blob hash admits its timestamps. Checkout CRLF conversion, changed/missing/busy files do not qualify. Source handles close after preparation, so the original remains editable afterward. This adds one full source-content read without copying payload or adding a cache. Non-Git inputs and linked roots with a `.git` file do not select this optimization; existing input admission remains unchanged. A damaged ordinary Git root, partial clone, shallow history or alternates is preserved and refused.

Atomically published `source-metadata.json` v1 includes a canonical-content `contentHash`. The complete Library tuple/manifest hash and whole-map `sourceMetadataHash` bind the map to the basis reference and Git receipt/snapshot identity. Pre-state retries also verify the same intent, paired Library manifest/proof and internal map proof, then reuse existing bytes. There is no mutable-original reread or automatic corruption repair. Only the same path/blob/length gets captured timestamps; unmatched entries and directories keep snapshot capture time. Existing bases without a map are not backfilled. See SU-05 for schemas, regression, additional read cost and the unexecuted new full A/B boundary.

The bounded journal's exact reclamation and v2 directory-plan qualification are tracked in BL; previous directory plans are preserved/rejected without automatic migration.
