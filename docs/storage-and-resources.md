# Execution resources and memory reclamation

This is the common contract for per-task process ownership, executable bundles, memory observations, and normal reclamation. Storage lifetime follows [NTFS workspaces](ntfs-workspaces.md) and the selected snapshot-basis contract.

## Processes and memory

The per-task supervisor in `Splinter.Platform.Windows` holds the Windows Job Object handle. It creates Unity suspended and assigns it to the job **before** resuming it, closing the gap for early child-process creation. Breakaway is prohibited. The supervisor and Editor remain alive after the CLI and conversation end. This is not a Host daemon.

The supervisor does not inherit the caller's standard input/output or other inheritable handles. The CLI's JSON response and output streams finish even while the Editor remains alive. Executables share one small bundle per build hash rather than being copied for every task, allowing the product to be rebuilt while running.

Runner-cache publication renames one completed temporary bundle atomically. On Windows, a child reader without delete sharing can reject that directory rename with native error 5. Only native errors 5/32/33 on that same temporary directory and an absent target receive a bounded one-second wait. The source handles and complete target length/hash validation remain; persistent denial preserves the unpublished bundle. No permissions/attributes are changed, no target is overwritten and no original/task/result publication timeout is increased.

`PrepareRunner` computes the content key from the ordered SHA-256 hashes of the current 8 executables. Read-only source handles are held only during preparation to prevent changes between hashing and copying. A new bundle is copied through a fixed-size buffer before its directory is published. Cache length and content hashes are checked by streaming, so reuse does not load entire executables into memory arrays. All source handles close after success or failure; damaged or missing caches are preserved and rejected. Runner-bundle verification records disk reuse and managed allocations in the preparation function. These allocations do not establish Editor or whole-system RAM savings.

Normal stop requires the caller to save and resolve blocking state in the exact Editor before requesting its normal shutdown. After exit, the supervisor checks each remaining process with a single handle for job membership and image identity. Shared Unity licensing clients and unverifiable processes are protected. Automatic job kill-on-close is disabled. Reclamation requires the recorded root exit and confirmed cleanup of owned processes. Shared licensing helpers are excluded from the owned process count.

After a launch, the supervisor records the native root exit code and the empty process group together. A receipt must match the launch token and contain both values. Status exposes the signed 32-bit code as `application.resources.rootExitCode`. A nonzero code produces the phase `exited-abnormally`. A stop that observes this failure returns `EditorExitedAbnormally` and interrupts the current final capture or release before reclaiming the workspace. After inspecting the log and saved files, the caller can explicitly resume preservation using its original request. The released resource record retains the exit code.

`application.resources` reports the number of owned processes, including the supervisor, and observed working set/private bytes. Running values are OS samples at a particular time. Release completes only after verifying `ownershipVerified=true`, `activeProcesses=0`, `workingSetBytes=0`, and `privateBytes=0`, and confirming the actual path is absent after Git reclamation. The result is recorded in `workspace.releasedResources`. Splinter does not forcibly empty OS file caches or standby memory, or claim that whole-system RAM has returned to its pre-execution value.

If the execution receipt lacks job ownership, `ProcessOwnershipUnknown` stops automatic reclamation. Together with `ProcessCleanupIncomplete`, paths, results, and processes are preserved while actual ownership is checked. An Editor timeout alone does not delete source or cache data. Successful release requires current `releasedResources` evidence.
