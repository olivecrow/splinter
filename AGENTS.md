# Splinter contributor instructions

## Workflow

- Read `README.md` and `docs/README.md` first, then only the owning feature documentation. `plan.html` owns product requirements; `docs/foundation.md` describes implementation; `docs/plans/` contains active work and agent procedures.
- Prioritize operational efficiency. Batch independent reads/checks; keep edits and dependent operations sequential. Use subagents only when requested.
- Use `development` for ordinary development and integration; `main` is for releases. Preserve unrelated edits. Do not commit or push unless requested.
- Prefer Unity CLI readiness and popup diagnostics for Unity; distinguish missing Pipeline support or restricted process visibility from Editor absence. Use Computer Use only when needed and release it promptly when finished so the user can use the computer.
- Use short Windows Unity project/state roots and check package paths with the chosen Editor's reader before launch. PackageCache I/O errors fail validation even when compilation or Play succeeds. Preserve existing task identities; choose an appropriate root before creating a fresh trial.
- Preserve the installed Editor version and the user's existing terms, license and preference identity. Do not use `-useTestPrefs`, `-cleanTestPrefs`, profile/environment redirection or consent/license edits to work around shared settings errors. Reproduce serialization contention against a scratch file in batch mode first; a new startup modal fails the trial and requires normal cancellation, not activation or automatic acceptance.
- Use a Splinter workspace when parallel work is explicitly requested or another task occupies the project. Otherwise edit directly. Do not nest a Codex worktree in a Splinter workspace.

## Documentation and repository size

- English is the default and the only language for feature guides, plans, verification, reports and contributor instructions. The only Korean documents are `README.ko.md` and `docs/ko/foundation.md`; keep these two aligned with their English counterparts. Do not create Korean verification results or duplicate other documents in Korean.
- Describe current behavior once in its owning feature guide and link it from `docs/README.md`. Update schemas, fakes and relevant conformance tests when contracts change.
- Keep current limitations and unresolved work. Do not accumulate completion diaries, obsolete plans, benchmark snapshots, screenshots, copied binaries or one-off experiment scripts. Git history provides earlier revisions; it is not necessary to keep old reports in the current tree.
- Keep reproducible tests and reusable diagnostics that exercise current behavior. Generated output belongs in ignored paths. Never delete workspace/basis/result/request state merely because it is old or lies under an ignored directory.
- The project is unreleased: support one current format per product path. Do not retain old-format decoders, migration, aliases or fallback solely for backward compatibility. Unsupported/damaged data must be rejected and preserved. Current-version interruption, lost-response and restart recovery remain required.

## Time limits and verification

- Before work and each preparation/capture/apply/reclamation/validation phase, set an estimate, its evidence, minimum scope and stop deadline. Base full-regression estimates on the complete case inventory and observed aggregate cost, not only a focused subset. If no evidence exists, start with a small representative check.
- At twice the estimate, stop new stages/retries and safely cancel or stop the owned provider. Do not wait simply because CPU/output remains active or extend estimates during execution. Routine phases expected to take tens of minutes are usability defects: diagnose them on a small reproduction first.
- Never force-kill in-progress writes/publication or edit/delete original/task/basis/result/request-key/digest/intent/protection state to escape a timeout. Report an unconfirmed safe stop immediately. Record unresolved failures and reduced/unexecuted coverage honestly.
- After a small reproduction improves, run focused checks before resuming the original operation. Durability/ownership/conflict weakening, skipped checks and larger timeouts are not performance fixes.
- The required complete regression entry point is `pwsh ./scripts/build.ps1`. Bound its execution using the stop policy; do not describe a focused run as a complete gate. Dependency changes require central version/lockfile updates and locked restore.
- Default regression uses the checked-in conservative eight-class xUnit schedule. Tests exhausting a process-wide resource must run in an exclusive collection; keep explicit cancellation and existing timeout bounds. Reuse immutable test catalogs within a sequential class fixture instead of compiling every schema before each test. Metadata capacity qualification is separate: `SPLINTER_LARGE_CATALOG_TESTS=1` opts into large generated inputs and needs its own estimate/stop scope. Do not enable it for routine regression or claim those large sizes passed from the default suite.
- Keep independent behaviors in separate test classes with private mutable fixtures. Size routine branch-selection fixtures around the current boundary; retain assertions for real I/O, ownership and recovery. Separate capacity/cost qualification from functional regression instead of retaining historical scale thresholds in every run.
- Current SCAL qualification remains incomplete. Do not automatically resume retained 100k/17GiB fixtures, Unity sessions, Git/Plastic native matrices or historical benchmark programs. Small component checks do not qualify whole-lifecycle throughput, RSS or OS/power-loss behavior. See `docs/verification/README.md`.

## Product and safety contracts

- `skills/splinter/SKILL.md` owns agent CLI usage. Read each command schema; use returned `data.workspace.path` for file tools/working directories. Preserve project/key/id/home/base/digest during handoff. No automatic Codex binding or arbitrary-file conversation locking is implemented.
- The lifecycle is use when needed → continue the same task → explicitly apply/preserve/discard. Conversation/Editor exit, timeout, lease expiry and disk pressure do not authorize integration or deletion. Release preserves independent results; discard is explicit.
- Preserve original NTFS location/filesystem and concurrent original editability. No initial full copy, read hydration or whole-file copy-up fallback. Git/Plastic/project snapshots and private byte ranges are current paths. VSS/StorageAuthority and ReFS basis designs are retired; do not restore those backends or manipulate OS snapshots/services.
- Managed project/Library preparation moves existing data on the same NTFS volume and exposes a writable original view. Initial preparation/final restore require the exact original Editor to save and stop normally. Restore requires dependent/readers to close; task reclamation only releases its own references. Do not remove VCS information to turn a project into a None input.
- Keep immutable bases, independent results, accepted-source seals, full native identity/hash/page/inventory proof, durable ACK, complete target locks, original/peer ownership, reader leases and same-request recovery. Logical seals never replace physical backing proof. Unknown or unowned data is preserved/refused.
- Runtime metadata maintenance resumes the exact in-progress request before new collection/reclamation. Completed retries return receipts. Editor stop is allowed; automatic integration/deletion is not.
- Intermediate checkpoint preserves a fixed result while task/path/basis/Library continue. Original publication uses explicit result/plan/intent/digest and per-path history. Preserve Git HEAD/index/branch and Plastic administration. A running original requires exact external Editor-cooperation evidence. No automatic commit/check-in or forced conflict resolution.
- Splinter owns returned project identity and its Editor/provider/resource lifetime. Agents and external tools own target selection, connection, refresh, compilation, Play/Test/build, screenshots and acceptance. Match returned project/PID with the workspace; tool-list omission is not proof of Editor absence. Do not retry writes solely on timeout or pin ports across reload.
- Do not add dedicated installers, automatic conversation binding, task queues/mode selection, shared-original-Editor orchestration, general Unity APIs, AI Runner/DAG or daemon/DB writers. M0 and historical experiments are closed; new work needs its own scope.
- Keep Core independent of Win32, Unity, Git and Codex APIs. Use common ports/fake conformance; inject application policy. Host is read-only composition. Product CLI is `scripts/splinter.ps1`; diagnostics/views/probes are `scripts/splinter-dev.ps1` and `tools/Splinter.Development`.
